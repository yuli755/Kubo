# AI开发前必读开发技术细节规范

> 适用范围：任何前端项目，包括 Web、H5、管理后台、官网、可视化大屏、组件库、小程序、跨端和桌面端项目。  
> 文档定位：给 AI 或开发者在真正写代码前使用，约束编码细节、目录组织、类型、接口、组件、样式、状态、测试和交付。  
> 配套文档：开发判断标准见《资深前端编码前必读开发规范》；异常、兜底、恢复、监控见《前端页面兜底机制与稳定性经验文档》。

## 0. 使用方式

开发前先把需求拆成页面、数据、接口、状态、权限和异常，再按本文检查编码细节。

给 AI 的推荐提示词：

```text
请先阅读《资深前端编码前必读开发规范》《前端页面兜底机制与稳定性经验文档》《AI开发前必读开发技术细节规范》。
编码前先说明目录结构、类型定义、接口封装、组件拆分、状态管理、表单校验、错误处理、样式规范和测试点。
不要把请求、业务逻辑、UI 展示、格式化、权限判断全部堆在一个文件里。
```

## 1. 通用编码底线

- 不写无法解释来源的代码。
- 不把临时代码提交为正式实现。
- 不在页面中散写接口地址。
- 不在组件中硬编码大量枚举。
- 不在生产代码中保留无意义 `console.log`。
- 不吞掉异常，至少要提示或记录。
- 不为了省事绕过类型、校验和权限。
- 不把所有逻辑写进一个超大组件。
- 不引入没有必要的大型依赖。
- 不修改无关文件制造额外风险。

## 2. 目录组织

推荐按职责拆分，而不是按随手方便拆分。

```text
src/
├─ api/ 或 services/       接口请求
├─ assets/                 静态资源
├─ components/             通用组件
├─ constants/              枚举、字典、固定配置
├─ hooks/ 或 composables/  复用逻辑
├─ layouts/                布局
├─ pages/ 或 views/        页面
├─ router/                 路由
├─ store/                  全局状态
├─ styles/                 样式
├─ types/                  类型
├─ utils/                  工具函数
└─ tests/                  测试
```

规则：

- 页面只负责编排，不承载所有业务细节。
- 接口请求只能放在 `api/services`。
- 枚举和值映射放在 `constants`。
- 跨页面复用逻辑放在 `hooks/composables`。
- 纯函数工具放在 `utils`。
- 通用类型放在 `types`。
- 页面私有组件放在页面目录下的 `components`。

## 3. 命名规范

- 文件名要表达职责，不用 `test1`、`newPage`、`common2`。
- 组件名用业务名词，不用含糊的 `Box`、`Content`。
- 布尔值使用 `is`、`has`、`can`、`should` 开头。
- 事件处理使用 `handle` 开头。
- 请求方法用业务动作命名，如 `createOrder`、`fetchUserList`。
- 常量用大写或统一常量风格。
- 类型名能区分 DTO、VO、Form、Query、Item。

示例：

```ts
type UserQuery = {}
type UserForm = {}
type UserListItem = {}
type UserDetailVO = {}
```

## 4. TypeScript 规范

- 正式项目优先使用 TypeScript。
- 禁止滥用 `any`。
- 外部接口返回值必须有类型。
- 表单数据必须有类型。
- 组件 props 必须有类型。
- 工具函数参数和返回值必须有类型。
- 复杂对象不要只写 `object`。
- 字典和枚举值要收敛成联合类型或常量。

不推荐：

```ts
const submit = (data: any) => {}
```

推荐：

```ts
type UserForm = {
  name: string
  phone?: string
  status: 'ENABLED' | 'DISABLED'
}

const submit = (data: UserForm) => {}
```

## 5. API 请求规范

- 所有请求必须统一封装。
- 页面禁止直接调用原生 `fetch` 或散写 `axios`。
- 请求层统一处理 baseURL、timeout、token、错误码。
- 接口方法只描述业务动作，不暴露页面细节。
- GET 查询参数和 POST body 要分清。
- 上传下载要单独封装。
- 请求失败要返回可理解的业务错误。
- 不能在请求层静默吞错。

接口文件示例：

```ts
export function fetchUserList(params: UserQuery) {
  return request.get<PageResult<UserListItem>>('/users', { params })
}

export function createUser(data: UserForm) {
  return request.post<UserDetailVO>('/users', data)
}
```

## 6. 数据结构规范

- 前端字段名要和接口约定一致。
- 不在多个页面重复手写同一份结构。
- 金额、日期、状态、权限字段必须明确含义。
- ID 字段必须确认指向哪类对象。
- 可空字段必须在类型中体现。
- 列表项、详情、表单、查询条件不要混用一个类型。

常见拆分：

```ts
type Query = {}
type Form = {}
type ListItem = {}
type Detail = {}
```

## 7. 组件拆分规范

需要拆分的信号：

- 单文件超过 300-500 行。
- 同时包含搜索、表格、弹窗、详情、权限、请求。
- 一段逻辑被复制到多个页面。
- 组件 props 过多且含义混乱。
- 模板或 JSX 已经难以快速定位结构。

推荐拆分：

```text
UserPage
├─ UserSearch
├─ UserTable
├─ UserFormDialog
├─ UserDetailDrawer
└─ useUserPage
```

原则：

- 通用组件关注复用能力。
- 业务组件关注业务表达。
- 页面组件关注流程编排。
- 组件内部不要直接知道过多全局业务。

## 8. Props 和事件规范

- props 只传组件需要的数据。
- 不把整个大对象随意传入深层组件。
- 事件名表达用户动作或业务结果。
- 子组件不直接修改父组件状态。
- 双向绑定要谨慎使用。
- 弹窗组件要明确 open、close、submit 三类动作。

示例：

```ts
type Props = {
  visible: boolean
  record?: UserDetailVO
}

type Emits = {
  close: []
  success: [data: UserDetailVO]
}
```

## 9. 表单技术规范

- 表单字段必须有初始值。
- 必填、长度、格式、范围必须有前端校验。
- 条件必填必须写成显式规则。
- 提交中按钮必须 loading 和 disabled。
- 提交失败保留用户输入。
- 提交成功后按业务决定重置、关闭或跳转。
- 长表单、高风险表单考虑草稿。
- 金额用数字输入并控制精度。
- 日期使用日期组件并限制非法范围。

表单提交流程：

```text
初始化表单
→ 用户输入
→ 前端校验
→ 提交 loading
→ 调用接口
→ 成功反馈
→ 刷新或跳转
→ 清理临时状态
```

## 10. 列表和表格规范

- 查询条件要有默认值。
- 分页参数统一。
- 搜索要能重置。
- 请求中显示 loading。
- 无数据显示 empty。
- 请求失败显示 error 或提示。
- 状态字段显示中文文案或可理解文案。
- 金额、日期、手机号等必须格式化。
- 操作按钮根据状态和权限显示。
- 操作列较多时保持一致顺序。

列表请求流程：

```text
读取查询条件
→ 发起请求
→ 设置 loading
→ 更新列表和分页
→ 处理空状态
→ 处理错误状态
```

## 11. 状态管理规范

只把真正共享的状态放入全局状态。

适合全局状态：

- 当前用户。
- 登录状态。
- 权限。
- 全局字典。
- 主题和布局。
- 多页面共享的缓存数据。

不适合全局状态：

- 单个表单临时输入。
- 单个弹窗开关。
- 单个页面 loading。
- 可通过接口重新获取的普通列表。

## 12. 路由规范

- 路由表要有统一配置。
- 页面标题、权限、缓存策略可放在路由 meta。
- 不存在路径必须进入 404。
- 无权限访问必须进入 403 或回退。
- 登录过期必须跳转登录页。
- 动态路由加载失败要有兜底页面。
- 路由参数必须校验。

不要假设 URL 参数永远合法。

## 13. 权限规范

- 前端权限只负责体验和入口控制。
- 真正权限必须由后端校验。
- 菜单权限、按钮权限、数据权限要区分。
- 没权限的入口默认隐藏或禁用。
- 高风险按钮不能只靠前端隐藏。
- 权限加载失败时默认收紧权限。

常见权限点：

- 页面是否可见。
- 按钮是否可点。
- 字段是否可见。
- 数据是否可查看。
- 操作是否可提交。

## 14. 异常处理规范

- 请求异常在请求层统一转换。
- 页面异常在页面层给用户恢复路径。
- 组件异常不能拖垮整个应用。
- 全局异常要记录但不能替代局部处理。
- 错误提示要让用户知道下一步。
- 生产环境不暴露堆栈细节。

用户可理解的提示：

```text
保存失败，请检查网络后重试。
登录已过期，请重新登录。
你没有权限执行此操作。
数据加载失败，请刷新页面。
```

## 15. 样式规范

- 优先使用统一设计系统或组件库。
- 全局样式要克制。
- 页面样式避免污染其他页面。
- 颜色、间距、字号尽量使用变量。
- 不随意写大量魔法数。
- 响应式布局要提前考虑。
- 文本不能溢出按钮、表格、卡片。
- 表格、表单、弹窗要保持统一密度。

不要为了局部效果破坏整体一致性。

## 16. 工具函数规范

- 工具函数必须是单一职责。
- 不依赖页面状态。
- 不偷偷读写全局变量。
- 输入和输出要明确。
- 边界值要处理。
- 多处重复逻辑优先提取。

适合工具函数：

- 日期格式化。
- 金额格式化。
- 字符串脱敏。
- 枚举文案转换。
- 文件大小格式化。
- 查询参数清理。

## 17. 常量和枚举规范

- 状态值统一放在 constants。
- 展示文案和颜色映射统一维护。
- 不在多个页面重复写同一套状态。
- 接口枚举值、前端展示值、筛选项要一致。

示例：

```ts
export const USER_STATUS = {
  ENABLED: 'ENABLED',
  DISABLED: 'DISABLED',
} as const

export const USER_STATUS_MAP = {
  ENABLED: { label: '启用', type: 'success' },
  DISABLED: { label: '禁用', type: 'info' },
}
```

## 18. 安全规范

- 禁止把 token、密钥、密码写进代码。
- 不使用不可信内容渲染 HTML。
- 必须使用富文本时要做安全过滤。
- URL 参数不能直接拼接到 DOM。
- 下载和跳转链接要校验来源。
- 敏感信息不要打印到控制台。
- 本地存储不要保存高敏感数据。
- 权限判断不能只靠前端。

重点检查：

```text
v-html / dangerouslySetInnerHTML
localStorage
console.log
外链跳转
文件预览
富文本
```

## 19. 性能规范

- 首屏资源不要无限膨胀。
- 大组件按需加载。
- 大列表使用分页或虚拟滚动。
- 搜索输入要防抖。
- 频繁事件要节流。
- 图片要压缩和懒加载。
- 图表和地图按需初始化。
- 不在渲染中做重计算。
- 不重复请求同一份稳定数据。

优化前先确认瓶颈，不盲目优化。

## 20. 缓存规范

- 缓存必须有失效策略。
- 用户相关缓存退出登录时必须清理。
- 字典缓存要能刷新。
- 表单草稿提交成功后必须删除。
- 缓存数据结构变化要考虑兼容。
- 不把权限结果永久缓存。

缓存不是为了掩盖接口问题。

## 21. 资源和依赖规范

- 引入依赖前确认是否已有替代。
- 不为一个小功能引入大型库。
- 依赖要关注维护状态和体积。
- 静态资源放在统一目录。
- 图片命名表达用途。
- 第三方 SDK 要封装隔离。
- 第三方失败不能拖垮主流程。

## 22. 环境配置规范

- 开发、测试、生产环境配置分离。
- 不把生产配置写死在代码中。
- 环境变量命名统一。
- 构建产物不能依赖本机路径。
- Mock 数据不能混入生产环境。
- 日志级别按环境区分。

常见环境：

```text
development
test
staging
production
```

## 23. 测试规范

至少检查：

- 页面能打开。
- 列表能加载。
- 表单能提交。
- 校验能拦截非法输入。
- 权限能限制入口。
- 接口失败有提示。
- 刷新页面状态正常。
- 重复点击不会重复提交。
- 删除、支付、审批等危险操作有确认。

重要项目应补充：

- 单元测试。
- 组件测试。
- 端到端测试。
- 回归测试清单。

## 24. 代码审查规范

审查时优先看风险，不只看格式。

重点检查：

- 数据是否可能错。
- 接口是否统一封装。
- 类型是否明确。
- 表单是否完整校验。
- 权限是否默认收紧。
- 错误是否可恢复。
- 是否有重复提交风险。
- 是否有敏感信息泄露。
- 组件是否过大。
- 是否改了无关代码。

## 25. AI 生成代码审查规则

AI 生成代码必须额外检查：

- 是否编造不存在的接口。
- 是否编造不存在的组件库 API。
- 是否遗漏导入。
- 是否使用项目中不存在的工具函数。
- 是否破坏现有目录风格。
- 是否忽略权限和错误状态。
- 是否把示例代码当正式代码。
- 是否使用不符合项目版本的语法。
- 是否产生重复文件或重复逻辑。

AI 输出后不要直接信任，必须运行、审查、测试。

## 26. 提交前检查清单

- 代码能启动。
- 页面能打开。
- 控制台无明显错误。
- 类型检查通过。
- 格式化通过。
- 没有无意义日志。
- 没有硬编码敏感信息。
- 没有未使用变量。
- 没有重复请求和重复提交。
- 异常状态可见。
- 空状态可见。
- 权限状态可见。
- 主要流程手动验证通过。

## 27. 最终标准

合格的前端代码应满足：

```text
目录清晰。
类型明确。
请求统一。
组件可维护。
状态可解释。
表单有校验。
错误可恢复。
权限默认收紧。
样式不污染。
性能不过度浪费。
安全不留明显漏洞。
AI 生成内容经过人工审查。
```

这份文档的价值不是限制写法，而是让不同技术栈、不同开发者、不同 AI 工具生成的前端代码，都能保持一致的工程底线。
