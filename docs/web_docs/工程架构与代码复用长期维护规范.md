# 工程架构与代码复用长期维护规范

> 适用范围：任何前端项目（Vue、React、Angular、Nuxt、Next.js、H5、后台、大屏、组件库、跨端应用）。
> 文档定位：长期维护类经验文档 —— 不涉及具体技术栈实现细节，只沉淀"如何组织代码 / 如何避免重复 / 如何降低长期维护成本"的判断标准。
> 配套文档：AI 协作前置对齐见《AI协作前端开发全流程与提示词规范》，异常与降级见《前端页面兜底机制与稳定性经验文档》，编码细节见《AI开发前必读开发技术细节规范》。
> 控制原则：条目化，宁可少写不要泛化，可以持续追加。

## 0. 使用方式

按下面的时机翻这份文档:

1. **新项目立项** → 读第 1、2、3 节,搭出目录骨架与依赖策略。
2. **接手旧项目** → 读第 4、5 节评估现状,再决定重构范围。
3. **开发新页面 / 新模块前** → 读第 6、7、8 节,先想清"这块要不要抽公共"。
4. **代码审查** → 用第 10 节的清单逐条对照。
5. **发现重复代码 / 硬编码 / 巨型组件** → 按第 9 节的判断标准决定是抽还是留。

**核心原则**:代码复用不是抽得越多越好,而是要抽在"变化会同步"的地方。抽错位置的复用比重复代码更难维护。

## 1. 分层原则:什么该放在哪一层

前端项目至少要有五层清晰的边界,任何一处越界都会在半年后变成"改一处炸三处"的技术债。

| 层 | 只做什么 | 绝对不做什么 |
|---|---|---|
| **视图层**（`views/` / `pages/`） | 页面组装、路由入口、页面级状态 | 直接调 axios、写业务规则、格式化数据 |
| **组件层**（`components/`） | 无业务的通用 UI、有业务的领域组件 | 直接调 API、直接读全局 store |
| **状态层**（`store/`） | 跨组件共享的状态、持久化 | 存放页面级临时数据、直接调 API 且不封装 |
| **接口层**（`api/`） | 请求封装、路径常量、参数序列化 | 业务判断、UI 提示、错误弹窗 |
| **工具层**（`utils/`） | 无状态纯函数、格式化、校验、常量 | 依赖 Vue/React 全局、依赖 store |

**判断话术**:
- "改一个字段名会不会影响多个文件?" → 影响 3+ 个,就该抽到接口层或工具层。
- "这个函数依赖当前登录用户吗?" → 依赖,放视图或 store;不依赖,放 utils。
- "换个页面能不能直接用?" → 能,放 components;不能,放 views。

## 2. 目录结构:不追求 DDD,追求"能猜到路径"

好目录的第一标准不是好听,而是:**一个新人拿到需求描述,能猜到文件在哪**。

推荐骨架(不追求技术栈):

```
src/
├── api/                    # 接口封装,按后端模块切分
│   ├── auth.js
│   ├── cases.js
│   └── ...
├── assets/                 # 图片/字体/静态资源
├── components/             # 通用组件
│   ├── common/             #   跨业务纯 UI(按钮、表格、上传)
│   ├── business/           #   跨页面复用的业务组件(如客户选择器)
│   └── ErrorBoundary/      #   兜底组件
├── directive/              # 自定义指令(权限、防抖、脱敏)
├── hooks/ 或 composables/  # 可复用逻辑
├── layout/                 # 布局(导航、侧边栏、面包屑)
├── router/                 # 路由与守卫
├── store/                  # 状态管理
├── styles/                 # 全局样式与变量
├── utils/                  # 无状态工具
│   ├── request.js          #   请求封装
│   ├── validators.js       #   校验规则
│   ├── dict.js             #   字典映射
│   ├── date.js             #   日期格式化
│   └── ...
└── views/                  # 页面,按业务域组织(不按角色)
    ├── cases/
    │   ├── list/
    │   ├── detail/
    │   └── components/     #   本模块专属子组件
    └── ...
```

**避免的坏结构**:
- ❌ 按角色分文件夹(`admin/`, `client/`, `lawyer/`) → 角色权限变了要跨目录搬文件
- ❌ 按技术分类(`services/`, `models/`, `helpers/`) → 找一个业务要跳 5 个目录
- ❌ 所有组件都平铺在 `components/` 下 → 500 个组件后查找靠 Cmd+P

## 3. 依赖策略:引一个包三年不能删

前端项目的技术债有一大半是依赖引进来的。判断"要不要装这个包":

**该装的三个条件**:
1. 功能复杂到自己实现 > 200 行,且社区有明确的最佳实践。
2. 包的维护活跃(近 6 个月有更新),issue 有人回应。
3. 未来 2 年内不会因为它绑死某个技术栈。

**不该装的信号**:
- 只在一处用 → 抄核心 30 行代码进 `utils/` 就够了。
- 功能重叠 → 已经有 `dayjs` 就别装 `date-fns`。
- 版本号还在 0.x → 大概率有 breaking change。
- 只是"看起来更方便" → 真实收益不足以偿付长期成本。

**必须锁的版本**:
- 主框架(Vue/React)、构建工具(Vite/Webpack)、UI 库 → `package.json` 用 `^` 但 `package-lock.json` 必须提交。
- 涉及数值/日期/字符串处理的库(dayjs、decimal.js) → 尽量固定小版本,升级前必须回归。

## 4. 何时抽复用:三次法则 + 变化耦合

**判断"要不要抽公共"的两条硬标准**:

### 4.1 三次法则(Rule of Three)
- 第一次写 → 直接写在业务代码里。
- 第二次写 → 复制粘贴,加个 TODO 注释。
- 第三次写 → 抽成公共函数/组件。

**为什么不第一次就抽?** 因为你还没看到它的三个不同用法,过早抽象会形成"看起来通用但每处调用都要传一堆 hack 参数"的畸形函数。

### 4.2 变化耦合(Change Coupling)
两块代码是否该合并,看它们**是不是总是一起改**:
- ✅ 改字段名要同时改 5 处 → 抽到接口层常量或 VO 定义。
- ✅ 加校验规则要同时改 3 处表单 → 抽到 `validators.js`。
- ❌ 两个组件长得像但业务规则不同 → 保留重复,别为了 UI 一致抽公共。

**判断话术**:
> "如果需求 A 变了,需求 B 会不会跟着变?"
> - 会 → 合并
> - 不会 → 分开,即使代码长得再像也别抽

## 5. 何时不抽:三种"看起来该抽实际上不该"的情况

### 5.1 UI 相似但业务不同
表格 A 和表格 B 都是"三列 + 分页 + 搜索",看起来该抽一个 `<DataTable>`。
但表格 A 是案件列表(有状态标签、金额格式化),表格 B 是审计日志(有 IP 脱敏、时间倒序)。

**结果**:抽出来的 `<DataTable>` 里塞满了 `if (type === 'case')` 分支,最终每加一个新表格都要改这个组件。**不如两个表格各写各的**,共用 `Pagination` / `SearchForm` 这种真通用的部分。

### 5.2 现在很像但未来会分叉
两个页面现在长得一模一样,但一个属于 A 业务线,一个属于 B 业务线。
抽出来后,B 业务线加了个字段,A 业务线不需要,于是加 prop → A 业务线加了个逻辑,B 业务线不需要,再加 prop → 最后组件有 15 个 prop,每处调用都要看半天。

**结果**:业务线独立时,重复优于抽象。

### 5.3 只是碰巧写法一样
两个循环长得一样,但一个是"过滤后累加金额",一个是"过滤后统计数量"。
抽成 `filterAndReduce(list, filterFn, reduceFn)` 后,读代码的人要跳到工具文件才能看懂 —— 反而增加了理解成本。

**结果**:5 行以内的重复,不抽比抽好。

## 6. 组件设计:三种角色分清楚

| 角色 | 特征 | 例子 |
|---|---|---|
| **展示组件** | 无状态、只接收 props、只 emit 事件 | `<Tag>`, `<Avatar>`, `<Pagination>` |
| **容器组件** | 拉数据、管状态、组合展示组件 | `<CaseList>`, `<CustomerDetail>` |
| **业务组件** | 有业务规则、跨页面复用 | `<ClientSelect>`(带客户类型联动), `<AmountInput>`(带金额校验) |

**判断话术**:
- 组件里出现 `axios.get` / `useQuery` → 容器组件,不能被别的容器组件当子组件用。
- 组件依赖某个业务枚举(如 `CLIENT_TYPE.ENTERPRISE`)→ 业务组件,放 `components/business/`。
- 组件只有 UI 逻辑,零业务耦合 → 展示组件,可以放组件库。

**必须避免的反模式**:
- 展示组件里塞 `import { userStore }` —— 立刻失去复用性。
- 容器组件互相嵌套 —— 数据流会成蛛网。
- 一个组件 800 行 —— 100% 是三种角色混在一起。

## 7. 状态管理:能不放 store 就不放

前端项目 60% 的复杂度来源于"到处存状态"。判断标准:

| 状态类型 | 存哪里 |
|---|---|
| 页面内临时数据(表单值、加载状态) | 组件内 `ref` / `useState` |
| 一个父子链共享 | props / 事件 / provide+inject |
| 跨路由但只用一次(如详情页→编辑页) | URL query / 路由 state |
| 跨路由长期使用(登录用户、菜单、字典) | store |
| 服务端数据 | 请求缓存(SWR / React Query / 自己封装 request.js) |

**红线**:
- 不要在 store 里存"表单当前正在编辑的值" —— 用户切换路由后你要么全清、要么忘清,都是坑。
- 不要用 store 做组件通信 —— 用 event bus / pinia 的 subscribe 比乱塞状态干净。
- 不要把所有 API 响应都缓存到 store —— 用请求层缓存,失效策略明确。

## 8. 常量与字典:硬编码的三种去处

项目里最常见的坏味道:`if (row.status === 'IN_PROGRESS')` 出现 30 次。

**三种去处**:

### 8.1 状态常量文件(单文件多枚举)
```javascript
// constants/case.js
export const CASE_STATUS = {
  DRAFT: 'DRAFT',
  IN_PROGRESS: 'IN_PROGRESS',
  CLOSED: 'CLOSED',
  WITHDRAWN: 'WITHDRAWN',
}

export const CASE_STATUS_LABEL = {
  [CASE_STATUS.DRAFT]: '草稿',
  [CASE_STATUS.IN_PROGRESS]: '进行中',
  [CASE_STATUS.CLOSED]: '已结案',
  [CASE_STATUS.WITHDRAWN]: '已退案',
}

export const CASE_STATUS_TAG_TYPE = {
  [CASE_STATUS.DRAFT]: 'info',
  [CASE_STATUS.IN_PROGRESS]: 'primary',
  [CASE_STATUS.CLOSED]: 'success',
  [CASE_STATUS.WITHDRAWN]: 'warning',
}
```

**判断话术**:
- 前端硬编码枚举值(`'IN_PROGRESS'`)超过 3 处 → 抽常量。
- 状态对应的中文标签、颜色、图标 → 用 `Map` 或对象放同一文件。

### 8.2 后端字典接口
如果字典会由业务运营人员维护(如"案由类型"、"费用类型"),后端提供接口,前端 `store` 首次加载缓存。

### 8.3 环境变量
只放"部署环境不同就要改"的值(API 域名、埋点 key、feature flag)。不要把业务枚举放这里,业务逻辑不该跟环境挂钩。

## 9. 判断何时重构:三个信号

不是每一处坏代码都值得改。判断"这次要不要顺手重构"看三点:

### 9.1 频繁改动信号(Change Frequency)
用 `git log --oneline <file> | head -20` 看这个文件近 3 个月被改了多少次。
- 改动 > 10 次 → 强烈候选,重构后收益大。
- 改动 < 3 次 → 稳定代码,不要动它。

### 9.2 缺陷聚集信号(Bug Hotspot)
用 `git log --oneline --grep='fix\|bug\|修复' <file>` 看这个文件出过多少 bug。
- 出过 3+ bug → 结构有问题,必须重构。
- 一次没出过 → 保持原样。

### 9.3 认知成本信号(Cognitive Load)
让一个不熟悉这块代码的同事(或自己一周前的自己)读一遍,记录卡壳点:
- 需要来回翻超过 3 个文件才能理解主流程 → 重构。
- 一遍能读懂 → 别动。

**判断话术**:
> "这段代码看着很脏,但是它稳定、没 bug、没人改。丑但活着,先不动。"

## 10. 交付前自检清单

每次交付(不管功能大小),按下面这张表过一遍:

### 10.1 命名与结构
- [ ] 组件名 / 变量名 / 函数名与实际做的事情一致(没有 `handleClick2`)。
- [ ] 一个文件不超过 500 行,一个函数不超过 50 行(有充分理由可放宽)。
- [ ] 目录层级不超过 4 层(`src/views/xxx/components/yyy/` 是极限)。

### 10.2 复用与硬编码
- [ ] 页面内重复超过 3 次的常量 / 枚举 → 已提取到 `constants/`。
- [ ] 跨页面重复的校验规则 → 已放 `validators.js`。
- [ ] 跨页面重复的格式化(金额、日期、脱敏)→ 已放 `utils/`。
- [ ] 没有把接口调用写死在组件里(全部走 `api/` 层)。

### 10.3 依赖与副作用
- [ ] 新装的依赖在 PR 描述里说明了理由和替代方案。
- [ ] `package-lock.json` / `pnpm-lock.yaml` 一起提交。
- [ ] 定时器 / 监听器 / 订阅 → 都在卸载时清理。
- [ ] 全局变量 / `window.xxx` → 有必要且加了命名空间前缀(如 `__APP_XXX__`)。

### 10.4 状态与数据流
- [ ] 状态存放位置符合第 7 节的判断。
- [ ] 表单提交后清空了本地状态。
- [ ] 页面路由切换后清理了未完成的请求(AbortController)。

### 10.5 兜底与错误处理
- [ ] 每个页面外层有 ErrorBoundary。
- [ ] 每个请求有 loading / error / empty 三种态。
- [ ] 用户可能触发失败的按钮(删除、支付)有二次确认。

### 10.6 可维护性
- [ ] 新写的通用函数有 JSDoc(至少一行说明 + 参数说明)。
- [ ] 新加的 hook / composable 在 README 或 docs 有一个使用示例。
- [ ] TODO 注释附了负责人和目标时间(`// TODO(ocelot, 2026-08): 待后端字典接口就绪后替换`)。

## 11. 长期维护的隐形成本清单

以下六项每一项都在项目 6 个月后爆炸:

| 隐形成本 | 早期预防 |
|---|---|
| 依赖过时导致构建工具无法升级 | 每季度 `npm outdated` 扫一遍,重大版本升级排进日程 |
| 硬编码枚举值散落全项目 | 项目起步就建 `constants/`,每加一个字段先看这里有没有 |
| API 路径散落全项目 | 强制走 `api/` 层,禁止组件内直接 `axios` |
| 没有类型定义导致重构不敢改 | 从项目起步就用 TS 或至少 JSDoc |
| 无人维护的"临时页面" | 每个页面在路由配置里标注 `owner` 和 `since` |
| 大量废弃代码不敢删 | 用 `git` 保留历史,发现废弃直接删;半年后想找靠 `git log -S` |

## 12. 判断话术合集(可直接给 AI)

给 AI 或团队新人的通用判断话术,复制过去即可当规约用:

- "**这个字段/常量硬编码超过 3 处了吗?** 超过 → 抽 `constants/`。"
- "**这个组件依赖业务枚举吗?** 依赖 → 放 `components/business/`,不放 `common/`。"
- "**改一处字段名会影响几个文件?** ≥ 3 → 说明抽象没做好。"
- "**这段代码近 3 个月改了几次?** ≥ 10 → 重构候选。"
- "**表单校验规则和后端一致吗?** 不一致 → 抄后端 DTO 注解,别自己重写。"
- "**这个 store 里的数据切换路由后还需要吗?** 不需要 → 别放 store。"
- "**这个组件里有 `axios` 或 `import store` 吗?** 有 → 不是展示组件,不该放 `common/`。"
- "**这次改动删了代码吗?** 一个功能上线只加不删,长期就是死代码坟场。"

## 13. 常见反模式速查

| 反模式 | 症状 | 解决 |
|---|---|---|
| **上帝组件** | 一个组件 1500 行,承担列表 / 表单 / 弹窗 / 详情 | 按角色拆(见第 6 节) |
| **祖传逻辑** | 一段代码没人敢删,注释写"很重要,请勿修改" | 用 `git blame` 找作者,问清楚再删 / 加测试 |
| **配置地狱** | 一个功能靠 10+ 个 flag / 环境变量拼出来 | 先合并 flag,再重构 |
| **假通用组件** | 组件里塞满 `v-if="type === 'xxx'"` | 拆成多个具体组件 |
| **过度抽象** | 工具函数嵌套 3 层泛型 / 高阶函数 | 拍平,直接写重复 |
| **状态穿透** | 三层组件之间靠 props 一路传值 | 用 provide/inject 或 store |
| **接口拼路径** | 组件里 `axios.get('/api/' + module + '/' + id)` | 走 `api/` 层封装 |
| **假异步** | `.then` 嵌 `.then` 嵌 `.then` | 改 `async/await` |
