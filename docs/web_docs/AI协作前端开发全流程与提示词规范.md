# AI 协作前端开发全流程与提示词规范

> 适用范围：任何前端项目（Vue、React、Angular、Svelte、小程序、H5、大屏、Electron 等），无论是否使用 AI 辅助编码。
> 文档定位：长期沉淀的 AI 协作方法论。既是"给人看的开发流程手册"，也是"给 AI 用的元提示词（Meta Prompt）"。
> 使用目标：让 AI 参与开发时不会跑偏、不会返工、不会破坏工程一致性，最终交付质量与人工独立完成持平或更高。
> 配套文档：
> - 具体编码细节 →《AI开发前必读开发技术细节规范》
> - 判断标准与交付底线 →《资深前端编码前必读开发规范》
> - 异常与降级 →《前端页面兜底机制与稳定性经验文档》
> - 工程结构与代码复用 →《前端工程架构与代码复用经验文档》
> - 契约与数据完整性 →《前后端契约一致性与数据完整性规范》

---

## 0. 为什么需要这份文档

AI 协作最容易出现的四类"跑偏"：

1. **规模跑偏**：一句"帮我加个功能"，AI 拉出十几个新文件、几百行改动，覆盖面远超需求。
2. **风格跑偏**：AI 不看现有代码就动手，引入新库、新写法、新目录结构，破坏工程一致性。
3. **契约跑偏**：AI 凭想象定义接口字段，前后端一测就崩。
4. **兜底跑偏**：AI 写"理想路径"的代码，异常、空态、加载态、权限被跳过。

这份文档的作用是**在 AI 动手前，先约束思路和输入**。不解决模型能力问题，只解决协作流程问题。

## 1. AI 协作四阶段模型

任何一次 AI 协作，都应该走完这四步。跳过任意一步，返工概率显著增加。

```
① 明确意图 → ② 收集上下文 → ③ 输出方案 → ④ 落地实施
   (用户)      (AI 主动)      (AI 输出)      (人审核 + AI 执行)
```

### 阶段①：明确意图（用户负责）

AI 无法猜测"你想要什么"。用户在提问时，至少需要说清三件事：

| 要说的事 | 好的例子 | 差的例子 |
| --- | --- | --- |
| 目标 | "客户列表页要加批量删除功能" | "客户页优化一下" |
| 边界 | "只改列表页，不动详情页" | "顺手把能优化的都优化了" |
| 约束 | "沿用现有的 el-table 二次封装，别引入新组件库" | (无) |

**AI 该做的**：如果用户没说清楚，主动追问 1-3 个关键问题再动手。不要凭猜测硬做。

### 阶段②：收集上下文（AI 负责）

在动任何代码前，AI 必须先做的事（按重要性排序）：

1. **读一遍要改的文件**：确认当前状态，避免"改一个已经不存在的东西"或"重复实现已有功能"。
2. **看一眼相邻同类文件**：比如要写新的列表页，先看两个已有列表页的写法，抄结构、抄命名、抄工具函数。
3. **确认依赖清单**：不要引入项目还没安装的库；不要重造项目 utils 里已经写过的函数。
4. **验证接口是否存在**：字段名、请求方法、参数结构，读一遍 `api/` 目录下的封装。
5. **确认样式规范**：设计变量、间距系统、颜色令牌，别硬编码。

**触发规则**：当用户只说了"做什么"没说"怎么做"，AI 默认走"抄现有模式"的路径，而不是走"最佳实践"的路径。工程一致性 > 个人品味。

### 阶段③：输出方案（AI 负责，用户审核）

对**非平凡任务**（超过 3 个文件 / 涉及公共模块 / 影响多个页面 / 数据结构变更），AI 必须先输出方案再动手。方案至少包含：

```
1. 要改哪些文件（路径 + 大概行数）
2. 要新增哪些文件（路径 + 用途）
3. 涉及的接口/数据变更（前后端联动点）
4. 已知的兼容性风险（会不会影响其他页面）
5. 需要用户确认的技术选择（如果有多方案）
```

**方案原则**：**先讲清楚，再动手做**。如果方案里有"我倾向 X 但也可以 Y"，让用户选。

### 阶段④：落地实施（AI 执行，用户可打断）

实施时的自我约束：

- 一次只做一件事，做完就停下来汇报。别一口气改二十个文件。
- 遇到超出预期的分支决策（"这个字段是加还是不加"），停下来问，别默认。
- 遇到"看起来是 bug 但和当前任务无关"的代码，标记出来但不主动改。
- 完成后，主动列出改动清单让用户复查。

## 2. 提示词模板：给 AI 用的开场白

### 模板 A：新功能开发

```text
【任务】<一句话说清要做什么>
【范围】只涉及 <页面/模块>，不改动 <排除项>
【已有参考】请先阅读以下现有实现，沿用相同风格：
  - <类似功能的文件路径>
  - <公共组件/工具函数路径>
【约束】
  - 沿用现有 UI 组件库，不新增依赖
  - 表单校验用 utils/validators 里的通用规则
  - 接口调用统一走 api/ 目录，不在组件内直接用 axios
【交付】
  - 先输出改动清单和方案，等我确认后再动手
  - 完成后列出所有改动文件和验证方式
```

### 模板 B：Bug 修复

```text
【现象】<用户看到什么>
【重现步骤】<1、2、3 步骤>
【预期】<应该是什么样>
【实际】<现在是什么样>
【已排查】<已经确认不是什么问题>
【要求】
  - 先定位根因再改代码，不要贴创可贴
  - 修复方案要能解释"为什么这样改能解决"
  - 检查是否有同类问题（比如相同的模式在其他文件里也存在）
```

### 模板 C：重构 / 优化

```text
【目标】<性能/可维护性/一致性 中的哪个>
【触发原因】<为什么现在要做这件事>
【范围边界】只重构 <明确范围>，其他保持不动
【不变量】以下行为在重构后必须保持一致：
  - <行为 1>
  - <行为 2>
【验证方式】<改完怎么验证没破坏原有功能>
```

### 模板 D：代码审查请求

```text
【审查对象】<文件路径 或 PR 链接>
【关注点】<下面几项挑一到三项，别全选>
  - 正确性：有没有边界情况没处理
  - 性能：有没有 N+1、循环里发请求、重复计算
  - 可维护性：命名、拆分、注释
  - 一致性：和项目其他部分风格是否一致
  - 契约：接口调用参数/字段是否和后端对齐
【输出】按"严重 / 一般 / 建议"三档给结论，每条都要有具体行号和修改建议
```

## 3. AI 的自我检查清单

AI 在输出代码前，对着这份清单默过一遍：

### 3.1 是不是先抄了再写

- [ ] 我看过至少一个类似功能的现有实现吗？
- [ ] 我用的命名、拆分方式和项目其他地方一致吗？
- [ ] 我引入的每一个依赖，项目里都已经装了吗？

### 3.2 是不是理清了数据流

- [ ] 数据从哪来（API / props / store / localStorage）？
- [ ] 数据传给谁（子组件 / 上报 / 持久化）？
- [ ] 关键字段的类型和后端一致吗？
- [ ] 空值、undefined、null 的分支都覆盖了吗？

### 3.3 是不是留了兜底

- [ ] 加载中显示什么？
- [ ] 请求失败显示什么？
- [ ] 数据为空显示什么？
- [ ] 权限不足显示什么？
- [ ] 用户点"取消"会不会走进 Promise reject 分支？

### 3.4 是不是没造轮子

- [ ] 我要写的这个工具函数，utils/ 里是不是已经有了？
- [ ] 我要写的这个校验规则，validators/ 里是不是已经有了？
- [ ] 我要写的这段格式化逻辑，是不是可以复用现有 filter/computed？

### 3.5 是不是能解释

- [ ] 每一行有业务含义的代码，我能用一句话说清楚它为什么在这？
- [ ] 我加的每一个新库、新目录、新抽象，能说清楚它值不值这个成本吗？

## 4. 常见 AI 反模式与对应规避

### 反模式 1：过度封装

**表现**：为了一个只用一次的按钮，抽出一个 `<UniversalActionButton>` 组件；为了两条格式化逻辑，写一个 `<FormatterFactory>`。

**规避**：三次原则（Rule of Three）。同一段逻辑出现第三次时才抽。前两次都用复制粘贴。

### 反模式 2：过度防御

**表现**：明明是内部方法，参数由自己控制，也写 `if (!params) return`；明明后端已经返回 `data: []`，还写 `data?.length > 0 ? data : []`。

**规避**：**只在系统边界做校验**（用户输入、外部 API 响应、跨模块调用）。内部方法信任调用方。

### 反模式 3：假注释

**表现**：`// 获取用户列表` 写在 `getUserList()` 上方；`// 循环遍历` 写在 `for` 上方。

**规避**：注释只解释**为什么**，不解释**做什么**。命名做不到的事才写注释。参考：
```js
// ❌ 坏注释：说了代码本身就能看出来的事
// 遍历订单
orders.forEach(...)

// ✅ 好注释：说了代码看不出来的事
// 后端要求同一订单不能重复计算，用 Set 去重
const uniqueOrderIds = new Set(orders.map(o => o.id))
```

### 反模式 4：Silent Failure

**表现**：`try { await api.xxx() } catch { }`——异常被吞掉，用户看不到反馈，日志里也没有痕迹。

**规避**：至少要做一件事：给用户提示 / 上报日志 / 触发降级。三选一，不能全跳过。

### 反模式 5：字段猜测

**表现**：后端接口没看，凭"应该叫这个吧"猜字段名（`userName` vs `username` vs `user_name`）。

**规避**：动手前先读接口文档或调一次真实接口。字段名不确定时，问一句比返工三次划算。

### 反模式 6：TODO 堆积

**表现**：`// TODO: 后面再优化` `// TODO: 补充异常处理` `// FIXME: 临时方案`。

**规避**：能立刻做就立刻做；做不了的写进 issue 而不是代码；确实要放代码里，必须带**日期+人+触发条件**：
```js
// TODO(2026-07-12, Ocelot): 等后端提供批量删除接口后替换，见 issue #123
```

## 5. 交付前的三层验证

AI 声称"完成了"不算完成。要过完三层验证才算：

### 第一层：静态验证（AI 自己做）

- [ ] 语法能过（本地 build 或 typecheck 无错）
- [ ] 引入的模块都存在（没有幽灵 import）
- [ ] 命名和现有代码一致
- [ ] 改动清单和方案一致（没有偷偷改别的）

### 第二层：功能验证（AI 主动跑一遍）

- [ ] 手动或用 dev server 打开受影响的页面
- [ ] 走一遍完整流程（正常路径）
- [ ] 至少测一个异常路径（比如接口失败、字段为空、用户取消）
- [ ] 权限相关的改动，切不同角色分别验证

### 第三层：回归验证（用户做，AI 提供检查清单）

AI 交付时必须列出：

```
【已改动文件】
- src/xxx.vue（新增批量删除弹窗）
- src/api/xxx.js（新增 batchDelete 方法）
- src/router/index.js（无改动，只是引用了新组件）

【建议验证的场景】
1. 全选后批量删除 → 应该弹二次确认
2. 部分选择后批量删除 → 只删选中的
3. 未选择直接点批量删除 → 按钮应该禁用
4. 删除接口失败 → 应该提示错误且列表不刷新

【可能影响的其他功能】
- 单条删除逻辑（因为共用了确认弹窗）
- 列表分页（删除后可能翻页）
```

## 6. AI 协作的边界与红线

有些事 AI 不能替人决定，看到就必须停下来问。

### 6.1 数据破坏性操作

- 删除数据库表 / 字段 / 记录
- 清空 localStorage / sessionStorage / IndexedDB
- 覆盖用户已有的文件
- 强制推送、rebase、reset --hard

**规则**：AI 遇到这类操作，即使用户明确要求，也要复述一遍确认："我要执行 `git reset --hard origin/main`，这会丢失本地所有未提交改动，确认吗？"

### 6.2 密钥、密码、令牌

- 不写入代码
- 不上传日志
- 不打印到控制台
- 不发到 AI 服务

**规则**：AI 看到 `.env` `secrets.yml` 之类文件，只做"引用它"的代码，不复述内容。

### 6.3 大规模架构决策

- 换 UI 组件库
- 换状态管理方案
- 换路由方案
- 换构建工具

**规则**：AI 遇到这类需求，先不动，先说"这属于架构级决策，建议先讨论：换的原因、替代方案、迁移成本、影响范围"。

### 6.4 已上线代码的紧急修改

- 生产环境热修复
- 影响支付、认证、数据落库的核心链路

**规则**：AI 只输出补丁方案，不直接改，等用户逐行审查。

## 7. 用 AI 做代码审查的正确姿势

反向使用：让 AI 审查人写的代码。

### 7.1 输入应该给什么

- **完整的 diff**（不是单个文件片段），让 AI 看到上下文
- **变更目的**（这个 PR 想解决什么问题）
- **约束条件**（不希望改的部分、必须遵守的规范）

### 7.2 期望 AI 输出什么

按严重程度分档，每条包含：

```
【严重】文件路径:行号
问题：具体是什么问题（一句话）
根因：为什么会导致问题（一句话）
建议：应该怎么改（代码片段或伪代码）
```

**不要**期望 AI 输出模糊评价，比如"可以更好"、"建议优化"。

### 7.3 AI 审查的盲区（要人补的）

- **业务正确性**：AI 不知道你的业务规则，只能看代码逻辑一致性
- **性能极端场景**：AI 看不出"这段代码在 100 万条数据下会崩"
- **安全性深层问题**：AI 能发现常见 XSS/注入，看不出组合漏洞
- **可维护性主观判断**：命名好不好、拆分合不合理，最终看团队共识

## 8. 项目级 AI 协作配置

如果项目长期用 AI 辅助开发，建议在仓库根目录建立以下"AI 上下文文件"，让每次协作都有稳定输入：

### 8.1 `CLAUDE.md` / `AI.md` / `.cursorrules`

**内容**：项目背景、技术栈、命名规范、目录约定、禁止事项、当前阶段（新功能期 / 稳定期 / 修复期）。

**作用**：每次 AI 协作前自动加载，不用重复解释。

**关键字段**：

```
# 项目名 & 一句话说明
# 技术栈（版本号必须写）
# 目录结构（哪些目录做什么）
# 编码规范链接（指向本 docs/ 目录下的文档）
# 当前阶段的重点与禁令（比如"修复期，暂停新功能"）
# 沟通规则（回答风格、术语翻译习惯）
```

### 8.2 `docs/` 目录

放**长期沉淀**的规范文档（就像本文档），不是**一次性**的修复报告。

区分：

| 类型 | 位置 | 特征 | 生命周期 |
| --- | --- | --- | --- |
| 长期规范 | `docs/*.md` | 通用、可复用 | 数年 |
| 项目决策 | `docs/adr/*.md` | 特定决策 + 上下文 | 项目生命周期 |
| 一次性报告 | 临时目录 或 PR 描述 | 具体修复过程 | 修复完成后归档删除 |

### 8.3 `.github/PULL_REQUEST_TEMPLATE.md`

让 AI 生成 PR 描述时有固定模板，避免每次格式不一致。

## 9. 度量：AI 协作是不是变好了

以下指标越低说明协作越顺畅：

- **返工率**：一次交付被要求"重做"的比例
- **偏离率**：AI 改动范围超出预期的比例
- **规范违反次数**：每次协作违反 CLAUDE.md 约定的次数
- **上下文丢失次数**：AI 忘了之前对话中确认的事情的次数

以下指标越高说明协作越顺畅：

- **一次通过率**：交付后用户直接接受、无需修改的比例
- **主动澄清率**：AI 在动手前主动问澄清问题的比例
- **兜底覆盖率**：AI 主动加了加载态/空态/错误态的比例

## 10. 快速自检：这次协作合格吗

每次协作结束，用这五个问题验收：

1. **改动是否止于任务范围？**（没有顺手改别的）
2. **是否复用了现有工具/组件/模式？**（没有造新轮子）
3. **是否留下了加载/空/错误/权限四态兜底？**（没有只写理想路径）
4. **字段名、路径、依赖是否都真实存在？**（没有幻觉产出）
5. **是否能一句话说清"改了什么、为什么改、怎么验证"？**（没有黑盒交付）

五个都是"是" → 合格。
一个是"否" → 打回补做。
三个以上是"否" → 说明协作流程本身出了问题，回到本文档第 1 节重新走一遍。

## 附录 A：常用 AI 提示词片段

粘到对话开头即可复用。

**A1. 抄现有代码的写法**
```text
在写新代码前，请先读 <参考文件路径>，抄它的结构、命名、错误处理方式。
除非我明确要求，不要引入新库、新目录、新模式。
```

**A2. 只输出方案不动手**
```text
不要动代码。先输出你的方案：改哪些文件、加哪些文件、涉及哪些接口、有哪些风险。
我确认后你再执行。
```

**A3. 分步交付**
```text
把这个任务拆成 <N> 步，每步做完停下来等我确认再做下一步。
第一步先做 <最小可验证的部分>。
```

**A4. 反向审查**
