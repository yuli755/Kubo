# 数据契约与前后端对齐规范

> 适用范围：任何前后端分离项目（Vue / React / Angular + 任意后端框架）。
> 文档定位：告诉前端团队"怎么和后端接口打交道才能不被坑"。围绕**契约**、**校验一致性**、**枚举同步**、**并发场景**、**数据完整性**5 个维度沉淀经验。
> 使用目标：让接口对接从"猜、试、返工"变成"看契约、按规则、一次过"。
> 配套文档：编码细节见《AI 开发前必读开发技术细节规范》；页面兜底见《前端页面兜底机制与稳定性经验文档》；架构与复用见《工程架构与代码复用长期维护规范》。

## 0. 使用方式

1. 接手一个新接口 → 先看第 1、2 节确认契约来源和字段含义。
2. 写表单前 → 看第 3、4 节保证前后端校验规则一致。
3. 有状态流转（订单、案件、审批）→ 看第 5 节。
4. 涉及金额、时间、ID → 看第 6、7、8 节。
5. 遇到并发场景（付款、库存、点赞）→ 看第 9 节。
6. 上线前 → 用第 12 节清单自检。

契约不是可选项，是接口质量的基线。

---

## 1. 契约的三种形态与优先级

**契约 = 前后端对一个接口的共同承诺。**在项目中通常有 3 种形态，可信度依次是：

| 形态 | 例子 | 可信度 | 使用场景 |
|---|---|---|---|
| **代码契约** | 后端 DTO + Controller 注解、数据库 DDL | 🟢 最高 | 判断"到底传什么、返什么"的最终依据 |
| **文档契约** | Swagger/Knife4j、OpenAPI YAML | 🟡 中等 | 快速查阅，但可能滞后于代码 |
| **口头契约** | 微信、聊天、会议纪要 | 🔴 最低 | 只能作为临时沟通，必须落到前两种 |

**规则：**

- 冲突时以代码契约为准，其他任何来源都不算数。
- 前端不要凭"上次聊过"或"文档里写的"下判断，遇到不一致时看后端 DTO/Controller 源码。
- 修改契约前**必须**双方确认，任何一方单方面改字段/类型/枚举都算破坏契约。

## 2. 接口五问：对接前必答

拿到一个新接口，写代码前先回答这 5 个问题。答不上就问后端，别猜。

1. **必填字段**：哪些字段是 `NotNull` / `NotBlank`？空字符串算不算传？
2. **字段类型**：ID 是 `Long` 还是 `String`？金额是 `BigDecimal` 还是浮点？日期是 `LocalDate` 还是 `LocalDateTime`？
3. **枚举取值**：状态字段的所有可能值？哪些是终态？
4. **错误约定**：业务失败是抛异常还是返回 `code != 200`？错误码有哪些？
5. **权限边界**：这个接口能被哪些角色调？返回结果会因角色不同而不同吗？

**建议做法**：把答案写在 API 封装文件顶部的注释里。半年后回来看时你会感谢自己。

```javascript
// api/case.js
/**
 * 创建案件
 * 必填: clientId, lawyerId, caseTitle, caseType, acceptDate
 * clientId/lawyerId 存的是 sys_user.id（不是 client_info.id，别踩坑）
 * caseType 取值: CIVIL/CRIMINAL/ADMINISTRATIVE/COMPANY
 * 权限: LAWYER 可调，CLIENT 不可调
 * 幂等: 否，重复提交会产生多条记录，前端需防抖 + 提交中禁用按钮
 */
export function createCase(data) { ... }
```

## 3. 校验规则一致性

**目标**：前端校验通过的数据，后端 100% 也能通过。前后端校验规则**不一致**是最常见的返工原因。

### 3.1 一致性要求

| 校验维度 | 前端表现 | 后端表现 |
|---|---|---|
| 必填 | `required: true` / `rules: [{ required: true }]` | `@NotNull` / `@NotBlank` |
| 最大长度 | `maxlength="200"` / `rules: [{ max: 200 }]` | `@Size(max=200)` / DB `VARCHAR(200)` |
| 数字范围 | `<InputNumber :min="0" :max="100">` | `@Min(0)` `@Max(100)` |
| 正则 | `rules: [{ pattern: /^1[3-9]\d{9}$/ }]` | `@Pattern(regexp="^1[3-9]\\d{9}$")` |
| 枚举 | 下拉选项 | DB `CHECK (status IN (...))` |
| 唯一性 | 失焦时调用 unique-check 接口 | Service 层预校验 + DB `UNIQUE KEY` 兜底 |

### 3.2 典型不一致陷阱

**陷阱 1**：后端 `@NotBlank`，前端只做了 `required`（Element Plus 的 `required` 只判空字符串，不判纯空格）

- 前端能通过 `"   "`，后端返 400
- 解决：自定义 trim 校验，或用 `pattern: /\S/`

**陷阱 2**：后端 `@Size(max=100)`，前端 `maxlength="200"`

- 用户复制 150 字进来，前端不拦，后端报 400
- 解决：前后端最大长度取同一个常量

**陷阱 3**：前端下拉多了一个"其他"选项，后端 CHECK 约束里没这个值

- 用户选了"其他"，提交时后端拒绝
- 解决：枚举值统一由后端提供接口返回，或前后端共用一份枚举文件（见第 4 节）

### 3.3 校验规则的单一来源

**推荐做法**：把校验规则抽到 `src/utils/validators.js` 等复用模块，多个表单引用同一份规则。

```javascript
// utils/validators.js
export const commonRules = {
  phone: [
    { required: true, message: '请输入手机号', trigger: 'blur' },
    { pattern: /^1[3-9]\d{9}$/, message: '手机号格式不正确', trigger: 'blur' }
  ],
  clientName: [
    { required: true, message: '请输入客户名称', trigger: 'blur' },
    { min: 2, max: 50, message: '长度在 2-50 字符', trigger: 'blur' }
  ]
}
```

**升级路径**：如果后端有 OpenAPI Schema，可以用工具（如 `openapi-typescript`、`swagger-codegen`）自动生成前端 TS 类型和校验规则，实现真正的"一份契约、双端消费"。

### 3.4 条件必填的正确写法

业务里经常有"A 为某值时，B 必填"的规则（如：企业客户必填公司名，个人客户不填）。

**错误写法**：静态 rules 里写死 `required: true`，个人客户也被要求填公司名。

**正确写法**：用 `computed` 生成动态 rules，或用条件必填工具函数。

```javascript
const formRules = computed(() => ({
  companyName: [
    {
      required: form.value.clientType === 'ENTERPRISE',
      message: '请输入企业名称',
      trigger: 'blur'
    }
  ]
}))
```

**同时**：切换客户类型时，把不需要的字段清空，避免脏数据带到后端。

## 4. 枚举同步策略

枚举值同步不做好，前后端会出现"你说 IN_PROGRESS 我说 ONGOING"的情况。

### 4.1 三种同步策略

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **前端硬编码** | 简单 | 后端加了值前端不知道 | 项目小、枚举稳定 |
| **接口拉取** | 后端加值前端自动同步 | 每次页面加载多一个请求 | 枚举频繁变动 |
| **代码生成** | 强一致，编译期检查 | 需要 CI 集成 | 大团队、多端消费 |

### 4.2 前端硬编码时的规范

**必做**：把所有枚举集中到 `src/constants/enums/`，禁止在业务代码里硬写字符串。

```javascript
// constants/enums/case.js
export const CASE_STATUS = {
  DRAFT: 'DRAFT',
  PENDING_FILING: 'PENDING_FILING',
  FILED: 'FILED',
  IN_PROGRESS: 'IN_PROGRESS',
  CLOSED: 'CLOSED',
  WITHDRAWN: 'WITHDRAWN'
}

export const CASE_STATUS_LABELS = {
  [CASE_STATUS.DRAFT]: '草稿',
  [CASE_STATUS.PENDING_FILING]: '待立案',
  [CASE_STATUS.FILED]: '已立案',
  [CASE_STATUS.IN_PROGRESS]: '进行中',
  [CASE_STATUS.CLOSED]: '已结案',
  [CASE_STATUS.WITHDRAWN]: '已退案'
}

export const CASE_STATUS_TAG_TYPE = {
  [CASE_STATUS.DRAFT]: 'info',
  [CASE_STATUS.PENDING_FILING]: 'warning',
  [CASE_STATUS.FILED]: 'primary',
  [CASE_STATUS.IN_PROGRESS]: 'primary',
  [CASE_STATUS.CLOSED]: 'success',
  [CASE_STATUS.WITHDRAWN]: 'info'
}
```

**禁止**：

```javascript
// ❌ 到处硬编码，改一次要全局搜索
if (row.status === 'IN_PROGRESS') { ... }
if (row.status === 'ONGOING') { ... }  // 拼错也没人知道

// ✅ 用常量
import { CASE_STATUS } from '@/constants/enums/case'
if (row.status === CASE_STATUS.IN_PROGRESS) { ... }
```

### 4.3 未知枚举值的容错

后端可能新增了枚举值但前端还没更新。列表页遇到未知值时：

```javascript
function getStatusLabel(status) {
  return CASE_STATUS_LABELS[status] || status  // 至少显示原始值，不要空白
}
```

**不要**：`CASE_STATUS_LABELS[status]`（返 undefined 显示为 "undefined"）
**也不要**：`CASE_STATUS_LABELS[status] || '未知'`（隐藏了问题，排查困难）

## 5. 状态流转的前后端协作

带状态的实体（订单、案件、审批）最容易翻车。

### 5.1 状态机由后端定义

**规则**：合法的状态流转路径**只能**由后端定义，前端只负责展示。

- 后端提供合法流转规则（可以是文档、接口返回、常量文件）
- 前端根据当前状态动态显示可用的操作按钮
- 前端**永远**不做"我觉得这个流转合理"的假设

### 5.2 前端按钮的动态显示

```vue
<template>
  <el-button v-if="canFile(row.status)" @click="handleFile(row)">立案</el-button>
  <el-button v-if="canProgress(row.status)" @click="handleProgress(row)">添加进度</el-button>
  <el-button v-if="canClose(row.status)" @click="handleClose(row)">结案</el-button>
  <el-button v-if="canWithdraw(row.status)" @click="handleWithdraw(row)">退案</el-button>
</template>

<script setup>
import { CASE_STATUS } from '@/constants/enums/case'

const canFile = (status) => status === CASE_STATUS.PENDING_FILING
const canProgress = (status) => status === CASE_STATUS.FILED || status === CASE_STATUS.IN_PROGRESS
const canClose = (status) => status === CASE_STATUS.IN_PROGRESS
const canWithdraw = (status) => [CASE_STATUS.PENDING_FILING, CASE_STATUS.FILED, CASE_STATUS.IN_PROGRESS].includes(status)
</script>
```

### 5.3 状态变更必带原因

**规则**：结案、退案、驳回、退款、注销等"负向"或"终止性"的状态变更，必须让用户填写原因。

- 前端：弹窗强制输入 `reason`，字数限制 10-500 字
- 后端：DTO 加 `@NotBlank @Size(min=10, max=500)`
- 数据库：字段 `NOT NULL`

**为什么**：出了纠纷时"为什么退案"是最重要的证据；没有原因的历史记录等于没有历史。

### 5.4 状态并发的乐观锁

多用户同时操作同一条记录时（如两个律师同时结案），需要防止后来者覆盖先来者。

**做法**：后端在关键实体上加 `version` 字段（乐观锁），前端每次更新时带上从查询接口拿到的 `version`。

```javascript
// 查询
const detail = await getCaseDetail(id)  // 返 { id, version, status, ... }

// 更新
await updateCase(id, { ...form, version: detail.version })
// 如果 version 已被其他人改过，后端返 409 Conflict，前端提示"数据已被修改，请刷新"
```

## 6. 金额字段的规范

金额是最容易出精度问题的字段，前后端要严格统一。

### 6.1 类型选择

| 层次 | 类型 | 说明 |
|---|---|---|
| 数据库 | `DECIMAL(15, 2)` | 精确到分，不用 FLOAT/DOUBLE |
| 后端 | `BigDecimal` | 不用 Double/Float |
| API 传输 | JSON number 或 string | 大金额（超过 JS 安全整数）用 string |
| 前端存储 | string / number（视精度） | 内部不做浮点运算 |
| 前端展示 | 千分位 + 2 位小数 | `¥10,000.00` |

### 6.2 前端不做浮点运算

**禁止**：

```javascript
// ❌ 浮点精度陷阱
total.value = 0.1 + 0.2  // 0.30000000000000004
```

**推荐**：需要在前端算金额时用 `decimal.js` 或 `big.js`，或直接把计算放到后端。

### 6.3 展示格式统一

抽一个格式化工具函数，全站复用：

```javascript
// utils/formatter.js
export function formatAmount(value, defaultText = '¥0.00') {
  if (value === null || value === undefined || value === '') return defaultText
  const num = Number(value)
  if (isNaN(num)) return defaultText
  return `¥${num.toLocaleString('zh-CN', { minimumFractionDigits: 2, maximumFractionDigits: 2 })}`
}
```

**禁止**：每个页面自己 `.toFixed(2)`、自己拼千分位。

### 6.4 输入组件

金额输入用 `InputNumber` + `precision="2"` + `min="0"`，别用普通文本框。

- 强制两位小数
- 禁止负数（如业务允许再放开）
- 上限用业务合理值（如单笔付款不超过 1 亿）

### 6.5 金额边界校验

前后端都要做：

- 付款金额 ≤ 未收金额
- 退款金额 ≤ 已收金额
- 金额 > 0（0 元账单一般是脏数据）

**前端**：提交前提示；**后端**：Service 层强校验 + DB CHECK 约束兜底。

## 7. 时间字段的规范

时间字段的坑仅次于金额。

### 7.1 类型选择

| 场景 | 后端类型 | 前端组件 |
|---|---|---|
| 只有日期（生日、有效期） | `LocalDate` | `<DatePicker type="date">` |
| 日期 + 时间（订单创建、审批时间） | `LocalDateTime` | `<DatePicker type="datetime">` |
| 精确时刻（防重放的 timestamp） | `Instant` / `long` | 通常不给用户选 |

### 7.2 时区处理

**规则**：

- 数据库统一存 UTC，或统一存服务器所在时区（保持一致即可）
- API 传输用 ISO 8601 格式（如 `2026-07-12T10:30:00Z` 或 `2026-07-12T18:30:00+08:00`）
- 前端展示按用户本地时区

**禁止**：后端返 `2026-07-12 10:30:00`（无时区信息），前端不知道是 UTC 还是本地时间。

### 7.3 日期字符串比较陷阱

**陷阱**：

```javascript
// 后端返 filingDate: "2026-07-12"
// 后端返 createTime: "2026-07-12 10:23:45"
if (filingDate < createTime) { ... }
// 字符串比较："2026-07-12" < "2026-07-12 10:23:45" → true（错误）
```

**正确做法**：转成 Date 对象或时间戳比较。

```javascript
if (new Date(filingDate).getTime() < new Date(createTime).getTime()) { ... }
```

**更好**：如果两个字段都有时分秒，DatePicker 用 `type="datetime"` 而不是 `type="date"`。

### 7.4 展示格式统一

用 dayjs 抽格式化函数：

```javascript
import dayjs from 'dayjs'

export function formatDate(value) {
  return value ? dayjs(value).format('YYYY-MM-DD') : '-'
}

export function formatDateTime(value) {
  return value ? dayjs(value).format('YYYY-MM-DD HH:mm:ss') : '-'
}

export function formatRelativeTime(value) {
  if (!value) return '-'
  const diff = dayjs().diff(dayjs(value), 'minute')
  if (diff < 1) return '刚刚'
  if (diff < 60) return `${diff} 分钟前`
  // ... 更多分支
}
```

## 8. ID 字段的规范

ID 看起来简单，实际是最容易踩坑的字段之一。

### 8.1 类型规范

- 后端用 `Long`（不用 `Integer`，业务量大了会溢出）
- API 传输：如果 ID 值可能超过 JS 的 `Number.MAX_SAFE_INTEGER`（2^53 - 1），必须用 string 传输
- 前端如果只是透传（存下来、发回后端），当 string 处理更保险

### 8.2 ID 语义清晰化

项目里最常见的坑：一个字段名叫 `client_id`，实际存的不是 `client_info.id` 而是 `sys_user.id`。这种约定务必显式写在：

- 数据库字段注释：`COMMENT '委托客户ID(sys_user.id)'`
- 后端 Entity 注释
- 前端 API 封装注释
- 团队 wiki 或 CLAUDE.md（AI 协作项目）

**规则**：任何"约定俗成但代码里看不出来"的 ID 映射，都必须写文档，否则半年后没人记得。

### 8.3 ID 存在性校验

前端选择器（如"选择客户"）返回 ID，后端 Service 拿到后**必须**先校验 ID 存在：

```java
ClientInfo client = clientMapper.selectById(dto.getClientId());
if (client == null) throw new BusinessException("客户不存在或已删除");
```

**前端不要假设**：前端选择器里显示的数据可能已被其他人删除，提交时 ID 已失效。

## 9. 并发场景的前后端协作

高并发场景（付款、抢券、库存）光靠前端防抖不够，前后端要配合。

### 9.1 防重复提交（前端侧）

- 提交按钮加 `loading` 状态，请求期间禁用
- 关键操作生成 `requestId`（UUID），带在请求头或参数里，后端幂等去重

```javascript
const submitting = ref(false)

async function handleSubmit() {
  if (submitting.value) return
  submitting.value = true
  try {
    await submitPayment({ ...form.value, requestId: uuidv4() })
  } finally {
    submitting.value = false
  }
}
```

### 9.2 分布式锁（后端侧）

关键业务（付款、库存扣减、状态变更）后端必须加分布式锁（Redis / Redisson），前端**不需要**关心锁的细节，只需要知道：

- 后端会保证并发安全
- 加锁失败后端会返回明确错误（如"操作过于频繁"），前端展示即可

### 9.3 乐观锁 vs 悲观锁

| 场景 | 推荐 |
|---|---|
| 冲突频率低（如修改个人资料） | 乐观锁（version 字段） |
| 冲突频率高、必须成功（如库存扣减） | 悲观锁（分布式锁）或原子操作（`UPDATE ... WHERE stock > 0`） |
| 金额计算类（付款） | 分布式锁 + 主库读取（避免主从延迟读到旧数据） |

### 9.4 主从数据库延迟

如果后端用主从架构，"写后立即读"可能读到从库的旧数据。

- 后端：关键读操作强制走主库（如 `@MasterOnly` 注解）
- 前端：付款、状态变更等操作后，刷新数据用主动查询而不是本地拼接（本地拼接可能与真实数据不一致）

## 10. 数据完整性的前端责任

后端有 DB 约束、Service 校验，前端一样要有前置校验。**双保险不是浪费，是数据质量的基石。**

### 10.1 前端为什么也要校验

- 用户体验：不用等一次网络往返才知道错
- 减轻后端压力：无效请求前端就拦下
- 引导用户：把规则用交互形式告诉用户（如禁用不合法选项）

### 10.2 前端校验的三层

| 层次 | 例子 |
|---|---|
| **输入时** | 输入框限制字符集、`InputNumber` 限制范围 |
| **提交前** | `form.validate()` 检查所有 rules |
| **业务规则** | 结案日期不能早于立案日期、退款不能超过已收金额 |

第 3 层最容易漏，需要写在自定义 validator 里。

### 10.3 关联数据的一致性

用户在表单里选择的关联数据（客户、律师、案件），前端要保证：

- 从下拉/搜索接口选择，不允许手动输入 ID
- 选择后把关联的显示名（如客户名称）也一起保存到表单，提交时可以让后端做二次校验
- 如果被选实体已被删除，展示时用"已删除"占位（`{{ item.name || '已删除' }}`）

### 10.4 删除操作的关联检查

删除客户前，前端应该：

1. 主动查询该客户的关联案件、账单数量（可以在删除按钮 hover 时显示）
2. 二次确认弹窗里明确列出关联数据数量
3. 后端必须再次校验（前端可能过时）

## 11. 错误码与前端处理

### 11.1 统一响应结构

后端所有接口用统一响应结构：

```json
{
  "code": 200,
  "message": "success",
  "data": { ... }
}
```

失败时：

```json
{
  "code": 40001,
  "message": "客户不存在",
  "data": null
}
```

### 11.2 前端拦截器统一处理

在 axios 响应拦截器里根据 code 分派：

```javascript
service.interceptors.response.use(response => {
  const { code, message, data } = response.data

  if (code === 200) return data

  // 认证失败
  if (code === 401) {
    router.push('/login')
    return Promise.reject(new Error('登录已过期'))
  }

  // 权限不足
  if (code === 403) {
    ElMessage.error('无权访问该资源')
    return Promise.reject(new Error(message))
  }

  // 业务错误
  ElMessage.error(message || '操作失败')
  return Promise.reject(new Error(message))
})
```

### 11.3 业务错误不 throw、只 return

某些"不算错误的失败"（如查询空结果、状态不允许操作），后端可以返 `code: 200 + data: null` 或专用的业务码，让前端可以感知但不弹错误提示。

避免"用户点了一下按钮，页面弹了一堆红字"——不友好。

## 12. 上线前对接自检清单

前端提测/上线前用这份清单自检，一条一条过。

**契约类**：

- [ ] API 封装注释里写清了必填字段、字段类型、枚举值、权限边界
- [ ] 所有枚举值来自 `constants/enums/`，业务代码里没有硬编码字符串
- [ ] 状态流转规则和后端一致，按钮根据状态动态显示

**校验类**：

- [ ] 前端所有必填字段和后端 `@NotNull` 对齐
- [ ] 前端 `maxlength` 和后端 `@Size(max)` 对齐
- [ ] 前端正则和后端 `@Pattern` 对齐
- [ ] 条件必填用 `computed` 动态生成，切换时清空不用的字段

**数据类**：

- [ ] 金额用 `InputNumber precision=2 min=0`，展示统一 `formatAmount`
- [ ] 日期字段选对了 `date` / `datetime` 类型
- [ ] 日期比较用 Date 对象或时间戳，不做字符串比较
- [ ] ID 字段类型正确（Long 类值当 string 处理）

**并发类**：

- [ ] 提交按钮有 loading 和 disabled 状态
- [ ] 关键操作有 `requestId` 或幂等设计
- [ ] 敏感操作有二次确认（删除、退款、结案）

**兜底类**：

- [ ] 未知枚举值有默认展示（不显示 undefined）
- [ ] 关联数据为空有占位（如"已删除"）
- [ ] 网络错误、超时错误有友好提示，不是直接抛堆栈

---

## 13. 结语

契约是承诺，规则是自律，一致性是底线。

前后端对齐做好了，接口 bug 会少 70%，代码质量会稳一大截。

任何**没写进代码**的口头约定，都会在半年后成为返工的理由。把契约、枚举、规则写进代码，写进注释，写进这份文档，让下一个接手的人（可能是你自己）少踩坑。
