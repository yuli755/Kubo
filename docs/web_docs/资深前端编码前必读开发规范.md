# 资深前端编码前必读开发规范

> 适用范围：任何前端技术项目，包括后台管理系统、官网、移动端 H5、跨端应用、小程序、可视化大屏、低代码平台、组件库和前端基础设施项目。
> 适用技术栈：Vue、React、Angular、Svelte、Solid、Next.js、Nuxt、Vite、Webpack、小程序、Electron、React Native 等。
> 使用方式：每次新建项目、接手项目、开发新模块、重构旧页面前，先阅读本文件。
> 文档定位：提供通用前端开发判断标准、问题识别方法和交付底线；具体编码细节另见《AI开发前必读开发技术细节规范》。
> 配套文档：涉及异常处理、页面降级、接口失败、弱网、缓存、监控、回滚等问题时，同时阅读《前端页面兜底机制与稳定性经验文档》。

## 0. 阅读和执行方式

建议按这个顺序使用本文：

1. 新项目启动前，先读第 1-3 节，确定工程结构和基本原则。
2. 开发页面前，先读第 2、4-12 节，确认接口、权限、表单、表格、组件和异常处理。
3. 提交代码前，执行第 19 节检查清单。
4. 做代码审查时，优先参考第 18 节，不要只看格式。
5. 发现新坑或新规范时，按“问题、规则、示例、检查项”的格式追加到本文。
6. 使用 AI 开发时，先让 AI 阅读本文，再要求它按本文的检查项给出实现方案。

本文不是一次性规范，而是项目经验沉淀。规则必须能指导编码、审查和问题定位，不能只写口号。

## 0.2 适用边界

本文优先适用于 Web 前端和以 Web 技术为核心的项目。

可直接适用：

- Vue、React、Angular、Svelte、Solid
- Next.js、Nuxt、Remix、Astro
- Vite、Webpack、Rspack 等构建体系
- 后台管理系统、SaaS、H5、官网、可视化大屏、组件库

可复用思想，但需按平台调整：

- 小程序：路由、分包、缓存、登录态要按平台 API 实现。
- React Native：页面、存储、网络、权限、崩溃处理要按原生能力调整。
- Electron：需要额外关注主进程、渲染进程、进程崩溃和本地文件权限。
- Flutter：工程原则可参考，但组件、状态、构建和运行时机制不同。

不要把本文当成某个框架的语法手册。本文约束的是工程质量、业务准确性和交付底线。

## 0.3 项目规模分级执行标准

| 项目类型 | 最低执行标准 |
|----------|--------------|
| 个人 Demo | 目录清晰、能运行、基础错误提示 |
| 小型业务页 | 请求封装、表单校验、loading/empty/error |
| 普通业务系统 | 权限、字典、统一格式化、危险操作确认 |
| 中后台系统 | 动态路由、状态管理、组件复用、审查清单 |
| 高可用项目 | 监控、灰度、回滚、幂等、稳定性演练 |
| 组件库/基础设施 | 类型、安全边界、文档、测试、版本兼容 |

原则：项目越小，规范越要轻；业务风险越高，兜底越要强。

## 0.4 技术栈落地差异

| 技术栈 | 落地重点 |
|--------|----------|
| Vue | 组合式逻辑、Pinia、Vue Router、`onErrorCaptured` |
| React | Hooks、状态库、React Router、Error Boundary |
| Next.js | SSR/SSG、Route Segment、Hydration、服务端错误 |
| Nuxt | 服务端数据、路由中间件、插件注入、Hydration |
| 小程序 | 分包、页面生命周期、平台登录、storage 限制 |
| Electron | 进程隔离、IPC、本地文件、自动更新、崩溃恢复 |
| React Native | 原生权限、网络状态、导航栈、崩溃采集 |

## 0.5 给 AI 或开发者的使用提示

当你把本文用于新项目或 AI 编码时，不要让 AI 直接开始写页面。先要求它完成以下判断：

1. 这个功能解决什么业务问题？
2. 关键数据有哪些，哪些字段不能错？
3. 页面需要哪些状态：loading、empty、error、no permission、success？
4. 哪些操作有风险，需要确认、防重复提交或回滚？
5. 接口失败、权限失败、刷新页面、重复点击时如何处理？
6. 当前项目规模属于哪一档，哪些规范必须执行，哪些可以简化？

推荐提示词：

```text
请先阅读《资深前端编码前必读开发规范》和《前端页面兜底机制与稳定性经验文档》。
在编码前，先说明业务目标、页面状态、接口边界、表单校验、权限规则、异常兜底和提交前检查项。
不要追求框架语法细节，优先保证数据准确、交互完整、错误可恢复、代码可维护。
```

## 1. 核心原则

### 1.1 先理解业务，再写代码

前端不是把接口数据显示出来就结束。编码前必须先确认：

- 这个页面解决什么业务问题。
- 谁会使用这个页面。
- 用户最常做的操作是什么。
- 哪些字段是关键数据。
- 哪些操作不可撤销。
- 哪些异常会造成业务损失。
- 后端接口、权限、状态流转是否已经明确。

如果业务规则没问清楚，不要靠猜测写代码。

### 1.2 数据准确性优先于操作便利

任何前端项目都必须把数据准确性放在第一位。

- 宁可让用户多填一个关键字段，也不要提交脏数据。
- 宁可增加一次确认弹窗，也不要误删、误支付、误发布。
- 宁可在前端提前拦截，也不要让错误数据流到后端。
- 前端校验只是第一道防线，后端必须再次校验。

典型高风险数据：

- 金额
- 日期
- 身份证、手机号、邮箱
- 用户权限
- 订单状态
- 审批状态
- 支付状态
- 发布状态
- 删除状态

### 1.3 页面不能只追求“能跑”

一个合格页面至少要满足：

- 能正确展示数据。
- 能正确提交数据。
- 有 loading 状态。
- 有空数据状态。
- 有错误状态。
- 有权限控制。
- 有表单校验。
- 有危险操作确认。
- 有成功和失败反馈。
- 刷新、返回、重复点击不会出问题。

只实现“正常路径”的页面，不算完成。

### 1.4 统一比局部聪明更重要

同一个项目里，写法必须统一。

不要出现：

- 有的页面直接用 `fetch`，有的页面用封装请求。
- 有的状态显示中文，有的直接显示枚举值。
- 有的表单有校验，有的没有。
- 有的删除有二次确认，有的直接删除。
- 有的金额带千分位，有的不带。
- 有的错误提示给用户看得懂，有的直接暴露技术错误。

统一的代码，比局部“炫技”的代码更容易维护。

## 2. 编码前必须确认的 12 个问题

开发任何页面或功能前，先回答下面问题：

1. 这个功能的主要用户是谁？
2. 用户进入页面后最核心的操作是什么？
3. 页面有哪些状态：加载中、空数据、正常、失败、无权限？
4. 表单字段哪些必填，哪些只在特定条件下必填？
5. 字段长度、格式、数值范围、日期范围是否明确？
6. 是否存在新增、编辑、删除、提交、审批、支付、发布等危险操作？
7. 是否需要二次确认？
8. 是否需要防重复提交？
9. 当前用户是否一定有权限看见或操作这些数据？
10. 后端接口失败时，页面应该如何恢复？
11. 刷新页面、返回页面、切换标签页时状态是否正确？
12. 这个页面会不会变大，是否需要提前拆分组件？

如果这些问题回答不清楚，先补齐需求和接口，不要急着写页面。

## 3. 推荐项目结构

不同技术栈目录名字可以不同，但职责必须清楚。

```text
src/
├── api/ 或 services/        接口请求
├── assets/                  静态资源
├── components/              通用组件
├── constants/               枚举、字典、状态常量
├── hooks/ 或 composables/    复用逻辑
├── layouts/                 页面布局
├── pages/ 或 views/          页面
├── router/                  路由
├── store/                   全局状态
├── styles/                  全局样式
├── types/                   TypeScript 类型
├── utils/                   工具函数
└── tests/                   测试
```

### 3.1 每个目录只做一类事

- `api/services`：只负责请求后端。
- `components`：只放可复用 UI 组件。
- `constants`：只放稳定枚举和字典。
- `hooks/composables`：只放可复用业务逻辑。
- `pages/views`：只负责编排页面。
- `utils`：只放与框架无关的工具函数。
- `store`：只存全局共享状态，不要滥用。

### 3.2 页面目录建议

复杂业务页面推荐：

```text
pages/order/
├── index.vue 或 index.tsx
├── components/
│   ├── OrderSearch.vue
│   ├── OrderTable.vue
│   ├── OrderFormDialog.vue
│   └── OrderDetailDrawer.vue
├── hooks/
│   └── useOrderPage.ts
└── constants.ts
```

不要把搜索、表格、弹窗、详情、权限、接口调用全部堆在一个文件里。

## 4. API 请求规范

### 4.1 页面禁止直接散写请求

不推荐：

```js
fetch('/api/users')
axios.post('/api/order/create', data)
```

推荐：

```js
// services/order.ts
export function createOrder(data) {
  return request.post('/orders', data)
}
```

页面只调用：

```js
await createOrder(formData)
```

### 4.2 请求层统一处理公共逻辑

请求封装应统一处理：

- baseURL
- timeout
- Token 或 Cookie 携带策略
- 请求头
- 统一响应结构
- 401 登录过期
- 403 无权限
- 500 服务异常
- 超时提示
- 文件上传和下载
- 错误信息提取

### 4.3 请求层不要吞错

错误可以提示，但不能静默吞掉。

推荐：

```js
showError(message)
return Promise.reject(error)
```

不推荐：

```js
showError(message)
return null
```

吞错会让页面误以为请求成功，后续状态更难排查。

### 4.4 Loading 要分层

不要所有请求都全屏遮罩。

推荐：

- 页面首次加载：页面级 loading。
- 表格刷新：表格局部 loading。
- 表单提交：按钮 loading。
- 上传下载：操作级 loading。
- 登录、初始化权限：可使用全屏 loading。

## 5. 状态、枚举和字典规范

### 5.1 枚举必须集中管理

不要在页面里到处写状态文案。

推荐：

```ts
export const ORDER_STATUS = {
  PENDING: 'PENDING',
  PAID: 'PAID',
  CANCELLED: 'CANCELLED'
} as const

export const orderStatusMap = {
  PENDING: { label: '待支付', color: 'warning' },
  PAID: { label: '已支付', color: 'success' },
  CANCELLED: { label: '已取消', color: 'default' }
}
```

页面统一使用状态组件或映射函数展示。

### 5.2 不要直接展示后端枚举值

不推荐：

```text
PENDING_APPROVAL
IN_PROGRESS
PAYMENT_FAILED
```

推荐：

```text
待审批
进行中
支付失败
```

### 5.3 前端枚举必须与后端一致

前端字典来源优先级：

1. 后端枚举定义
2. 接口文档
3. 数据库约束
4. 产品需求文档

不要前端自行发明状态。

## 6. 权限规范

### 6.1 权限至少分三层

```text
路由权限：能不能进入页面
按钮权限：能不能看到操作入口
接口权限：后端最终兜底
```

前端权限只能优化体验，不能作为安全边界。

### 6.2 权限判断不要散在模板里

不推荐：

```jsx
{ user.role === 'ADMIN' || row.ownerId === user.id ? <Button>编辑</Button> : null }
```

推荐：

```jsx
{ canEdit(row, user) ? <Button>编辑</Button> : null }
```

权限函数集中管理：

```ts
export function canEditOrder(order, user) {
  if (order.status === 'CLOSED')
    return false
  if (user.role === 'ADMIN')
    return true
  return order.ownerId === user.id
}
```

### 6.3 禁止只隐藏按钮不校验接口

按钮隐藏不是权限控制的终点。

用户仍可能通过：

- 浏览器控制台
- 手写请求
- 修改前端代码
- 重放接口

绕过前端限制。后端必须再次校验。

## 7. 表单规范

### 7.1 表单必须有前端校验

至少校验：

- 必填
- 最大长度
- 最小长度
- 数字范围
- 金额精度
- 日期范围
- 邮箱格式
- 手机号格式
- URL 格式
- 文件大小和类型
- 跨字段规则

跨字段规则示例：

- 结束日期不能早于开始日期。
- 已付金额不能大于应付金额。
- 企业用户必须填写企业名称。
- 开票状态为已开票时，发票号不能为空。

### 7.2 表单提交必须防重复

提交按钮必须有：

- loading
- disabled
- 成功反馈
- 失败反馈
- 提交后状态恢复

### 7.3 表单编辑和详情要区分

不要用一个巨大表单同时承担：

- 新增
- 编辑
- 查看
- 审批
- 复制

如果复用，也要明确模式：

```ts
type FormMode = 'create' | 'edit' | 'view' | 'approve'
```

### 7.4 表单字段要按业务分组

复杂表单不要平铺。

推荐：

```text
基础信息
联系方式
业务信息
附件信息
审批信息
备注
```

## 8. 表格和列表规范

### 8.1 列表页标准结构

```text
页面标题
筛选区
操作工具栏
表格
分页
弹窗/抽屉
```

### 8.2 表格必须处理常见状态

- 加载中
- 空数据
- 加载失败
- 无权限
- 部分字段为空
- 字段过长
- 大量数据分页

### 8.3 操作列必须按状态显示

例如：

- 已完成订单不显示“取消”。
- 已发布内容不显示“删除草稿”。
- 已结算账单不显示“确认收款”。
- 无权限用户不显示编辑按钮。

不要让用户点了按钮后才告诉他不能操作。

### 8.4 金额、日期、空值必须格式化

统一工具函数：

```ts
formatDate()
formatDateTime()
formatMoney()
formatPercent()
formatFileSize()
formatEmpty()
```

不要每个页面各写一套格式化逻辑。

## 9. 组件规范

### 9.1 什么应该抽成组件

适合抽：

- 多页面复用的搜索区域
- 分页器
- 状态标签
- 文件上传
- 表格操作栏
- 详情描述
- 统计卡片
- 时间线
- 评分组件
- 空状态
- 错误状态

不适合过早抽：

- 只用一次的小片段
- 业务规则还不稳定的表单
- 为了“看起来高级”而抽象的配置组件

### 9.2 组件输入输出要明确

组件通过 props 接收数据，通过 emit/callback 暴露事件。

不要让通用组件偷偷读业务 store。

### 9.3 组件不要做太多事

一个组件最好只解决一个明确问题。

如果组件开始同时处理：

- 接口请求
- 权限
- 表单
- 表格
- 弹窗
- 状态流转

说明它应该拆分。

## 10. 状态管理规范

### 10.1 不要滥用全局状态

适合放全局状态：

- 当前用户信息
- 权限
- 主题
- 语言
- 全局配置
- 跨页面共享的缓存

不适合放全局状态：

- 普通表单数据
- 单页临时查询条件
- 弹窗开关
- 某个组件内部 loading

### 10.2 持久化要谨慎

可以持久化：

- Token 或登录态标识
- 主题
- 语言
- 少量用户偏好

谨慎持久化：

- 权限菜单
- 敏感用户信息
- 大量业务数据
- 表单草稿

## 11. 样式和 UI 规范

### 11.1 样式要统一

项目应统一：

- 颜色
- 字体
- 间距
- 圆角
- 阴影
- 表格密度
- 表单宽度
- 按钮顺序
- 状态颜色

不要每个页面自己随手写颜色和间距。

### 11.2 禁止大量内联样式

不推荐：

```html
<div style="display:flex;margin-left:12px;color:#999">
```

推荐：

```html
<div class="user-info">
```

样式集中写在 CSS、SCSS、CSS Modules、Tailwind 组合类或设计系统中。

### 11.3 响应式要提前考虑

即使是后台系统，也要确认：

- 小屏是否能横向滚动。
- 表格操作列是否被挤没。
- 弹窗在小屏是否超出。
- 长文本是否换行或省略。
- 表单项是否能纵向排列。

## 12. 异常处理规范

### 12.1 每个页面都要有异常状态

至少考虑：

- 接口失败
- 网络超时
- 登录过期
- 无权限
- 空数据
- 资源加载失败
- 组件渲染失败

### 12.2 错误提示要能指导用户

差：

```text
Error: 500
```

好：

```text
服务暂时不可用，请稍后重试。
```

更好：

```text
账单保存失败，请检查金额和付款状态后重试。
```

### 12.3 危险操作必须二次确认

必须确认：

- 删除
- 批量删除
- 发布
- 撤回
- 支付
- 退款
- 禁用账号
- 重置密码
- 审批通过
- 审批驳回

## 13. 安全规范

### 13.1 不要随意使用 HTML 注入

避免：

```html
<div v-html="content"></div>
```

```jsx
<div dangerouslySetInnerHTML={{ __html: content }} />
```

除非内容经过可信清洗。

### 13.2 Token 存储要评估风险

常见方案：

- `localStorage`：简单，但 XSS 风险高。
- `sessionStorage`：关闭页面后丢失，但仍可被脚本读取。
- HttpOnly Cookie：前端读不到，安全性更好，但需要后端配合。

公网项目、支付项目、敏感数据项目，不要随便把长期 Token 放在 `localStorage`。

### 13.3 敏感信息要脱敏

列表页和非必要场景应脱敏：

- 手机号
- 邮箱
- 身份证号
- 银行卡号
- 地址
- 公司证件号
- Token
- 密钥

### 13.4 前端不能保存密钥

禁止在前端代码里硬编码：

- API 密钥
- 私钥
- 数据库密码
- 第三方服务 secret
- 管理员默认密码

## 14. 性能规范

### 14.1 首屏性能

关注：

- 路由懒加载
- 组件懒加载
- 图片压缩
- 资源分包
- 缓存策略
- 首屏接口数量
- 骨架屏或 loading

### 14.2 列表性能

大数据列表要考虑：

- 分页
- 虚拟滚动
- 防抖搜索
- 服务端筛选
- 避免循环中请求接口
- 避免无意义深拷贝

### 14.3 输入性能

搜索框、联想输入、远程下拉必须防抖。

```ts
debounce(search, 300)
```

不要用户每输入一个字符就请求一次接口。

## 15. 编码质量规范

### 15.1 必须统一编码

所有文件必须使用 UTF-8。

建议配置 `.editorconfig`：

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
indent_style = space
indent_size = 2
```

### 15.2 必须配置质量工具

推荐至少具备：

- ESLint：检查代码问题。
- Prettier：统一格式。
- TypeScript：减少字段和接口错误。
- Stylelint：检查样式。
- lint-staged：提交前检查改动文件。
- commitlint：统一提交信息。

推荐脚本：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "lint": "eslint src --fix",
    "format": "prettier --write src",
    "typecheck": "tsc --noEmit",
    "test": "vitest"
  }
}
```

### 15.3 优先使用 TypeScript

任何中大型前端项目都建议使用 TypeScript。

至少定义：

- API 请求参数类型
- API 返回类型
- 表单类型
- 表格行类型
- 枚举类型
- 用户类型
- 路由 meta 类型
- 组件 props 类型

## 16. 测试规范

### 16.1 不是什么都要测，但关键路径必须测

必须重点覆盖：

- 登录
- 权限
- 表单校验
- 金额计算
- 状态流转
- 删除和撤销
- 支付和退款
- 数据格式化
- 工具函数

### 16.2 推荐测试层级

```text
单元测试：工具函数、hooks、权限函数
组件测试：表单、表格、弹窗
端到端测试：登录、核心业务流程
```

## 17. Git 和交付规范

### 17.1 提交前检查

提交前必须确认：

- 页面无明显报错。
- 控制台无无意义错误。
- 格式化已执行。
- lint 通过。
- 构建通过。
- 核心流程手动验证通过。
- 没有提交无关文件。
- 没有提交密钥、Token、账号密码。

### 17.2 不要混合提交

一个提交只做一类事。

不要把：

- 修 bug
- 改样式
- 重构
- 格式化
- 新功能

全部混在一次提交里。

## 18. 代码审查重点

审查前端代码时，优先看：

- 是否破坏业务规则。
- 是否缺少权限判断。
- 是否缺少表单校验。
- 是否缺少错误状态。
- 是否有重复提交风险。
- 是否有 XSS 风险。
- 是否有敏感信息泄露。
- 是否有大文件未拆分。
- 是否有重复代码可以提取。
- 是否与项目已有风格一致。

不要只看缩进和命名。

## 19. 编码前检查清单

开始写代码前：

- 我知道这个功能的业务目标。
- 我知道用户是谁。
- 我知道接口字段含义。
- 我知道权限规则。
- 我知道状态流转。
- 我知道必填和校验规则。
- 我知道异常时怎么展示。
- 我知道是否需要二次确认。
- 我知道是否需要拆组件。
- 我知道是否已有可复用代码。

提交代码前：

- API 没有散写。
- 状态没有硬编码。
- 表单有校验。
- 危险操作有确认。
- 提交有 loading。
- 页面有空状态和错误状态。
- 权限判断集中管理。
- 敏感信息已脱敏。
- 没有无意义 console。
- 没有明显性能问题。
- 文件没有过大失控。
- 构建和检查通过。

## 20. 最终标准

一个前端功能完成，不是指“页面能打开”，而是指：

```text
正常路径能用。
异常路径可控。
用户操作有反馈。
数据提交准确。
权限边界清晰。
代码结构可维护。
后续人员能接手。
```

这是所有前端项目都应该坚持的最低标准。
