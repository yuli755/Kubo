## 子阶段 B：数据权限治理落地（P5 核心功能）

### B1：后端 — 接入 PermissionContext 到请求链路

**目标**：在 `RequestInterceptor` 中基于已认证用户填充 `PermissionContext` 并设置到 `PermissionContextHolder`。

**具体工作**：
1. 在 `RequestInterceptor.preHandle()` 中，获取当前用户后：
   - 查询用户的 `roleCodes`（通过 `UserEntity.getRoles()`）
   - 查询用户的 `departmentIds`（通过 `UserEntity.getDepartments()`）
   - 查询用户的 `factoryIds`、`warehouseIds`（若有关联）
   - 判断是否 `bypassDataPermission`（调用 `SystemPermissionService.isRoot()` 或检查 `system:data-permission:bypass` 权限）
2. 构造 `PermissionContext` 并调用 `PermissionContextHolder.open(context)`，在 `afterCompletion` 中关闭

**涉及文件**：
- `RequestInterceptor.java`（修改）
- `UserEntity.java`（可能需要补充部门/工厂/仓库关联）

### B2：后端 — 修复数据权限模块缺陷

**目标**：修复 Agent 审查发现的 4 个问题。

**具体工作**：
1. **修复 Subject Type 枚举不一致**：`DataPermissionSubjectType` 缺少 `FACTORY` 和 `WAREHOUSE`，但 `JpaPermissionRuleProvider.matchesSubject()` 的 switch 引用了它们。需要统一（方案：在 enum 中新增 `FACTORY` 和 `WAREHOUSE` 值）
2. **修复 SYSTEM 匹配逻辑**：当前 `SYSTEM → context.bypassDataPermission()` 语义反了——SYSTEM 策略应匹配所有用户，而非仅 bypass 用户。改为 `return true`
3. **实现 DEPARTMENT/FACTORY/WAREHOUSE 匹配**：补充 `departmentIds`、`factoryIds`、`warehouseIds` 的匹配逻辑
4. **扩展 `RowPermissionPredicate`**：新增 `owner()`、`department()`、`factory()`、`warehouse()` 工厂方法

**涉及文件**：
- `DataPermissionSubjectType.java`
- `JpaPermissionRuleProvider.java`
- `RowPermissionPredicate.java`

### B3：后端 — 实现 JPA Specification 行级权限过滤

**目标**：基于 JPA（非 MyBatis）实现查询时自动注入行级权限条件。

**方案**：使用 Spring Data JPA 的 `Specification` 接口 + `JpaSpecificationExecutor`。

**具体工作**：
1. 创建 `DataPermissionSpecification` 工具类，接收 `PermissionContext` 和 `resourceKey`，生成 `Specification<T>`：
   - 调用 `DataPermissionService.getPolicies()` 获取策略
   - 将策略的 `conditionJson` 解析为 JPA `Predicate`（租户隔离、所有者过滤、部门树过滤等）
   - 若策略为空且 `shouldDenyByDefault()` 为 true，返回 `(root, query, cb) → cb.disjunction()`（空结果）
2. 为试点模块的 Repository 添加 `JpaSpecificationExecutor` 接口
3. 在试点模块的 Service 层注入 `DataPermissionSpecification`，在查询方法中叠加权限条件

**涉及文件（新增）**：
- `DataPermissionSpecification.java`
- 试点模块 Service 修改：`InventoryService.java`、`OrderService.java`

### B4：后端 — 列级脱敏 AOP

### B9：前端 — 构建 TanStack-to-airpower 适配器（消除桥接）

**目标**：创建一个适配器 hook，使 TanStack Query 的数据能直接驱动 ATable，消除当前「TanStack 只做 mutation、airpower 做查询」的双轨状态。

**问题**：当前 list.vue 使用 airpower 的 `useTable()` 做数据查询，TanStack Query 的 `useQuery` 列表 hooks 定义了但从未使用。ATable 组件要求 `useHook` prop 符合 `ITableResult` 接口（包含 `service`、`serviceClass`、`request`、`response`、`list`、`isLoading` 等）。

**方案**：创建 `useTanStackTable()` 适配器：
```typescript
function useTanStackTable<E, S>(options: {
  queryKey: string[]
  queryFn: (params) => Promise<{ list: E[], total: number }>
  entity: E
  service: S
  serviceClass: Constructor<S>
}): ITableResult<E, S>
```

适配器内部：
1. 维护 `request` ref（page/filter/sort 状态）
2. 调用 `useQuery()` 以 `request` 为 query key 依赖
3. 将 `data.value.list`、`data.value.total`、`isFetching` 映射到 `response`、`list`、`isLoading` ref
4. 暴露 `onSearch`、`onPageChanged`、`onSortChanged` 更新 `request` 触发 TanStack 重新查询
5. 保留 `service` 和 `serviceClass` 供 ATable 内部 CRUD 操作

**涉及文件（新增/修改）**：
- `src/hook/useTanStackTable.ts`（新增适配器）
- 试点模块 list.vue（替换 `useTable`/`useBillTable` 为 `useTanStackTable`）

## 风险控制

1. **不引入 MyBatis-Plus**：基于 JPA Specification + `@Filter` 实现行级权限，避免双 ORM 维护成本
2. **不引入 RabbitMQ**：Outbox 表已建但暂不实现异步消息，首期使用同步数据库轮询（或不实现 Outbox 投递）
3. **不改变 UI 框架**：保持 Element Plus + AirPower，不引入 TailwindCSS/shadcn-vue/Framer Motion
4. **每个 commit 原子化**：确保任一 commit 可独立回滚
5. **试点先行**：B3-B4 仅对 WMS/Inventory 和 MES/Order 两个试点模块实施，验证通过后再扩展到其他模块
