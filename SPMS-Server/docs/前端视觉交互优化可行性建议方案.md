# 前端视觉与交互优化可行性建议方案（2026-09-10）

> 触发背景：P3 通用操作审计日志闭环落地后，前端功能性改造告一段落；本次评估**视觉美化、交互动画与体验优化**的可行空间。
> 参考口径：既有的「前端二次改造优化可行性建议方案」已评估过 `law-firm-platform`（结论：技术选型不可借鉴）；
> 本文以**专业设计系统实践**为主线，结合 Element Plus / Vue 生态的成熟做法，给出诚实基线 + 分项清单 + 推荐执行顺序。
> 每一条都标注 **价值 / 工作量 / 风险 / 前置**。

---

## 0. 结论先行（TL;DR）

1. **Kubo 前端的工程化已经很强，缺的不是「重做」，是「最后一公里的统一与品牌化」**：
   树摇（unplugin-vue-components + shim）、PWA（autoUpdate + `/api` runtime 缓存）、路由预载（`useRoutePreload`）、
   TanStack Query 缓存、`index.html` 内联骨架屏、体积预算（入口 450KB / 总量 900KB gzip）都已就位。
   **本次优化重点不在性能，在视觉一致性、动效与反馈。**

2. **当前视觉面是「Element Plus / airpower 默认皮肤」**：主题色 `#409eff` 散落硬编码在
   `index.html`、PWA manifest、各处内联样式里，没有设计 token 层、没有深色模式、没有路由过渡、
   没有统一的微交互与空/错反馈规范。这是最明显、也最「投入产出比高」的改造面。

3. **推荐推进序（低风险先行）**：
   `V1 设计 Token 层` → `V2 深色模式` → `V5 加载态分级` → `V3 路由过渡` → `V7 空/错/成功反馈`
   → `V4 微交互/列表动效` → `V6 看板动效` → `V8 无障碍与动效降级`（V8 贯穿全程，是护栏不是收尾）。

4. **铁律（不可破）**：动效只走 `transform` / `opacity`（合成器友好）；全程尊重
   `prefers-reduced-motion`；**不引入运行时动效库**（ECharts 已占约 2.77MB，再叠动效库会顶破体积预算）。

---

## 1. 现状盘点（诚实基线）

### 1.1 已具备（本次不重复造轮子）

| 能力 | 现状 |
| --- | --- |
| 框架与 UI | Vue 3.5 + Vite 7 + Element Plus 2.12 + Pinia 3 + TanStack Vue Query 5 + `@airpower/web`（AFrame/ATable/APanel） |
| 首屏反馈 | `index.html` 内联骨架屏（logo 脉冲 + 进度条滑动的 `@keyframes`），已相当精致 |
| 加载态 | 全局 `v-loading` 遮罩（App.vue / Console.vue），element-plus 指令已按需注册 |
| 动效（散点） | 登录页、首页、`iot/monitor`、`mes/routing/progress`、`UserCard`、`ThirdLogin` 等零散存在 `transition`/`animation` |
| 性能护栏 | 树摇、PWA 缓存、路由预载、Query 缓存、`check-bundle-size.mjs` 体积预算、`check-source-text` 等门禁 |

### 1.2 缺口（本次改造对象）

1. **无设计 token 层**：主题色/间距/圆角/阴影/字体散落硬编码（`#409eff`、`#66b1ff`、`#909399`、`#e4e7ed`…），
   改一个主色要全局搜索替换，且无法派生 hover/disabled 等状态色。
2. **无深色模式**：无 `html.dark`、无 `--el-color-*` 覆盖、无持久化/跟随系统。
3. **无路由过渡**：`<router-view/>` 切换是硬切，页面进出无过渡。
4. **加载态单级**：只有「整页 loading 遮罩」一种形态，表格/卡片/图表局部刷新时没有骨架屏与分级反馈。
5. **空/错/成功反馈薄弱**：空状态多为「表格空文字」，错误多为裸 toast，缺统一插画/文案/CTA 规范。
6. **微交互缺失**：hover/focus/行高亮/按钮按压反馈不一致，列表增删改无 FLIP 过渡。
7. **看板无数据动效**：ECharts 默认无入场过渡，数字无滚动；安全态势看板/业务概况静态呈现。
8. **无障碍与动效降级**：无 `prefers-reduced-motion` 处理、无统一 `focus-visible` 样式、对比度未审计。

## 2. 分项方案

> 每项「现状 → 方案 → 价值/工作量/风险/前置」。V1/V2 是地基，其余项都依赖它们。

### V1 · 设计 Token 层（CSS 变量 + Element Plus 主题定制）【地基 · 推荐优先】

- **现状**：主题色硬编码，无变量层。
- **方案**：
  - 新建 `src/styles/tokens.scss`，定义 `:root` 下的 `--kubo-color-primary` / `--kubo-radius` / `--kubo-shadow-*` /
    `--kubo-spacing-*` / `--kubo-font-*` 等语义变量。
  - 在 `:root` 里**映射覆盖** Element Plus 官方变量（`--el-color-primary` 及其 `light-3/5/7/8/9`、`dark-2` 派生色、
    `--el-border-radius-base`、`--el-box-shadow-*`），让 EP 组件与自定义组件同源同色。
  - 建立 `主色 + 状态色（success/warning/danger/info）` 的完整色阶（可用 EP 的 `color-mix` 或预计算色阶）。
  - 收口 `index.html` 骨架屏、PWA `theme_color`、`logo.svg` 的硬编码色到 token。
- **价值**：高（改主色 = 改一处，全局生效；是深色/品牌化的前置）。
- **工作量**：低-中。
- **风险**：低（纯 CSS 变量，不碰逻辑）。
- **前置**：无。

### V2 · 深色模式【高感知 · 推荐紧随 V1】

- **现状**：无深色。
- **方案**：
  - 引入 `element-plus/theme-chalk/dark/css-vars.css`（官方暗色变量），配合 V1 的 token 做品牌色暗色映射。
  - 新增主题 store（`useThemeStore`）：`light / dark / system` 三态，持久化到 Pinia persist，`system` 跟随
    `prefers-color-scheme` 并监听变化。
  - `html` 根节点切换 `dark` 类；在 Console 的 header（TenantSwitcher 旁）加一个轻量切换按钮。
  - **审计清单（风险所在）**：图表（ECharts 轴线/文字色）、表格斑马纹、内联硬编码色（如
    `monitor.vue`、`progress.vue` 的固定色）、`logo.svg`、PWA `theme_color`（同步切换或设为中性色）。
- **价值**：高（用户感知最强、差异化最明显）。
- **工作量**：中。
- **风险**：中（漏审计的硬编码色在暗色下对比度崩坏）。
- **前置**：V1。

### V3 · 路由过渡与页面级动效【体验提升】

- **现状**：`Console.vue` 里 `<router-view/>` 硬切。
- **方案**：
  - 用 Vue `<Transition name="fade-slide">` 包裹 `<router-view/>`，`enter/leave` 只做 `opacity + translateY(4~8px)`。
  - 菜单展开/收起、侧栏抽屉沿用 EP 自带过渡（已有 `el-collapse-transition`）。
- **价值**：中-高。
- **工作量**：低。
- **风险**：低（注意 AFrame 内部结构，过渡时长 ≤ 200ms 避免拖沓）。
- **前置**：V1（时长/缓动用 token）。

### V4 · 微交互与列表动效【精细度提升】

- **现状**：hover/focus/行高亮不一致，列表增删改硬刷新。
- **方案**：
  - 统一 `hover`（行背景过渡）、`focus-visible`（描边高亮）、按钮 `active`（轻微缩放/下压）。
  - 列表增删改用 `<TransitionGroup>` + FLIP（`v-move`），**仅对 < 50 行的小列表启用**，大表格关闭行级动画。
  - 复用已装的 `vue-draggable-plus` 做拖拽排序过渡（现仅部分页面用）。
- **价值**：中。
- **工作量**：中。
- **风险**：中（大列表动画会掉帧，需设行数阈值）。
- **前置**：V1、V8（reduced-motion 兜底）。

### V5 · 加载态分级（骨架屏 + 局部 loading）【体验提升】

- **现状**：只有整页 `v-loading` 遮罩。
- **方案**：
  - 把 `index.html` 骨架屏的做法**组件化**：`<Skeleton>` 通用骨架组件（表格/卡片/图表三形态）。
  - 表格首次加载用骨架，刷新用「局部 loading」（保留旧数据 + 顶部细进度条），避免整表闪烁。
  - 图表/看板用占位骨架 + 淡入。
- **价值**：中-高。
- **工作量**：中。
- **风险**：低。
- **前置**：V1。

### V6 · 看板动效（ECharts 过渡 + 数字滚动）【画龙点睛】

- **现状**：安全态势看板 / 业务概况静态。
- **方案**：
  - ECharts 开启入场动画（`animationDuration` / `animationEasing`），折线/柱状过渡。
  - 关键数字（总数、环比）用**零依赖 `useCountUp` composable**（`requestAnimationFrame` 缓动），
    **只在首次挂载/数据变化时滚一次**，不随 TanStack Query 每次 refetch 重滚。
- **价值**：中。
- **工作量**：中。
- **风险**：中（动效触发时机要克制，否则喧宾夺主）。
- **前置**：V1、V8。

### V7 · 空/错/成功反馈统一【一致性提升】

- **现状**：反馈文案/形态零散。
- **方案**：
  - 统一「空状态」组件（插画 + 标题 + 可选 CTA），替换各表格裸空文字。
  - 统一错误态（区分「网络/权限/服务端」三类，给可操作建议，复用 `Console.vue` 已有的 `el-result` 形态）。
  - 统一成功反馈（toast 文案模板 + 时长规范）。
- **价值**：中。
- **工作量**：中。
- **风险**：低。
- **前置**：V1。

### V8 · 无障碍与动效降级【护栏 · 贯穿全程】

- **现状**：无 reduced-motion、无统一 focus-visible、对比度未审计。
- **方案**：
  - 全局注入 `@media (prefers-reduced-motion: reduce)` 规则：关闭所有自定义动画/过渡。
  - 统一 `:focus-visible` 样式（token 化的描边色）。
  - 主色/状态色与文字对比度做一次审计（≥ WCAG AA 4.5:1）。
- **价值**：中（合规 + 专业度）。
- **工作量**：低。
- **风险**：低。
- **前置**：V1。

## 3. 性能与无障碍护栏（动效安全准则）

> 本次改造的「不可破」约束，逐条写死，防止视觉改造回退既有性能成果：

1. **只动 `transform` / `opacity`**，不触发 layout/paint 的宽高/位置动画（用 `will-change` 只加在真动画元素上）。
2. **尊重 `prefers-reduced-motion`**：所有自定义动效统一走一个 `useMotionSafe()` 判定或全局 CSS 覆盖。
3. **大列表不逐行动画**：行级过渡设阈值（如 ≤ 50 行），大表只做整体淡入。
4. **不引入运行时动效库**：ECharts 已 ~2.77MB；数字滚动用 `rAF` 自研，不新增依赖。
5. **遵守体积预算**：入口 450KB / 总量 900KB gzip（`check-bundle-size.mjs` 已存在，改造后需重新跑）。
6. **不破坏既有门禁**：`maskContract.spec.ts` / `permissions.spec.ts` / `check-permission-codes` 等扫描型门禁，
   新组件/composable 若被扫到需同步补用例。

## 4. 推荐执行顺序与分批

| 批次 | 内容 | 独立交付 | 依赖 |
| --- | --- | --- | --- |
| 第一批 | V1 设计 Token + V2 深色模式 | 一个 PR，改主色全局生效 + 一键深色 | 无 |
| 第二批 | V5 加载态分级 + V3 路由过渡 | 骨架屏 + 页面过渡 | V1 |
| 第三批 | V7 反馈统一 + V4 微交互/列表动效 | 空/错/成功 + hover/focus/FLIP | V1、V8 |
| 第四批 | V6 看板动效 | 图表入场 + 数字滚动 | V1、V8 |
| 贯穿 | V8 无障碍与动效降级 | 随每批落地 | V1 |

> 每批**单开 PR + CI 三 job 全绿**再合，不混入数据权限收口主链（与既有「前端二次改造」提案的纪律一致）。
