# 导出与注入面安全审计

> 触发：生产级审查「全方位/深层次/多维度审核」的延续。本批专查两类常被漏掉的注入面——
> SQL 注入（原生 SQL / `${}` 拼接）与 CSV 导出公式注入。**结论：SQL 注入无漏洞（已取证），
> CSV 公式注入有一处低危缺口（框架限制，给出落地建议，未擅自改）。**

---

## 0. 结论先行

1. **SQL 注入：无漏洞**。mapper XML 里 22 处 `${fragment}` 看着吓人，实为数据权限行过滤片段——
   服务端 `SqlPermissionRuleRenderer` 生成、值走 `:dpRule*` 标量绑定、`RowPermissionPredicate.requireBindable`
   只放行标量且拒绝集合/不可绑定类型。**片段结构不来自用户输入**（§1）。
2. **CSV 公式注入：已落地**。导出 CSV 经 `CollectionUtil.toCsvInputStream`（框架静态反射），文本字段
   以 `=`/`+`/`-`/`@` 开头会在 Excel 打开时当公式执行（客户端侧、低危）。已新增 `CsvFormulaSanitizer`
   （遍历全部 String 字段、副本前缀单引号、不改原实体）并接入 21 个自定义导出服务（§2）。
3. **其余导出相关面**（路径穿越 / 大小越界 / 扩展名白名单）已在 `FileService.upload` 就位（MD5 落盘、
   文件名用 MD5、扩展名按 `FileCategory` 白名单），无缺口。

---

## 1. SQL 注入面取证（无漏洞）

### 1.1 `${fragment}` 是什么

22 个 mapper XML 里的 `AND ${fragment}` 是数据权限的**行级过滤片段**，注入链如下：

```
数据权限策略(condition_json) → SqlPermissionRuleRenderer.render → RowPermissionPredicate
  → 片段 SQL（结构服务端生成）+ 标量参数（:dpRule0_0 …）
  → mapper 的 <if test="fragment != null">AND ${fragment}</if>
```

关键护栏（`RowPermissionPredicate`）：

- `requireBindable`：只接受 `Number / String / Boolean` 标量；集合/数组一律拒绝
  （「fragments must come from SqlPermissionRuleRenderer」）；
- `null` 一律拒绝（`col = NULL` 在 SQL 里是「未知」，宁可闸口抛）；
- `IN` 列表由渲染器逐项展开成独立 `:dpRule*` 参数，不接受 `IN (:list)` 的驱动依赖。

> 结论：`${fragment}` 是**受控拼接**——SQL 结构来自渲染器白名单语法、数据走绑定参数，
> 等价于「参数化查询 + 受限的结构模板」。真正的注入要件（用户输入直接进 SQL 文本）不成立。

### 1.2 其余 SQL 面

| 位置 | 形态 | 结论 |
| --- | --- | --- |
| `DataFieldPolicyRepository` `@Query` | `:resourceKey` 绑定参数 | 安全 |
| `CodeRuleService` `String.format("%0"+n+"d", …)` | 数字补零格式化（非 SQL） | 安全 |
| 其余 CRUD | JPA / MyBatis-Plus 预编译 | 安全 |

## 2. CSV 公式注入（低危，已落地）

### 2.1 问题

导出走 `CollectionUtil.toCsvInputStream(entities, Class)`（框架静态反射取字段值拼 CSV）。
文本字段（客户名/物料名/备注等，用户可写）若以 `=`、`+`、`-`、`@`、`\t`、`\r` 开头，用户用
Excel/WPS 打开导出的 CSV 时会被解释为**公式/外部链接**执行（CSV/Formula Injection，CWE-1236）。

- **严重度：低**——纯客户端行为，服务端无代码执行；现代 Excel 已对多数向量加确认弹窗；
- **触发条件**：管理员把含恶意单元格的 CSV 用表格软件打开。

### 2.2 落地实现（`common/CsvFormulaSanitizer`）

- 新增静态工具 `CsvFormulaSanitizer`：遍历实体的**全部 String 字段**（含继承层次，缓存字段清单），
  值以危险首字符开头时在**副本**上前缀单引号 `'`（`=cmd` → `'=cmd`），再交给 `toCsvInputStream`。
- **为何遍历全部 String 字段而非只盯 `@Export`**：框架字段选择是内部反射、无法在无框架源码下保证
  「逐字段一致」，而「多转义无害、漏转义有害」——非导出字段转义了也不进 CSV，导出字段必被覆盖。
- **绝不改原对象**：与 `ExportColumnMasker.maskForExport` 同款「复制实体」模式（Spring `BeanUtils`），
  原实体可能仍在本事务持久化上下文里，直接 `field.set` 会把 `'` 写进库。
- 接入 **两条导出链**：
  1. **21 个自定义导出服务**（`*Service.createMapperExportTask`）：`toCsvInputStream(masked, …)` 一行改为
     `toCsvInputStream(CsvFormulaSanitizer.sanitize(masked), …)`；
  2. **框架 JPA 回退导出**（`CurdController.export` → `super.export`，Mapper 读链路关闭时走）：
     `BaseService.afterExportQuery` 改为 `sanitize(maskForExport(entities))`，与既有遮蔽同一钩子、一层覆盖。
- 契约测试 `CsvFormulaSanitizerTest` 6 用例（六种危险首字符 / 安全值不复制 / 副本不改原实体 /
  继承字段 / 非 String 忽略）。

### 2.3 待本机验证

- 本机 `./mvnw test` 跑 `CsvFormulaSanitizerTest`；
- 真实环境导出一个含 `=1+1` 前缀文本的客户/物料，用 Excel 打开确认显示为文本（不执行公式），
  并确认数据权限遮蔽与公式转义同时生效（两层各自复制实体、互不覆盖）。

## 3. 与其它能力的关系

- **导出遮蔽**（`ExportColumnMasker`）：公式转义（`CsvFormulaSanitizer`）与列级脱敏是**两个独立关切**，
  分两层做——脱敏在 `maskForExport`、转义在 `sanitize`，叠加时各自复制实体、互不覆盖（接入顺序：
  `maskForExport(rows)` → `sanitize(masked)` → `toCsvInputStream`）。
- **文件上传**（`FileService.upload`）：已做扩展名白名单 + MD5 落盘 + 大小上限，与本批「导出」互补，
  构成「进（上传）出（导出）都防滥用」的完整闭环。
- **公开端点限流**（`RateLimitHelper`）：导出是登录后操作，不属公开端点；但大导出任务应留意
  `createExportTask` 的异步线程池（数据权限批已取证其 `CallerRunsPolicy` 退化为同步），与限流无关。
