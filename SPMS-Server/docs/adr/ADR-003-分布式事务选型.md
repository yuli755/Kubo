# ADR-003: 分布式事务选型 - Seata AT 模式 vs TCC/Saga/本地消息表

> **状态**：✅ 已通过
> **日期**：2026-08-01
> **决策者**：后端架构师
> **技术栈影响**：后端事务层
> **关联文档**：[分布式事务框架](../Kubo 平台高并发重构实施路线规划计划.md#5-关键技术攻关专项-贯穿全周期)

---

## 1. 背景与问题

### 问题描述
- 微服务拆分后，跨服务业务操作需要强一致性保证
- 核心场景：订单创建 → 库存扣减 → 财务记账 (三服务强一致)
- 原单体架构使用本地事务，拆分后需要分布式事务方案

### 约束条件
- 核心交易链路要求强一致性 (RPO=0)
- 团队对 Seata AT 模式有使用经验
- 业务代码改动最小化原则 (AT 模式零侵入)
- 性能要求：事务提交延迟 < 100ms

### 驱动因素
- 微服务拆分后的数据一致性保证
- 业务代码零侵入 (AT 模式优势)
- 团队技术栈复用

---

## 2. 备选方案

### 方案 A: Seata AT 模式 (Automatic Transaction) ✅ **选中**

| 维度 | 评价 |
|------|------|
| **优点** | - **零业务代码侵入**：仅需加 `@GlobalTransactional` 注解<br>- 自动生成反向 SQL 回滚，无需手写补偿逻辑<br>- 支持 MySQL/PostgreSQL/Oracle 等主流数据库<br>- Spring Cloud Alibaba 原生集成，配置极简<br>- 团队有生产经验，风险可控<br>- 支持多种隔离级别、全局锁、分支事务并发控制 |
| **缺点** | - 长事务锁定资源时间长，并发性能受限<br>- 大事务 (多表、多行) 产生大量行锁，死锁风险增加<br>- 需要数据库支持 `SELECT FOR UPDATE` (MySQL 支持)<br>- 网络分区时可能阻塞资源直到超时<br>- 不支持跨数据库类型 (异构事务) |
| **技术成熟度** | 高 (生产级) |
| **团队熟悉度** | 高 (有经验) |
| **代码侵入性** | 极低 (仅注解) |
| **性能开销** | 中 (行锁 + 反向 SQL 生成) |
| **调试难度** | 中 (需开启 SQL 审计) |

### 方案 B: TCC (Try-Confirm-Cancel)

| 维度 | 评价 |
|------|------|
| **优点** | - 无长事务锁，资源占用时间短，并发性能高<br>- 业务语义明确，Try/Confirm/Cancel 语义清晰<br>- 支持异构事务 (跨数据库、跨服务、跨中间件)<br>- 补偿逻辑由业务控制，灵活性强<br>- 适合高并发、长流程场景 |
| **缺点** | - **业务代码侵入极大**：每个接口需实现 Try/Confirm/Cancel 三个方法<br>- 幂等性、空回滚、悬挂控制需业务手动实现<br>- 业务开发成本极高、维护成本高<br>- 补偿逻辑复杂，容易出错<br>- 需要业务方深度参与设计 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 中 |
| **代码侵入性** | 极高 (三接口) |
| **性能开销** | 低 (无长锁) |
| **调试难度** | 高 (分布式追踪复杂) |

### 方案 C: Saga 模式 (编排/编舞)

| 维度 | 评价 |
|------|------|
| **优点** | - 适合长流程、多服务编排<br>- 无长锁、高并发<br>- 补偿逻辑显性化、可视化编排<br>- 适合业务流程长、人工介入场景 |
| **缺点** | - 最终一致性 (非强一致)<br>- 补偿逻辑复杂、需人工干预兜底<br>- 编排器单点风险 (需高可用)<br>- 调试、追踪复杂 |
| **技术成熟度** | 中 |
| **团队熟悉度** | 低 |
| **代码侵入性** | 中 |
| **性能开销** | 低 |
| **调试难度** | 高 |

### 方案 D: 本地消息表 + 定时补偿 (最终一致性)

| 维度 | 评价 |
|------|------|
| **优点** | - 实现简单、无额外组件依赖<br>- 无长锁、高并发<br>- 消息可靠性由数据库事务保证<br>- 适合非核心、允许最终一致场景 |
| **缺点** | - **最终一致性** (非强一致)<br>- 消息延迟 (依赖定时轮询)<br>- 补偿逻辑需手动编写<br>- 消息堆积、重复消费、乱序处理复杂 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 高 |
| **代码侵入性** | 中 |
| **性能开销** | 低 |
| **调试难度** | 中 |

## 3. 决策结果

**最终选择**：**混合模式 - 核心强一致链路用 Seata AT，非核心允许最终一致用本地消息表**

### 核心强一致链路 (必须强一致) → **Seata AT 模式**

| 场景 | 服务 | 一致性要求 | 方案 |
|------|------|------------|------|
| 订单创建 → 库存扣减 → 财务记账 | `kubo-sales` → `kubo-wms` → `kubo-finance` | **强一致 (RPO=0)** | `@GlobalTransactional` |
| 采购入库 → 库存增加 → 财务应付 | `kubo-procurement` → `kubo-wms` → `kubo-finance` | **强一致** | `@GlobalTransactional` |
| 工单完工 → 库存入库 → 成本结转 | `kubo-mes` → `kubo-wms` → `kubo-finance` | **强一致** | `@GlobalTransactional` |

### 非核心/允许最终一致 (允许秒级延迟) → **本地消息表 + RabbitMQ 可靠投递**

| 场景 | 服务 | 一致性要求 | 方案 |
|------|------|------------|------|
| 日志审计、操作记录 | 所有服务 | 最终一致 | 本地消息表 + 异步写入 |
| 通知推送 (短信/邮件/钉钉) | `kubo-notify` | 最终一致 | RabbitMQ 可靠投递 |
| 报表数据同步 | `kubo-report` | 最终一致 | Flink CDC / 定时同步 |
| 设备遥测数据上报 | `kubo-iot` | 最终一致 | 批量批量写入 |
| 报表导出、大文件生成 | `kubo-report` | 最终一致 | SSE/异步任务 |

## 3. 决策结果详细说明

### Seata AT 模式最佳实践 (强制执行)

| 规则 | 说明 |
|------|------|
| **全局事务注解** | 仅在**入口 Service 方法**加 `@GlobalTransactional`，Controller 禁止加 |
| **分支事务** | 所有涉事 Service 方法**不加** `@Transactional`，由 Seata 代理管理 |
| **全局锁** | 更新操作**必须**走 `SELECT ... FOR UPDATE`，禁用乐观锁 `@Version` (AT 模式自动加全局锁) |
| **超时配置** | `timeout=30000` (30s)，防止长事务死锁 |
| **回滚策略** | 默认 `RuntimeException` 触发回滚，业务异常需手动抛出 `RuntimeException` |
| **分支事务幂等** | 所有 Service 方法**必须**幂等 (基于 `Idempotency-Key`) |
| **SQL 审计** | 开启 `undo_log` 表监控，定期清理过期记录 (保留 7 天) |
| **性能红线** | 单全局事务涉及表 < 10 个、行锁 < 1000 行、耗时 < 30s |

### 本地消息表设计规范 (最终一致)

```sql
CREATE TABLE message_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_key VARCHAR(128) NOT NULL UNIQUE COMMENT '幂等键',
    exchange VARCHAR(128) NOT NULL COMMENT '交换机',
    routing_key VARCHAR(128) NOT NULL COMMENT '路由键',
    payload JSON NOT NULL COMMENT '消息体',
    status ENUM('INIT','SENT','DONE','FAILED') DEFAULT 'INIT' COMMENT '状态',
    retry_count INT DEFAULT 0 COMMENT '重试次数',
    max_retry INT DEFAULT 10 COMMENT '最大重试',
    next_retry_time DATETIME COMMENT '下次重试时间',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status_retry (status, next_retry_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='本地消息表';
```

**投递流程**：
1. 本地事务内：业务数据写入 + `message_log` 写入 (status=INIT) → 提交
2. 事务提交后：发送 RabbitMQ → 更新 status=SENT
3. 消费端消费成功 → ACK → 发送 HTTP 回调 / 发送确认消息 → 更新 status=DONE
4. 定时任务 (每分钟)：扫描 `status=SENT AND retry_count < max_retry AND next_retry_time < NOW()` → 重发
5. 超过最大重试次数 → status=FAILED → 死信队列/人工处理

## 3. 决策结果总结

**最终选择**：**混合模式 - 核心 Seata AT + 非核心本地消息表**

**选择理由**：
1. **核心交易零妥协** - 订单/库存/财务强一致，Seata AT 零侵入保证正确性
2. **非核心高性能** - 通知/日志/报表最终一致，高吞吐低延迟
3. **团队经验复用** - 团队对 Seata AT 和本地消息表均有生产经验
2. **架构清晰** - 强一致/最终一致边界清晰，治理简单

**妥协与风险**：
- Seata AT 长事务锁资源 → 严格控制事务边界、行锁数量、超时时间
- 本地消息表延迟 (秒级) → 业务侧接受最终一致语义
- 双模式增加认知负担 → 文档化边界、Code Review 强制检查

**缓解措施**：
- 建立 `kubo-seata-starter` 统一封装，封装最佳实践
- 建立 `kubo-common-mq` 封装本地消息表模板
- Code Review 强制检查：全局事务边界、锁范围、超时配置
- 压测验证：核心链路 3000 QPS、P99 < 150ms、死锁率 < 0.01%
