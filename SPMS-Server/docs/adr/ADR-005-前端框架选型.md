# ADR-005: 前端框架选型 - Vue 3 + TypeScript + Vite + Pinia + Element Plus + @airpower/web

> **状态**：✅ 已通过
> **日期**：2026-08-01
> **决策者**：前端架构师
> **技术栈影响**：前端技术栈
> **关联文档**：[前端技术栈选型](../archive/Kubo 平台-前端高并发重构实施路线规划计划.md#3-技术栈升级与选型确认)

---

## 1. 背景与问题

### 问题描述
- 现有前端基于 Vue 3 + TypeScript + Vite + Element Plus + @airpower/web
- 需要支撑 10k+ 并发用户、复杂交互、高性能渲染
- 现有架构存在：构建未压缩、无服务端状态管理、WebSocket 无心跳重连、大表格/图表渲染卡顿

### 约束条件
- 团队对 Vue 3 + TypeScript + Element Plus 熟悉
- @airpower/web 为内部基础框架，强耦合，短期无法替换
- 预算有限，倾向成熟生态方案
- 需要支持 PWA 离线、大数据渲染、实时通信

### 驱动因素
- 高并发场景下的性能优化需求
- 复杂交互场景的状态管理需求
- 实时通信稳定性需求
- 工程化、工程质量提升需求

---

## 2. 备选方案

### 方案 A: Vue 3 + TypeScript + Vite + Pinia + Element Plus + @airpower/web + 新增核心库 ✅ **选中**

| 维度 | 评价 |
|------|------|
| **优点** | - **零重写成本**：复用现有 Vue 3 + TS + Element Plus + @airpower/web 投资<br>- **生态成熟**：Vue 3.5 + TS 5.9 + Vite 7 + Pinia 3 + Element Plus 2.12 均为最新稳定版<br>- **增量重构**：可模块化引入 @tanstack/vue-query、虚拟滚动、WebWorker、PWA<br>- **团队零学习成本**：核心技术栈不变，仅引入增强库<br>- **@airpower/web 适配**：已有适配器层设计，风险可控<br>- **生态完善**：工具链、DevTools、社区支持完善 |
| **缺点** | - @airpower/web 强耦合，长期需自研核心组件替代<br>- Element Plus 组件库较重，需按需引入优化<br>- Vue 3 响应式系统在超大数据量下仍有性能瓶颈 (需 WebWorker/虚拟滚动)<br>@airpower/web 升级破坏性变更风险 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 极高 |
| **重构成本** | 低 (增量重构) |
| **性能上限** | 高 (配合虚拟滚动/WebWorker/PWA) |
| **生态成熟度** | 完善 |

### 方案 B: React 18 + TypeScript + Next.js + Zustand + Ant Design

| 维度 | 评价 |
|------|------|
| **优点** | - React 生态最繁荣、人才最多<br>- Next.js 全栈框架、SSR/SSG/ISR 支持完善<br>- Server Components 减少客户端包体积<br>- 生态最繁荣、组件库最丰富 |
| **缺点** | - **完全重写**，重构成本极高、周期长、风险极大<br>- 团队 Vue 技能栈需全面转型，学习曲线陡峭<br>- @airpower/web 无法复用，需完全重写业务组件<br>- 现有业务逻辑全部重写，风险不可控<br>- 10k 并发场景下 Next.js SSR 压力大，需额外缓存层 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 (需全员转型) |
| **重构成本** | 极高 (完全重写) |
| **风险** | 极高 |
| **迁移周期** | 6-12 个月 |

### 方案 C: Vue 3 + Nuxt 3 + Pinia + Element Plus

| 维度 | 评价 |
|------|------|
| **优点** | - Nuxt 3 SSR/SSG/SSG 支持、SEO 友好<br>- 自动导入、约定优于配置、开发体验好<br>- Nitro 引擎支持多平台部署 |
| **缺点** | - SSR 对 10k 并发压力大，需额外缓存/CDN<br>- @airpower/web 兼容性未知<br>- 服务端渲染增加架构复杂度<br>- 团队无 Nuxt 3 生产经验 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 中 |
| **重构成本** | 中 |
| **风险** | 中 |

### 方案 D: 微前端 (qiankun / Module Federation) + 现有技术栈

| 维度 | 评价 |
|------|------|
| **优点** | - 技术栈无关、可渐进式迁移<br>- 团队自治、独立部署<br>- 新旧技术栈共存 |
| **缺点** | - 架构复杂度极高 (沙箱隔离、通信、样式隔离、公共依赖共享)<br>- 调试极其困难<br>- 首屏加载性能通常下降<br>- 10k 并发场景下不必要 (单体前端足够) |
| **技术成熟度** | 中 |
| **团队熟悉度** | 低 |
| **复杂度** | 极高 |
| **风险** | 高 |

## 3. 决策结果

**最终选择**：方案 A - **Vue 3 + TypeScript + Vite + Pinia + Element Plus + @airpower/web + 增强库**

**选择理由**：
1. **零重写成本** - 复用现有 10 万+ 行代码投资，风险最低
2. **团队零学习成本** - 核心技术栈不变，仅引入增强库
3. **增量重构可控** - 可模块化引入增强库，模块化验证
4. **@airpower/web 适配可控** - 已建立适配器层设计，长期可替代
4. **性能目标可达成** - 配合虚拟滚动、WebWorker、PWA、@tanstack/vue-query 可达成所有 SLA

**妥协与风险**：
- @airpower/web 强耦合 → 建立适配器层隔离，长期计划自研核心组件替代
- Element Plus 组件重 → 严格按需引入 + 图标 Sprite
- 大数据渲染瓶颈 → 虚拟滚动 + WebWorker + progressive 渲染

**缓解措施**：
- 锁定 @airpower/web 版本 `^2.9.1`，建立适配器层隔离核心依赖
- 核心组件二次封装 (VirtualTable/ProChart/ProForm/ProSearch)
- 建立组件库 Storybook 文档，规范使用规范

## 3. 架构模式重构

| 模式 | 现状 | **重构后** | 收益 |
|------|------|------------|------|
| **状态管理** | Pinia 分散 | **分层状态架构**：`Global Store` + `Feature Store` + `Server State` (@tanstack/vue-query) | 关注点分离、服务端状态自动缓存/去重/预取 |
| **API 请求层** | Axios 直接调用 | **统一请求网关**：`useRequest` + 请求取消/重试/去抖/缓存/错误码统一处理 | 重试策略、防抖搜索、请求去重、离线队列 |
| **实时通信** | airpower-websocket 直接用 | **WebSocket Manager**：心跳重连、消息分优先级队列、背压控制、断点续传 | 10k 并发稳定、消息不丢、不阻塞主线程 |
| **权限系统** | 指令/装饰器分散 | **Permission Engine**：编译期裁剪 + 运行时缓存 + 指令/组件/函数三重防护 | 渲染零开销、动态权限秒级生效 |
| **构建产物** | 单包、未压缩 | **代码分割 + 多级缓存 + 压缩 + PWA** | 首包 < 200KB、二次访问离线可用 |
