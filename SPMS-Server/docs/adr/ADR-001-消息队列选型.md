# ADR-001: 消息队列选型 - RabbitMQ vs RocketMQ

> **状态**：✅ 已通过
> **日期**：2026-08-01
> **决策者**：后端架构师
> **技术栈影响**：后端基础设施
> **关联文档**：[RabbitMQ 关键模式落地设计](../archive/Kubo 平台高并发重构实施路线规划计划.md#3-rabbitmq-关键模式落地设计-替代-rocketmq-原生能力)

---

## 1. 背景与问题

### 问题描述
- 微服务架构需要可靠的消息队列支撑异步解耦、事件驱动、最终一致性
- 原系统无统一消息队列，直接 HTTP 调用耦合度高
- 需要支持：事务消息、顺序消息、延时消息、高吞吐、死信重试

### 约束条件
- 团队对 RabbitMQ 运维经验丰富 (已有生产环境运维经验)
- 现有监控告警体系已集成 RabbitMQ
- 团队对 RocketMQ 无生产运维经验
- 预算有限，倾向开源方案

### 驱动因素
- 微服务拆分后的异步解耦需求
- 分布式事务 (Seata AT) 需要可靠消息投递
- 库存扣减等场景需要顺序消费
- 订单超时、预警升级需要延时消息

---

## 2. 备选方案

### 方案 A: RabbitMQ 3.12+ (Quorum Queues) ✅ **选中**

| 维度 | 评价 |
|------|------|
| **优点** | - 团队运维经验丰富，零学习成本<br>- Spring AMQP / Spring Cloud Stream 原生支持<br>- Quorum Queues 提供高可用、数据安全<br>- 死信队列 (DLX) + TTL 完美支持延时消息<br>- 一致性哈希分片队列 + 单消费者实现顺序消费<br>- 管理 UI 友好，运维可视化好<br>- 协议标准 (AMQP 0-9-1)，多语言客户端成熟 |
| **缺点** | - 吞吐量十万级/秒 (低于 RocketMQ 百万级)<br>- 事务消息需基于「本地消息表 + 定时补偿」实现<br>- 大消息性能一般 (>1MB 需分片)<br>- Erlang 运行时排查难度较大 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 高 |
| **运维复杂度** | 中 |
| **成本** | 低 (开源) |
| **扩展性** | 中 (集群扩容需重新分区) |
| **生态成熟度** | 完善 |

### 方案 B: RocketMQ 5.x

| 维度 | 评价 |
|------|------|
| **优点** | - 原生支持事务消息、顺序消息、延时消息<br>- 百万级/秒吞吐量<br>- 存储性能强、大消息友好<br>- 社区活跃、阿里巴巴主导 |
| **缺点** | - 团队零运维经验，学习曲线陡峭<br>- 运维工具链需从零建设<br>- NameServer + Broker 部署相对复杂<br>- Spring 生态集成不如 RabbitMQ 原生<br>- 监控告警体系需从零建设 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 (零经验) |
| **运维复杂度** | 高 |
| **成本** | 低 (开源) |
| **扩展性** | 强 (水平扩展友好) |
| **生态成熟度** | 良好 |

### 方案 C: Apache Kafka

| 维度 | 评价 |
|------|------|
| **优点** | - 极高吞吐量、海量数据存储<br>- 日志语义、回放能力强<br>- 扩展性极强 |
| **缺点** | - 运维极其复杂 (ZooKeeper/KRaft)<br>- 延时消息、事务消息支持弱<br>- 顺序消费实现复杂<br>- 运维团队无经验<br>- 过度设计 (非日志/流处理场景) |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 |
| **运维复杂度** | 极高 |
| **成本** | 高 (运维成本) |
| **扩展性** | 极强 |
| **生态成熟度** | 完善 (但偏大数据场景) |

---

## 3. 决策结果

**最终选择**：方案 A - **RabbitMQ 3.12+ (Quorum Queues)**

**选择理由**：
1. **团队零学习成本** - 现有运维经验可直接复用，风险最低
2. **Spring 生态原生支持** - Spring AMQP / Spring Cloud Stream RabbitMQ Binder 零配置集成
3. **运维体系复用** - 现有监控、告警、运维 SOP 可直接复用
4. **功能需求可满足** - 通过「本地消息表 + 定时补偿」实现事务消息，分片队列实现顺序消费，DLX+TTL 实现延时消息，完全满足业务需求
5. **成本最优** - 零学习成本、零运维建设成本、零监控建设成本

**妥协与风险**：
- 吞吐量上限十万级/秒 (但 10k 用户场景峰值 5k QPS 远低于上限)
- 事务消息需自研「本地消息表 + 定时补偿」方案 (已有成熟方案)
- 大消息 (>1MB) 需应用层分片

**缓解措施**：
- 建立 RabbitMQ 运维手册、故障演练 SOP
- 核心链路建立「本地消息表 + 定时补偿」标准化模板
- 监控告警覆盖：连接数、队列堆积、磁盘使用率、消费延迟
