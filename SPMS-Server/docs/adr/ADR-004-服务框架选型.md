# ADR-004: 服务框架选型 - Spring Cloud Alibaba (Nacos + Dubbo 3) vs Spring Cloud Netflix / k8s Native

> **状态**：✅ 已通过
> **日期**：2026-08-01
> **决策者**：后端架构师
> **技术栈影响**：后端服务框架
> **关联文档**：[服务框架版本表](../archive/Kubo 平台高并发重构实施路线规划计划.md#12-完整技术栈版本表)

---

## 1. 背景与问题

### 问题描述
- 微服务架构需要服务注册发现、配置中心、RPC 通信、负载均衡、熔断限流
- 原单体架构无服务治理能力
- 团队对 Spring Cloud Alibaba 生态熟悉

### 约束条件
- 团队对 Spring Cloud Alibaba (Nacos + Dubbo) 有生产经验
- 需要支持多语言扩展 (未来可能接入 Go/Python 服务)
- 预算有限，倾向开源方案
- 需要与 Kubernetes 原生集成

### 驱动因素
- 微服务治理标准化
- 服务间高性能 RPC 通信
- 配置动态刷新、灰度发布支持

---

## 2. 备选方案

### 方案 A: Spring Cloud Alibaba (Nacos 2.x + Dubbo 3.x Triple) ✅ **选中**

| 维度 | 评价 |
|------|------|
| **优点** | - 团队零学习成本，生产经验丰富<br>- Nacos 同时解决注册中心 + 配置中心，组件少<br>- Dubbo 3 Triple 协议基于 gRPC，高性能、多语言支持、流控熔断内置<br>- Spring Cloud Alibaba 一站式集成，配置极简<br>- Nacos 支持动态配置推送、灰度发布、命名空间隔离<br>- 社区活跃、阿里巴巴主导、文档完善 |
| **缺点** | - 组件版本升级需关注兼容性矩阵<br>- Dubbo 3 Triple 协议调试工具相对较少<br>- Nacos 单集群写入性能瓶颈 (需分集群) |
| **技术成熟度** | 高 |
| **团队熟悉度** | 高 |
| **运维复杂度** | 中 |
| **成本** | 低 (开源) |
| **多语言支持** | 强 (Triple/gRPC) |
| **生态成熟度** | 完善 |

### 方案 B: Spring Cloud Netflix (Eureka + Feign/Hystrix) + Spring Cloud Config

| 维度 | 评价 |
|------|------|
| **优点** | - Spring Cloud 核心组件，文档最全<br>- 社区最成熟、资料最多 |
| **缺点** | - **Netflix 组件多已停维护** (Hystrix/Eureka/Zuul 进入维护模式)<br>- 组件多 (Eureka + Config Server + Bus + Hystrix + Zuul/Gateway)，运维复杂<br>- Feign 性能弱于 gRPC/Dubbo Triple<br>- 无原生多语言支持<br>- Spring Cloud Config 依赖 Git，大配置推送慢 |
| **技术成熟度** | 高 (但停维护) |
| **团队熟悉度** | 中 |
| **运维复杂度** | 高 (组件多) |
| **成本** | 低 |
| **多语言支持** | 弱 |
| **生态成熟度** | 成熟但停维护 |

### 方案 C: Kubernetes Native (Service Mesh: Istio/Linkerd) + gRPC

| 维度 | 评价 |
|------|------|
| **优点** | - 基础设施层解耦，应用零侵入<br>- 强大的流量管理、安全、可观测性<br>- 原生 Kubernetes 集成、GitOps 友好<br>- 多语言透明支持 |
| **缺点** | - **学习曲线极陡峭**，团队零经验<br>- 资源开销大 (Sidecar 每 Pod + 100MB+ 内存)<br>- 排查难度极大 (Sidecar 代理层)<br>- 运维复杂度极高 (CRD、CR、控制平面)<br>- 过度设计 (10k 用户规模不需要 Service Mesh) |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 (零经验) |
| **运维复杂度** | 极高 |
| **成本** | 高 (资源 + 运维) |
| **扩展性** | 极强 |
| **生态成熟度** | 完善 |

### 方案 D: Spring Cloud Gateway + Spring Cloud LoadBalancer + Resilience4j + Nacos

| 维度 | 评价 |
|------|------|
| **优点** | - Spring 官方组件、长期维护<br>- 组件轻量、组合灵活<br>- Resilience4j 功能强大 (熔断、限流、重试、舱壁) |
| **缺点** | - 无成熟 RPC 框架 (只能 REST/Feign)<br>- 缺乏服务治理能力 (路由、熔断需自己组装)<br>- 多语言支持弱<br>- 组装工作量大、易踩坑 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 中 |
| **运维复杂度** | 中 |
| **成本** | 低 |
| **多语言支持** | 弱 |

## 3. 决策结果

**最终选择**：方案 A - **Spring Cloud Alibaba (Nacos 2.x + Dubbo 3.x Triple)**

**选择理由**：
1. **团队零学习成本** - 核心竞争力，生产经验可直接复用
2. **一站式解决** - Nacos 同时解决注册中心 + 配置中心，组件最少
3. **高性能 RPC** - Dubbo 3 Triple 基于 gRPC，性能强、多语言支持
4. **生态成熟** - Spring Cloud Alibaba 一站式集成，配置极简
5. **多语言扩展** - Triple 协议天然支持 Go/Python/Node.js 服务接入
6. **运维体系复用** - 现有 Nacos/Dubbo 运维经验、监控告警可直接复用

**妥协与风险**：
- Dubbo 3 Triple 协议调试工具较少 → 使用 `dubbo-admin` + `grpcurl` + 日志追踪
- Nacos 单集群写入瓶颈 → 按业务域分集群 (核心/非核心/配置)
- 版本兼容性矩阵复杂 → 统一版本锁定在父工程 `kubo-parent`

**缓解措施**：
- 统一版本锁定在 `kubo-parent` (Spring Cloud 2023.x + Spring Boot 3.2 + Dubbo 3.2 + Nacos 2.3)
- 建立 `kubo-common-dubbo` 统一封装 (序列化、超时、重试、熔断、指标)
- 建立 Nacos 配置规范：命名空间隔离 (dev/staging/prod)、配置分组 (common/业务域)

## 3. 关键配置规范

### 3.1 Nacos 配置规范

```yaml
# bootstrap.yml 统一配置
spring:
  application:
    name: ${SERVICE_NAME:kubo-service}
  cloud:
    nacos:
      config:
        server-addr: ${NACOS_ADDR:localhost:8848}
        namespace: ${NACOS_NAMESPACE:dev}
        group: ${SERVICE_GROUP:kubo}
        file-extension: yaml
        shared-configs:
          - data-id: kubo-common.yaml
            group: kubo-common
            refresh: true
          - data-id: kubo-database.yaml
            group: kubo-common
            refresh: true
          - data-id: kubo-redis.yaml
            group: kubo-common
            refresh: true
      discovery:
        server-addr: ${NACOS_ADDR:localhost:8848}
        namespace: ${NACOS_NAMESPACE:dev}
        group: ${SERVICE_GROUP:kubo}
        metadata:
          version: ${APP_VERSION:1.0.0}
          zone: ${ZONE:zone-a}
```

### 3.2 Dubbo 3 Triple 配置规范

```yaml
dubbo:
  application:
    name: ${spring.application.name}
    qos-enable: false
  protocol:
    name: tri
    port: 50051
  registry:
    address: nacos://${NACOS_ADDR:localhost:8848}?namespace=${NACOS_NAMESPACE:dev}
  registry:
    check: false
  consumer:
    check: false
    timeout: 3000
    retries: 2
    loadbalance: loadbalance
  provider:
    timeout: 3000
    threadpool: fixed
    threads: 200
    queues: 100
  serialization: protobuf
  codec: protobuf
```

### 3.3 统一超时与重试规范

| 场景 | 超时时间 | 重试次数 | 重试间隔 | 熔断阈值 |
|------|----------|----------|----------|----------|
| 同城 RPC | 3s | 2 | 100ms | 50% 错误率/10s |
| 跨 AZ RPC | 5s | 1 | 200ms | 30% 错误率/10s |
| 外部 HTTP | 10s | 1 | 500ms | 50% 错误率/30s |
| 数据库查询 | 3s | 0 | - | - |
| 数据库写入 | 5s | 0 | - | - |

## 4. 影响评估

| 影响维度 | 影响程度 | 影响说明 | 缓解措施 |

| 现有代码改动 | 中 | 服务引入 Dubbo 3 依赖、配置调整 | 统一 Starter 封装 |
