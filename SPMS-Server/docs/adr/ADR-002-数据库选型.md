# ADR-002: 数据库选型 - MySQL 8.0 InnoDB Cluster vs 分布式数据库

> **状态**：✅ 已通过
> **日期**：2026-08-01
> **决策者**：后端架构师 + DBA
> **技术栈影响**：后端数据层
> **关联文档**：[数据库选型说明](../Kubo 平台高并发重构实施路线规划计划.md#12-完整技术栈版本表)

---

## 1. 背景与问题

### 问题描述
- 微服务架构需要高可用、高性能的核心交易型数据库 (OLTP)
- 原系统使用 MySQL 单机/主从，无自动故障转移，RPO > 0
- 微服务拆分后需要分库分表、读写分离支持
- 团队对 MySQL 生态最熟悉

### 约束条件
- 团队对 MySQL 生态最熟悉 (开发、运维、SQL 调优)
- 预算有限，倾向开源/社区版方案
- 核心交易数据强一致性要求 (RPO=0)
- 现有数据量单表最大 5000 万行，年增长 20%

### 驱动因素
- 微服务拆分后的数据隔离需求
- 高可用要求 (RPO=0, RTO<30s)
- 分库分表、读写分离需求
- 团队技术栈延续性

---

## 2. 备选方案

### 方案 A: MySQL 8.0 InnoDB Cluster (Group Replication) ✅ **选中**

| 维度 | 评价 |
|------|------|
| **优点** | - 团队零学习成本，生态最熟悉<br>- InnoDB Cluster 原生高可用：单主多从、自动故障转移、RPO=0、RTO<30s<br>- Group Replication 原生多主/单主模式、冲突检测、成员管理<br>- ShardingSphere-JDBC 原生支持 MySQL 分片、读写分离、影子表<br>- 生态最完善：工具链、监控、备份、审计、SQL 审核工具链完善<br>- 成本最低：开源社区版、硬件资源利用率高<br>- SQL 兼容性最好，无语法迁移成本 |
| **缺点** | - 写入扩展性受限于单主 (单主写入 QPS 上限 ~5万)<br>- 单表数据量 > 5亿行性能下降<br>- 跨分片事务复杂 (需 ShardingSphere/应用层协调)<br>- 大表 DDL 锁表风险 (需 gh-ost/pt-online-schema-change) |
| **技术成熟度** | 极高 |
| **团队熟悉度** | 极高 |
| **运维复杂度** | 低 (团队熟悉) |
| **成本** | 极低 (开源) |
| **扩展性** | 中 (读扩展强、写扩展受限) |
| **生态成熟度** | 极完善 |

### 方案 B: TiDB (分布式 NewSQL)

| 维度 | 评价 |
|------|------|
| **优点** | - 原生分布式、水平扩展无上限<br>- 强一致性 (Raft)、自动分片、自动故障转移<br>- MySQL 协议兼容、应用层基本无感迁移<br>- HTAP 能力：OLTP + OLAP 混合负载<br>- 弹性伸缩、在线 DDL 无锁 |
| **缺点** | - 团队零运维经验，学习曲线陡峭<br>- 资源占用大 (3+ TiKV + 3+ TiDB + 3+ PD)<br>- 运维复杂度高 (PD/TiKV/TiDB 多组件)<br>- 成本高 (硬件资源 3-5 倍 MySQL)<br>- 部分 MySQL 语法/函数不兼容<br>- 事务延迟略高 (Raft 复制) |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 (零经验) |
| **运维复杂度** | 高 |
| **成本** | 高 (硬件 3-5 倍) |
| **扩展性** | 极强 |
| **生态成熟度** | 良好 |

### 方案 C: OceanBase / PolarDB-X (云厂商分布式数据库)

| 维度 | 评价 |
|------|------|
| **优点** | - 云厂商托管、运维负担低<br>- 原生分布式、强一致、自动分片<br>- MySQL 兼容性好 |
| **缺点** | - 厂商锁定严重 (阿里云/腾讯云)<br>- 成本高 (商业版 License + 云资源)<br>- 自建部署运维复杂<br>- 版本迭代受厂商控制 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 |
| **运维复杂度** | 中 (托管) / 高 (自建) |
| **成本** | 高 |
| **扩展性** | 极强 |
| **生态成熟度** | 良好 |

### 方案 C: PostgreSQL + Citus / Patroni

| 维度 | 评价 |
|------|------|
| **优点** | - 功能强大、标准 SQL 支持最好<br>- Citus 提供分布式能力<br>- 丰富的数据类型、索引类型 |
| **缺点** | - 团队零 PostgreSQL 经验<br>- Citus 运维复杂、社区版功能受限<br>- 生态工具链不如 MySQL 完善 |
| **技术成熟度** | 高 |
| **团队熟悉度** | 低 |
| **运维复杂度** | 高 |
| **成本** | 低 |
| **扩展性** | 中 |
| **生态成熟度** | 良好 |

## 3. 决策结果

**最终选择**：方案 A - **MySQL 8.0 InnoDB Cluster (Group Replication)**

**选择理由**：
1. **团队零学习成本** - 核心竞争力，开发/运维/DBA 全栈熟悉
2. **生态最完善** - 工具链、监控、备份、审计、SQL 审核、gh-ost/pt-osc 成熟
3. **高可用原生满足** - InnoDB Cluster RPO=0、RTO<30s，满足金融级要求
4. **ShardingSphere 原生支持** - 分片、读写分离、影子表压测无缝集成
4. **成本最优** - 开源社区版、硬件利用率高、无 License 费用
5. **演进路径清晰** - 单表 > 5亿行或写入 QPS > 5万时，再评估 TiDB/OceanBase 迁移

**妥协与风险**：
- 写入扩展性受限于单主 (但 10k 用户场景峰值写入 QPS < 5万，远低于上限)
- 单表 > 5 亿行性能下降 (冷热分离 + 归档应对)
- 跨分片事务复杂 (Seata AT + ShardingSphere 应对)

**缓解措施**：
- 建立冷热分离策略：历史流水归档至 ClickHouse/Doris
- 大表 DDL 使用 gh-ost/pt-osc 无锁变更
- 单表数据量监控告警：> 1 亿行预警，> 3 亿行强制归档
- 预留分布式数据库迁移接口 (抽象 Repository 层)

## 4. 影响评估

| 影响维度 | 影响程度 | 影响说明 | 缓解措施 |
|----------|----------|----------|----------|
| 现有代码改动 | 中 | Repository/Service 适配 ShardingSphere | 统一 BaseMapper、分片键注解 |
| 数据迁移 | 高 | 全量 + 增量双写迁移 | 双写校验脚本、回滚预案 |
| 接口兼容性 | 无 | 内部存储变更 | 无 |
| 团队学习成本 | 低 | 团队熟悉 MySQL | 复用现有知识 |
| 运维复杂度 | 低 | 团队熟悉 MySQL 运维 | 复用现有运维体系 |
| 性能影响 | 正向 | 读写分离提升读性能 | 压测验证 |

## 5. 演进路线图

| 阶段 | 触发条件 | 目标架构 | 时间窗口 |
|------|----------|----------|----------|
| **当前** | 单表 < 5000万、写入 QPS < 5万 | MySQL InnoDB Cluster + ShardingSphere | 当前 ~ 2 年 |
| **Phase 2** | 单表 > 5亿 或 写入 QPS > 5万 | MySQL + ClickHouse (OLAP) + Redis (热点) | 2 ~ 4 年 |
| **Phase 3** | 事务吞吐瓶颈、跨分片事务复杂 | TiDB / OceanBase (核心交易) + MySQL (非核心) | 4 年后 |
