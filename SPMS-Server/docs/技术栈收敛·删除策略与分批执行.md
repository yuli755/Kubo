# 技术栈收敛 · 删除策略与分批执行

> 日期：2026-09-17
> 触发：用户确认目标栈（前端 Vue 3.5 / Vite 7 / TS 5.9 / Element Plus 2.12 / ECharts 6 / Pinia 3 / axios / vue-router 4，
> 后端 Spring Boot 3 / MyBatis-Plus / MySQL / Redis / RabbitMQ），并问「是否先删技术栈之外的技术与代码，然后再修复」。

## 0. 结论：**分三类，不是"一刀切先删"**

| 类别 | 判据 | 处置 | 为什么 |
| --- | --- | --- | --- |
| **A · 死件** | 零引用，或**代码自己声明是空壳** | ✅ **立刻删**（先删后修） | 删掉即消除"看着有、其实不能用"的误导，删除本身就是修复 |
| **B · 承重件** | 被业务代码真实调用（哪怕只有一处） | ⛔ **不能先删**：替换 → 验证 → 删旧 | 先删会让系统失去可运行的中间态，也无法回滚到"哪一步开始坏的" |
| **C · 开发期工具** | 不进产物（测试/lint/构建插件） | 保留 | 它们不是"技术栈外的技术"，删了只会降低质量门槛 |

**为什么承重件不能"先删再修"**：三批瘦身之所以顺利，靠的是每批删完预览还活着、测试全绿，出问题能一眼定位到本批；
如果先把 `@airpower/web`（144 个页面在用）或 JPA（写路径）摘掉，得到的是"全站白屏 + 写不进库"，
此时既没有参照物（旧组件的行为规格是唯一的迁移依据），也没有回滚点（一次改动横跨 200 个文件）。

## 3. 关键路径发现：后端"去 airpower"的第一刀是**脱离 parent**

`pom.xml` 的 `<parent>` 就是 `cn.hamm:airpower:6.4.3` —— Spring Boot 版本、依赖管理、
**Redis**、validation、JPA 全是从它传递进来的（pom 里搜 `redis` **一个字都没有**）。
所以"删掉 airpower 依赖"这件事不可能零散做：一旦去掉 parent，所有传递依赖同时消失。

**脱离 parent 时必须一次性补齐的清单**（按代码实际用量扫描，不是拍脑袋）：

| 能力 | 证据 | 需补 |
| --- | --- | --- |
| Web（`RestController`/`MultipartFile`） | `org.springframework.web` 34 文件 | `spring-boot-starter-web` |
| 校验 | `jakarta.validation` 29 文件 | `spring-boot-starter-validation` |
| **Redis** | `RedisTemplate` 4 文件（令牌吊销/登录防暴破/限流/权限事件） | `spring-boot-starter-data-redis`（**当前是传递依赖，最险的一条**） |
| JPA（过渡期） | `jakarta.persistence` 85 文件 | `spring-boot-starter-data-jpa`（Flyway 后删） |
| 事务 | `org.springframework.transaction` 9 文件 | 由 data-jpa/jdbc 带入 |
| 缓存注解 | `org.springframework.cache` 2 文件 | `spring-boot-starter-cache` |
| 定时任务 | `@Scheduled` 3 文件 | Boot 自带（`@EnableScheduling`） |
| JSON | `com.fasterxml.jackson` 7 文件 | `spring-boot-starter-json`（web 带入） |
| 迁移 | 现在 9 个手工 SQL | **Flyway**（新增） |
| 迁移依赖 | — | `spring-boot-starter-parent`（替换 airpower parent）+ JDK/编码/插件版本显式化 |

**做法**：先新增一个 `pom-airpower-free.xml` 草案与现有 pom 并存评审（不切）；
切换用一个提交完成（parent + 补齐依赖 + 版本显式化），随后 `mvn -q compile` 必须绿 ——
**这一步必须在有 JDK/Maven 的环境做**，沙箱里做不了（无 JDK、Maven Central 不可达）。
