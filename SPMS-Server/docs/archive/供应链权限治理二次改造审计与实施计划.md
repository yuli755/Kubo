# 供应链权限治理二次改造审计与实施计划

> 文档状态：审计版，编码前置基线
>
> 审计日期：2026-08-16
>
> 适用项目：`SPMS-Server`
>
> 目标：在真实代码、真实数据、真实缓存和真实消息链路基础上，逐步建设供应链平台的租户级、行级、列级数据权限体系。

---

## 1. 审计结论

### 1.1 总体判断

本项目具备二次改造价值，但不能按现有规划文档原样实施。当前项目是 **Spring Boot + AirPower + JPA/Hibernate 的模块化单体**，不是已经落地的 MyBatis-Plus 微服务集群。

目标描述中的以下能力目前属于规划方向，而不是已交付能力：

- MyBatis/MyBatis-Plus 行级 SQL 权限拦截。
- RabbitMQ 权限变更事件和缓存广播。
- 本地消息表 Outbox 与定时重试。
- gRPC 权限规则服务。
- AOP + 自定义注解的列级权限脱敏。
- Redis 中版本化权限规则缓存。

本轮不直接编码，先冻结改造边界、数据权限语义、迁移顺序、验收口径和回滚策略。后续编码必须按本文档的阶段门槛推进，不允许以静态页面、假接口、假数据或只隐藏前端按钮作为完成证明。

### 1.2 当前实现证据

| 审计项 | 当前事实 | 结论 |
|---|---|---|
| 应用形态 | `SPMS-Server` 按 `asset`、`factory`、`iot`、`mes`、`wms` 等模块组织 | 当前为模块化单体 |
| ORM | `BaseRepository` 继承 AirPower CURD Repository，实体使用 `jakarta.persistence` 和 Hibernate 注解 | 当前主链路是 JPA/Hibernate |
| 用户模型 | `UserEntity` 通过 `ManyToMany` 关联 `RoleEntity` 和 `DepartmentEntity` | 已有用户-角色-部门基础 |
| 角色模型 | `RoleEntity` 关联菜单和权限 | 已有 RBAC 关系 |
| 权限模型 | `PermissionEntity` 保存权限标识、名称、类型和父级关系 | 主要是菜单/按钮/接口权限 |
| 超级管理员 | `UserEntity.isRootUser()` 当前通过用户 ID 为 `1` 判断 | 需要改为显式系统权限 |
| Redis | 业务通过 AirPower `RedisHelper` 使用 | 有 Redis 基础，但没有权限缓存体系 |
| MyBatis | 源码和 `pom.xml` 未形成现有 Mapper 主链路 | 尚未实现行级 SQL 拦截 |
| RabbitMQ | 源码中没有 Spring AMQP 生产者/消费者 | 尚未实现异步刷新 |
| gRPC | 源码中没有 gRPC 服务或客户端 | 不应在首期直接拆分 |
| 数据库迁移 | 当前 JPA 配置为 `ddl-auto: validate`，仓库没有现成 Flyway/Liquibase 主链路 | 新表和新字段必须先提供可执行迁移方案 |
| 测试 | 当前后端测试以应用上下文和 Redis 行为测试为主 | 缺少数据权限集成测试 |

### 1.3 可行性结论

判定为：**有条件可行，建议分阶段改造，不建议一次性全量切换。**

必须先满足的条件：

1. 先完成数据资源和租户字段盘点。
2. 先定义权限规则的数据模型和默认拒绝语义。
3. 先建立可回滚的数据库迁移和历史数据回填方案。
4. 先迁移少量试点模块，再扩大 MyBatis-Plus 行级拦截范围。
5. 在真实 MySQL、Redis、RabbitMQ 环境完成自动化验证后，才允许生产启用强制拦截。

## 2. 改造目标与非目标

### 2.1 改造目标

#### 目标一：租户级隔离

所有受保护业务数据必须首先按 `tenant_id` 隔离。租户 ID 必须来自已验证的认证上下文或服务端任务上下文，不能只信任请求头或前端参数。

#### 目标二：行级权限

同一张业务表对不同用户返回不同数据范围，支持：

- 当前租户。
- 当前用户。
- 部门及部门树。
- 工厂。
- 仓库。
- 供应商或客户范围。
- 负责人范围。
- 多组 `AND / OR` 条件。
- 显式全量权限。
- 无策略默认拒绝。

行级权限必须同时覆盖：

- 列表查询。
- 详情查询。
- 分页和 `COUNT`。
- JOIN 和子查询。
- 聚合和统计。
- 更新。
- 删除。
- 批量操作。
- 导出。

#### 目标三：列级权限

敏感字段按照用户权限动态脱敏，适用于接口响应和导出，不依赖前端隐藏字段。

第一批候选敏感字段：

- 手机号。
- 身份证号。
- 邮箱。
- 联系地址。
- 采购价格。
- 销售价格。
- 成本价格。
- 员工薪资或绩效信息。
- 设备密钥和第三方凭证。

#### 目标四：权限缓存最终一致

权限变更后，数据库、Redis、本地缓存和各应用实例最终收敛到同一权限版本。需要具备：

- 版本号。
- 变更事件。
- Outbox 记录。
- RabbitMQ 投递。
- 消费幂等。
- 定时重试。
- 死信处理。
- 人工补偿。

#### 目标五：新业务表可复用

新业务表接入权限时，应通过资源注册、字段映射和策略配置接入，不能复制一套新的 Controller 权限判断代码。

### 2.2 非目标

以下事项不作为首期强制目标：

- 不立即把当前模块化单体拆成完整微服务集群。
- 不立即建立独立 gRPC 权限中心。
- 不直接删除所有现有 JPA 代码后再重写全部业务。
- 不把前端编译期裁剪当成安全边界。
- 不把浏览器端 WebSocket “绝对不丢消息”作为验收条件。
- 不在没有真实压测数据时承诺固定 P95/P99 数值。

## 3. 目标架构方向

### 3.1 首期架构

```text
浏览器 / 任务调度
        |
        v
认证与请求上下文
        |
        v
PermissionContext
        |
        +--> PermissionDecisionService
        |          |
        |          +--> 本地缓存
        |          +--> Redis 规则缓存
        |          +--> 本地数据库规则提供者
        |
        +--> 业务 Service
                    |
                    +--> MyBatis-Plus Mapper
                                |
                                +--> DataPermissionInterceptor

业务 DTO / 导出结果
        |
        v
ColumnMaskingAspect + @SensitiveField
        |
        v
响应或导出

权限变更事务
        |
        v
permission_change_outbox
        |
        v
RabbitMQ 权限变更事件
        |
        v
各实例清理本地缓存并刷新规则版本
```

### 3.2 权限内核职责边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| `PermissionContextResolver` | 从认证、租户和任务上下文构造权限上下文 | 不自行信任前端权限范围 |
| `PermissionRuleProvider` | 根据资源、动作、用户和租户加载规则 | 不拼接未经校验的 SQL |
| `PermissionDecisionService` | 判断动作和规则是否允许 | 不直接处理 HTTP 页面按钮 |
| `DataPermissionInterceptor` | 在 SQL 执行阶段注入行级条件 | 不替代接口级鉴权 |
| `ColumnMaskingAspect` | 对 DTO/导出字段脱敏 | 不修改持久化实体原值 |
| `PermissionCache` | 维护权限规则和版本 | 不在缓存故障时放开权限 |
| `OutboxDispatcher` | 投递权限变更事件并重试 | 不绕过数据库事务 |

### 3.3 首期不拆 gRPC 的原因

当前项目没有服务发现、配置中心、熔断、链路追踪和权限服务独立部署能力。首期在单体内定义 `PermissionRuleProvider` 接口，未来可以替换为 gRPC 客户端，但不让业务模块直接依赖远程协议。

这样可以先验证：

- 权限模型是否正确。
- 行级条件是否覆盖真实业务。
- 缓存和失效是否可靠。
- 复杂 SQL 是否可以安全改写。

## 4. 权限数据模型设计

### 4.1 数据资源

`data_resource` 用于声明哪些业务资源受权限保护：

| 字段 | 说明 |
|---|---|
| `resource_key` | 例如 `wms.inventory` |
| `table_name` | 对应数据库表 |
| `table_alias` | SQL 注入时的标准别名 |
| `tenant_column` | 租户字段，默认 `tenant_id` |
| `owner_columns` | 用户或组织归属字段 |
| `supported_actions` | 查询、详情、更新、删除、导出 |
| `status` | 草稿、启用、停用 |
| `version` | 资源配置版本 |

未注册资源不得被权限拦截器默认为全量开放；生产环境应按默认拒绝处理。

### 4.2 数据策略

`data_policy` 保存结构化权限规则：

| 字段 | 说明 |
|---|---|
| `policy_code` | 策略唯一编码 |
| `resource_key` | 资源标识 |
| `action` | 访问动作 |
| `effect` | `ALLOW` 或 `DENY` |
| `condition_json` | 结构化条件树 |
| `priority` | 冲突时的优先级 |
| `status` | 是否启用 |
| `version` | 规则版本 |
| `created_by` | 创建人 |
| `updated_by` | 修改人 |

条件节点首期只允许：

- `TENANT_EQUALS_CONTEXT`。
- `USER_EQUALS_CONTEXT`。
- `FIELD_IN_CONTEXT_SET`。
- `FIELD_EQUALS_VALUE`。
- `ALL_OF`。
- `ANY_OF`。
- `DENY_ALL`。

不允许把请求参数或管理员输入直接拼接成 SQL。

### 4.3 字段策略

`data_field_policy` 保存：

- 资源标识。
- DTO 字段路径。
- 敏感分类。
- 明文访问权限标识。
- 脱敏策略。
- 是否允许导出明文。
- 策略版本。

### 4.4 Outbox

`permission_change_outbox` 至少保存：

- 事件 ID。
- 聚合类型和聚合 ID。
- 变更前后版本。
- 事件负载。
- 投递状态。
- 重试次数。
- 下一次重试时间。
- 最后错误。
- 创建时间和完成时间。

## 5. 分阶段实施计划

### 阶段 0：基线盘点与冻结规则

**目标：** 在不改变业务行为的情况下确定权限边界。

**工作项：**

1. 生成受保护业务表清单。
2. 为每张表标记 `tenant_id`、部门、工厂、仓库、负责人等字段。
3. 盘点所有 JPA Repository 和复杂查询。
4. 盘点详情、列表、统计、导出和批量写操作。
5. 记录当前角色、菜单、接口权限关系。
6. 记录现有 Redis Key 命名和生命周期。
7. 建立越权测试数据集，不使用生产数据。

**阶段产物：**

- 数据资源清单。
- 字段归属矩阵。
- 查询复杂度矩阵。
- 当前权限回归基线。
- 试点模块候选清单。

**通过条件：**

- 每个试点资源都能明确数据归属字段。
- 没有归属字段的表被标记为暂缓接入。
- 所有系统级全量查询都有明确任务身份和审计要求。

### 阶段 1：权限模型与数据库迁移

**目标：** 先把权限数据本身建起来。

**工作项：**

1. 创建资源、策略、主体、字段策略和 Outbox 表。
2. 为试点业务表补充租户字段。
3. 完成历史数据租户归属回填。
4. 增加非空、索引和联合唯一约束。
5. 将超级管理员从“用户 ID 为 1”迁移为显式系统权限。
6. 建立策略版本和变更审计。

**通过条件：**

- 数据库迁移可重复执行或具备明确版本号。
- `ddl-auto: validate` 环境启动成功。
- 历史数据没有空租户或无法解释的租户归属。
- 策略数据可以通过真实 API 创建和查询。

### 阶段 2：权限上下文和策略计算

**目标：** 在不拦截现有业务 SQL 的前提下完成权限内核。

**工作项：**

1. 定义 `PermissionContext`。
2. 定义 `PermissionRuleProvider`。
3. 定义结构化条件表达式。
4. 实现默认拒绝的 `PermissionDecisionService`。
5. 实现本地缓存和 Redis 缓存适配。
6. 增加权限模拟接口，仅供管理员和测试环境使用。

**通过条件：**

- 同一用户在不同租户上下文下得到不同规则。
- 无规则、过期规则和上下文缺失均不会放大权限。
- 规则计算结果可追踪到资源、动作和版本。

### 阶段 3：JPA 到 MyBatis-Plus 垂直迁移

**目标：** 为可靠 SQL 拦截建立统一 Mapper 主链路。

**推荐顺序：**

1. `personnel`：用户、角色、部门、权限基础数据。
2. `system`：菜单、权限、审计和配置。
3. `wms`：库存、入库、出库、移库。
4. `mes`：计划、工单、工艺和领料。
5. `factory`：工厂、仓库和组织结构。
6. `asset`、`iot` 及其他模块。

**每个模块必须完成：**

- Entity/Mapper/Service 映射。
- 事务边界迁移。
- 分页和 COUNT 验证。
- JOIN、统计和导出验证。
- 更新、删除和批量操作验证。
- 原 JPA 写路径下线。
- 模块级回滚方案。

**重要约束：**

不能在同一业务写路径中长期同时使用 JPA 和 MyBatis。可以按模块切换，但不能让两套 ORM 共同维护同一事务语义。

### 阶段 4：MyBatis-Plus 行级拦截

**目标：** 在真实 Mapper 执行阶段实现行级隔离。

**工作项：**

1. 实现 `DataPermissionInterceptor`。
2. 从 SQL AST 识别受保护表和别名。
3. 注入租户条件和业务维度条件。
4. 覆盖 SELECT、UPDATE、DELETE。
5. 验证分页插件和 COUNT 改写顺序。
6. 处理 JOIN、子查询、聚合和批量 SQL。
7. 对未注册表、未知别名、解析失败 SQL 默认拒绝。
8. 提供受控系统任务绕过能力并记录审计。

**通过条件：**

- 不能通过修改请求参数扩大数据范围。
- COUNT 不能统计无权数据。
- 详情、更新、删除和导出不能绕过列表权限。
- SQL 解析失败不会回退到原始全量 SQL。

### 阶段 5：列级脱敏

**目标：** 让响应和导出字段按权限动态脱敏。

**工作项：**

1. 定义 `@SensitiveField`。
2. 定义 `FULL`、`PARTIAL`、`LAST4`、`HASH` 等策略。
3. 在 DTO 输出层执行脱敏。
4. 处理集合、分页、嵌套 DTO 和导出。
5. 明文访问记录审计。
6. 脱敏异常采用安全失败策略。

**通过条件：**

- 没有明文权限的角色在接口和导出中都看不到原值。
- 持久化实体不会被脱敏逻辑污染。
- 脱敏失败不会泄露原始字段。

### 阶段 6：Outbox、RabbitMQ 和缓存一致性

**目标：** 权限变更可以可靠传播到所有应用实例。

**工作项：**

1. 权限变更和 Outbox 写入处于同一数据库事务。
2. 定时投递未发送事件。
3. RabbitMQ 消费端按事件 ID 幂等。
4. 清理本地缓存并递增 Redis 规则版本。
5. 失败事件重试和死信。
6. 增加人工重试和补偿入口。
7. 增加缓存命中、失效延迟、消费失败和积压监控。

**通过条件：**

- 数据库提交成功、消息发送失败时可以补偿。
- 重复消费不产生错误副作用。
- Redis 或 RabbitMQ 故障时不回退全量数据。
- 多实例最终都能获得新权限版本。

### 阶段 7：灰度与生产上线

**目标：** 控制权限改造风险。

**上线顺序：**

1. 观察模式：只记录预期权限条件，不改变查询结果。
2. 对比旧查询与新权限结果。
3. 单资源强制模式。
4. 单模块灰度。
5. 扩大租户和用户范围。
6. 下线旧旁路。

**回滚要求：**

- 回滚开关只能回退到上一版已验证的策略和代码。
- 不允许通过回滚开关恢复无鉴权的全量查询。
- 数据库迁移必须有向前兼容和回滚说明。

## 6. 接口和代码边界

### 6.1 核心内部接口

```text
PermissionContextResolver
PermissionRuleProvider
PermissionDecisionService
PermissionCache
DataPermissionInterceptor
ColumnMaskingService
PermissionChangePublisher
OutboxDispatcher
```

### 6.2 管理接口

后续需要提供真实持久化接口：

- 数据资源管理。
- 行级策略管理。
- 字段策略管理。
- 权限版本查询。
- 权限模拟。
- 权限变更审计。
- Outbox 失败事件查询和重试。
- 缓存刷新状态查询。

所有管理接口必须经过现有接口级 RBAC，并额外执行租户范围校验。

### 6.3 禁止的实现方式

- 只在前端隐藏按钮。
- 只在 Controller 中手写 `if (userId)` 判断。
- 直接把请求参数拼成 SQL。
- 通过异常捕获后放开原始查询。
- Redis 不可用时返回全租户数据。
- 只保护列表、不保护详情和写操作。
- 通过用户 ID `1` 永久绕过所有权限。
- 用静态 JSON 或内存假数据证明权限生效。

## 7. 测试与验收方案

### 7.1 单元测试

- 租户上下文解析。
- 用户、角色、部门、工厂和仓库范围。
- `AND/OR` 条件表达式。
- 无规则默认拒绝。
- 规则版本和缓存失效。
- 字段脱敏策略。
- 事件幂等键生成。

### 7.2 数据库集成测试

使用真实 MySQL 或同等兼容测试环境验证：

- 两租户相同业务表互不可见。
- 部门树范围。
- 仓库范围。
- 分页和 COUNT。
- JOIN 和子查询。
- 更新、删除和批量操作。
- 导出数据范围。
- SQL 解析失败安全拒绝。

### 7.3 缓存与消息测试

- Redis 命中、未命中和过期。
- RabbitMQ 重复消息。
- Outbox 投递失败。
- 定时重试。
- 死信转人工补偿。
- 多实例本地缓存清理。
- 版本落后时强制刷新。

### 7.4 安全验收

- 伪造租户请求头。
- 修改用户 ID 参数。
- 修改部门、工厂、仓库过滤参数。
- 直接调用详情接口。
- 直接调用导出接口。
- 批量更新不可见数据。
- 用户被撤销角色后继续使用旧 Token。
- Redis 故障时尝试读取数据。

## 8. 可观测性和运行要求

至少增加以下指标：

- 权限规则加载成功/失败次数。
- 本地缓存命中率。
- Redis 缓存命中率。
- 权限判定耗时。
- SQL 解析失败次数。
- 权限拒绝次数及原因。
- 明文敏感字段访问次数。
- Outbox 待发送数量。
- RabbitMQ 重试数量。
- RabbitMQ 死信数量。
- 权限版本传播延迟。

日志中不得记录密码、Token、身份证原文、手机号原文或其他敏感值。
