> 状态：已实证并落地两项（terser `keep_fnames` -29.7 KB、airpower CSS 剥离 -34.6 KB），
> 总体 895.8 → 831.5 KB（-64.3 KB）。echarts / element 经复核确认已近下限，暂不动。
> 数据来源：`pnpm build` + `pnpm size` 实测（gzip，level 9）。基线为本文档落地前的 895.8/900 KB。

## 二、已实证并落地：去掉 terser `keep_fnames`（-29.7 KB）

### 问题

`vite.config.mts` 的 terser 同时保留了**类名**（`keep_classnames`）和**函数名**（`keep_fnames`），注释写「保留类名以兼容 airpower 反射机制」，但两者被无差别保留。

### 排查

airpower 反射的真实依赖点（`@airpower/web/dist/main.js`）只有 class-transformer 的：

```js
if (!SuperClass || SuperClass.prototype.constructor.name === Transformer.name) { ... }  // 共 4 处
```

即「类名字符串比较」，依赖的是**类名**。项目 `@Type(Entity)` 装饰器全用**类引用**（非字符串）。据此判断：**类名必须保留，函数名对反射无意义**。

### 对照实验（分离两个参数的贡献）

| 配置 | 总体 | 首屏 |
|------|------|------|
| 基线（两者都保留） | 895.8 KB | 414.4 KB |
| 都去掉 | 864.4 KB | 400.0 KB |
| **只去函数名（保留类名）** | **866.1 KB** | **400.5 KB** |
| 只去类名（保留函数名） | 893.7 KB | 413.9 KB |

结论：`keep_fnames` 贡献 ≈ **29.7 KB**，`keep_classnames` 贡献仅 ≈ 2.1 KB。

### 落地

```ts
terserOptions: {
  compress: { keep_classnames: true, keep_fnames: false },
  mangle:   { keep_classnames: true, keep_fnames: false },
}
```

**安全性**：保留 `keep_classnames` ⇒ 类名原样输出 ⇒ `constructor.name === Transformer.name` 比较完全不变 ⇒ class-transformer 反射不受影响。196 单测全绿。

## 三、候选方向（按「收益 × 确定性 / 风险」排序）

### 1. airpower 整包 CSS 剥离（-34.6 KB）｜✅ 已落地

- 深挖发现：`web.css`（378 KB 未压缩 / 52.2 KB gzip）**92% 是 element-plus 全量样式**（341 KB），
  airpower 自身 `.a-*`/`.web-*` 仅 26 KB。该全量样式与项目按需引入的 vendor-element.css
  大面积重复，且大部分是项目/airpower 都用不到的组件。
- 落地：新增构建期插件 `infra/plugins/airpower-css-strip.ts`，白名单剥离——仅保留：
  - airpower 自身样式（`.a-*`/`.web-*`/`data-v`/过渡/keyframes/`:root` 变量）；
  - airpower 独用 el 组件（vendor-element.css 未覆盖，须保留）：`el-table`/`el-menu`/
    `el-image`/`el-upload`/`el-pagination`/`el-popover`/`el-check-tag`/`el-cascader`
    （含子组件 `el-sub-menu`/`el-pager`/`el-table-column` 等）。
  删除与 vendor-element.css 重复的 element 组件样式。
- 正确性依赖（已核验）：airpower 独用组件的内部依赖（el-scrollbar 滚动/el-checkbox 多选/
  el-tooltip 列头提示/el-popper 弹层）均为项目直接使用的组件，样式由 vendor-element.css
  提供；airpower 引用的 `--el-menu-hover-bg-color` 等独用变量仅定义于 web.css `:root`，故
  `:root` 整体保留。
- 收益：vendor-airpower.css 49.6 → 14.9 KB（-34.7 KB）。
- **遗留**：视觉正确性需本机浏览器回归（表格/菜单/图片/上传/分页/弹层/级联选择）。

### 2. echarts（179 KB 懒加载）｜复核确认已近下限

- 注册面已最小：`BarChart/LineChart/PieChart` + `Grid/Legend/Tooltip` + `CanvasRenderer`，
  每项均被 2 处消费者实际使用；动态 import 懒加载，不影响首屏。
- 进一步只能换库（uCharts / 自绘 SVG，工作量大、风险高）或去掉 Legend/Tooltip（几 KB，
  损害交互）。
- 建议：**暂不动**。除非 total 再次顶破且无更优选择。

### 3. element-plus（168.8 KB）｜复核确认按需已穷尽

- aggregate.ts 按需 re-export 的组件逐一比对项目 `.vue` 标签 + 命令式 import + airpower
  依赖，**无「引入但未使用」的冗余**；`ElTable/ElDatePicker/ElSelect/ElTree` 等重型组件
  均为业务必需。
- 建议：**暂不动**。

### 4. airpower JS（107.3 KB）｜依赖上游

- `@airpower/web` 的 `package.json` `sideEffects` 未声明（非 `false`），Rollup 无法树摇其未用模块（如 MQTT/AI 前端、二维码等）。
- 除非 airpower 上游改为按模块 ESM 导出 + `sideEffects: false`，否则前端侧无解。
- 建议：**记录为上游诉求**，前端不动。

### 5. 首屏 vendor 拆懒加载（潜在省 50~100 KB 首屏）｜中期机会

- 首屏闭包里 element 168.8 + airpower 107.3 = 276 KB，而登录页实际只需其中一小部分（AFrame/ADialog + ElButton/ElInput/ElForm）。
- 若把 `ATable/ElTable/ElDatePicker/ElSelect/ElTree` 等「管理页重组件」拆到懒加载 chunk，首屏可显著下降。
- 障碍：airpower 是单体 dist，`ATable` 与 `ADialog` 同在一个文件，无法按组件懒加载；element 侧可按需拆，但会引入 chunk 碎片化与「公共依赖重复」风险。
- 建议：**首屏当前 400.5/450 未超预算（余 49.5 KB）**，等首屏逼近红线再启动。

## 四、落地顺序建议

1. ✅ **keep_fnames**（已落地）：-29.7 KB，总体 895.8 → 866.1。
2. ✅ **airpower CSS 剥离**（已落地）：-34.6 KB，总体 866.1 → 831.5（92.4%），
   累计较基线 -64.3 KB，腾出约 68 KB（≈6 个模块页）。
3. 保持 `pnpm size` 门禁观测：总体在 880 KB 打预警，不等到 900 顶破再决策。
4. 真正需要再压缩时，按「风险从低到高」依次评估：首屏 vendor 拆懒加载 → echarts 换库
   → airpower JS 上游诉求。

## 五、口径提醒（不临时改数）

`check-bundle-size.mjs` 头部已写明：首屏预算 450 KB 是红线（影响真实加载体验）；total 900 KB 是退化预警（含全部懒加载分包，管理端每加一页 +5~15 KB 是预期增长）。本次 keep_fnames 是「压缩」而非「加预算」，符合脚本口径。
