结论

该规划具备二次改造价值，但不建议原样执行。综合当前仓库、后端实现和规划文档，建议判定为：

> 有条件可行，建议先修订架构假设，再分阶段实施。

当前前端技术栈本身不存在必须推倒重来的问题，真正风险集中在：协议和后端架构假设不一致、性
能指标缺少边界、请求与实时数据模型尚未统一、权限和数据契约仍未完全闭环。

一、规划中需要立即修正的问题

- 文档假设后端已经是 kubo-{domain} 微服务集群，但当前 SPMS-Server 仍是按业务模块组织的单
  体 Spring Boot 应用，包含 asset、factory、iot、mes、wms 等模块，并非已经落地的微服务集
  群。

- 文档同时出现“自定义 WebSocket 协议”和“STOMP over WebSocket”两种方案；当前后端依赖     
  airpower-websocket，前端实现的是原生 JSON 帧、PING/PONG、查询参数 Token，并不是       
  STOMP。

- “10,000 msg/s 无丢包”不能作为浏览器端单一 SLA。浏览器无法保证进程崩溃、断网或后台挂起
  期间绝对不丢消息，必须改成“服务端可持久化、客户端可确认、可重放、业务最终一致”。

- FCP < 1.2s、TTI < 2s、全站 gzip <800KB 等目标过于绝对，应按首页、控制台壳、业务页面分
  别设定，并以 P75/P95、网络环境和设备等级为前提。

- PWA 的 API NetworkFirst 缓存不能直接用于库存、订单、设备状态等强一致数据，否则可能展示
  过期数据甚至产生错误操作。

- “所有列表页迁移到 Vue Query”不应作为架构验收条件。当前大量页面依赖 AirPower 的实体、表
  格和请求生命周期，应该按模块渐进迁移。

- “权限编译期裁剪”不适合当前后端动态菜单权限模式。权限必须以后端菜单、接口鉴权和运行时权
  限数据为事实来源，前端只能负责展示优化。

├─ WebSocket Manager：连接、心跳、重连、订阅、限流

│

API Gateway / BFF                                                                       
├─ 认证与 Token 校验

建议先采用模块化单体 + 可拆分边界，不要一开始就拆成微服务。只有在以下条件满足后，才考虑
独立拆分模块：

- 模块拥有稳定的领域边界；
- 数据库表和事务边界已明确；
- 独立部署有实际收益；
- 已具备链路追踪、配置中心、服务发现、限流和灰度能力；
- 有针对该模块的容量和故障隔离需求。

三、前端建议的落地分层

1. 基础层
    - 保留 Vue、Pinia、AirPower、Element Plus。
    - 继续使用现有 Vite 分包、Terser、PWA 和 Vue Query。
    - 将请求、权限、WebSocket 通过 Adapter 封装，避免直接替换 AirPower 核心能力。

2. 请求层
    - 统一处理超时、取消、重复请求、错误码、401、403、429 和网络离线。
    - GET 查询可以重试；新增、修改、删除默认不自动重试，除非请求带幂等键。
    - 搜索请求使用 AbortController 取消前一个请求。
    - 分页、排序、筛选参数必须使用生成类型，禁止用宽泛 any 兜底。
    - Vue Query 先用于高频查询和监控数据，不直接改造所有 AirPower CRUD 页面。

3. 实时层
    - 当前协议建议继续使用 AirPower 原生 JSON WebSocket，先不要引入 STOMP。
    - 协议至少补充：
        - connectionId
        - messageId
        - eventVersion
        - serverTime
        - sequence
        - ack
        - resumeFrom
        - ttl

    - 消息按优先级处理：
        - P0：安全、停机、严重报警，不丢失，支持确认；
        - P1：设备状态、生产异常，可合并和覆盖；
        - P2：普通日志、统计刷新，可丢弃或批量处理。

    - 浏览器切后台时降低心跳和订阅频率，恢复前台后执行增量同步，而不是无条件补发全部消  
      息。

    - 后端必须提供“事件重放或状态快照接口”，WebSocket 只能作为实时通知通道，不能作为唯一
      数据源。

4. 状态层
    - Global Store：登录用户、当前租户、工厂、权限加载状态。
    - Feature Store：编辑器草稿、弹窗状态、局部筛选。
    - Vue Query：列表、详情、统计、监控快照。
    - 禁止把接口返回的大量列表长期持久化到 Pinia 或 LocalStorage。

5. 权限层
    - 后端菜单和权限接口是唯一事实来源。
    - 动态菜单加载时把后端权限标识写入 route.meta.permission。
    - 写操作统一使用 v-permission 或现有 AirPower 权限能力。
    - 权限加载失败必须 fail-closed：隐藏写操作、阻止敏感操作，并显示恢复入口。
    - /403、菜单缺失、权限过期、登出清理和后端 403 需要统一回归测试。
    - 前端权限始终只是 UX 控制，不能代替后端接口权限和数据权限。

四、后端必须配套的关键设计

- 租户隔离：所有业务查询必须显式带租户和工厂上下文，不能只依靠前端传参。
- 幂等性：新增、入库、出库、审核、提交、撤销等命令使用 Idempotency-Key 或业务单号去重。
- 消息一致性：采用 Outbox 或可靠消息表，避免数据库提交成功但 RabbitMQ 消息丢失。
- 缓存策略：
    - Redis 只缓存可重建数据；
    - 权限、菜单、配置需要版本号或主动失效；
    - 库存、订单状态不能只依赖缓存作为最终事实。

- 数据库扩展：
    - 先做索引、慢查询、分页和归档；
    - 再评估读写分离；
    - 最后才考虑分库分表；
    - 不建议在业务模型未稳定前直接引入 ShardingSphere。

- 可观测性：
    - 前端请求 ID 与后端 Trace ID 贯通；
    - 记录接口耗时、错误码、重试次数、WebSocket 重连次数、消息积压；
    - 业务指标和技术指标分开监控。

- 限流与降级：
    - 登录、导出、报表、设备监控和 WebSocket 连接分别限流；
    - 导出和大报表改成异步任务；
    - 监控页面支持降采样、暂停刷新和手动恢复。

五、建议修订后的实施阶段

阶段 0：两周基线与契约冻结

- 记录真实构建包体积、FCP、LCP、TTI、API P95、WebSocket 连接数。
- 确认当前 WebSocket 协议，不在 STOMP 和自定义协议之间并行建设。
- 统一错误码、分页结构、权限模型和租户上下文。
- 生成 OpenAPI 类型并建立 Breaking Change 检查。
- 确认压测环境、测试数据量和回滚方式。

阶段 1：三至六周基础能力

- 完成 Request Gateway。
- 完成 WebSocket Manager 的心跳、重连、订阅恢复和消息优先级。
- 完成动态菜单、路由权限和按钮权限统一。
- 先迁移设备监控、库存查询、订单查询等高频页面到 Vue Query。
- 建立统一 loading、empty、error、forbidden 状态。

阶段 2：四至六周性能专项

- 大表格按页面实际数据量决定是否虚拟滚动。
- 图表先做聚合、降采样和时间窗口限制，再考虑 Web Worker。
- WebSocket 先做批量合并和页面级订阅，再做 Worker 化。
- PWA 只缓存静态资源和明确允许缓存的只读数据。
- 对导出、报表和大批量操作改为异步任务。

阶段 3：三至四周质量和灰度

- Playwright 覆盖登录、刷新、动态菜单、403、权限过期、重试和重复提交。
- 建立 API 契约测试、WebSocket 协议测试和数据权限测试。
- 进行单租户、单工厂、多租户和高峰时段压测。
- 灰度发布并保留旧页面或旧请求路径作为回滚通道。

整体周期建议从原文的 14 周调整为16 至 20 周，且前 6 周不应以“全量迁移完成”为目标。

最终建议

保留原规划中的技术方向：Vite 构建优化、Vue Query、请求网关、WebSocket 管理、权限统一、虚
拟化和可观测性；但应将其调整为：

> 模块化单体优先、协议先冻结、契约先行、查询渐进迁移、实时消息可恢复、缓存默认保守、以实
> 测指标驱动拆分。

不建议当前立即搭建完整 Monorepo 多包体系、切换 STOMP、全面迁移所有列表页或拆分微服务。这
些工作会增加结构复杂度，却不能直接解决当前最重要的稳定性、权限一致性和数据契约问题。
