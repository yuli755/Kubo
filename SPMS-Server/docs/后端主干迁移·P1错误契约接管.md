## 本轮生产改动

- `framework/error/ErrorCode`、`BusinessException` 只依赖 JDK；异常不继承旧 ServiceException。
- `Errors` / `CustomError` 使用自持契约，不再 import/implement 旧 IException。常量、code、默认文案、key/label getter 保留。
  保留实际使用的 when/show/比较/空值行为；不复制无人使用的一整套接口。
- 错误枚举文案改为不可变，删除仓内没有调用方的共享 setMessage，定制消息只作用于当次异常。
  保留 Supplier 旧角色：Errors.get() 新建空 500 异常，CustomError.get() 返回自身。
- `ApiResponse` 自持 code/message/data/可选 traceId，响应不可变，不承担 JSON 文本解析。
- `BusinessExceptionAdvice` 在旧通用 Exception 兜底之前处理自持异常，保持 **HTTP 200 + 业务码**，不会把 401/403/200001 塌缩为 500。
- `DataIntegrityViolationAdvice` 返回自持响应，保留数据库冲突分流；cause 链增加身份集合，避免异常循环导致无穷遍历。
- FileService 抛自持异常；UserController 的登录 catch **同时接受 BusinessException 与旧 ServiceException**，失败计数与原异常重抛都保留。
- 项目显式声明 BOM 管理的 Lombok provided 依赖；本项目自己的编译期处理器不再寄托于旧依赖的 provided 传递。

## 为什么保留一个旧响应桥

核对固定 `c07a6bd3f4d7` 的 CurdResponseInterceptor：它对所有返回值执行 advice，但**只有 body 是旧 Json 时**，
才进行 RootModel 白名单/脱敏和 body traceId 处理。直接把响应改成普通 POJO 会绕过这段逻辑。

因此 `common/compat/LegacyApiResponseBridge` 以最高优先级注册，只接受 ApiResponse + Jackson 消息转换器，
把 code/message/data/traceId 明确转换为旧 Json，再交给现有过滤链。它不在自持 framework 包内，旧依赖如实计数。
保留原 data 引用、旧控制器和权限拦截；文本、下载、OpenAPI Map 不被包裹。这是暂留适配点，不是伪装成已删净。
