# 前端技术栈收敛与视觉焕新方案（2026-09-17）

> 触发背景：使用方反馈「**需要焕然一新的感觉，但没效果**」「**技术栈太多太杂，不好维护、不好统一处理**」。
> 本文不是复述既有文档，而是对 HEAD `936bf64` 做**实测盘点**（import 统计 / 文件计数 / 依赖树）后给出的
> 「该删什么、该换什么、按什么顺序换」的决策方案。所有数字均可在本地 `grep` 复现。

---

## 0. 结论先行（TL;DR）

1. **技术栈版本不旧**：Vue 3.5 / Vite 7 / TS 5.9 / Pinia 3 / TanStack Query 5 / Element Plus 2.12 / Vitest 4
   全部在 2026 年的当前主力档位。**「杂」不来自版本，而来自「并存轨道」**——同一件事有 2–3 套做法同时活着。
2. **「看不出变化」的根因已定位**：页面外观 100% 由 `@airpower/web` 的三件套决定：
   `AFrame`（壳：顶栏/侧栏/菜单）+ `ATable`（列表）+ `AFormField + getFormConfigList(Entity)`（元数据驱动表单）。
   **只要这三件套还是 airpower 的默认皮肤，底层无论怎么重构，视觉都不会动一个像素。**
3. **要「焕然一新」，最省钱的杠杆是「换壳」，不是「换框架」**：自研 `KAppShell` + `KDataTable` + 显式表单 schema，
   **不动任何依赖**即可拿到约 80% 的观感变化，工作量 0.5–1 天。
4. **真正该被替换的旧选型只有一个**：`@airpower/web` 及其配套的 `src/model/**Service` 类继承体系
   （`AbstractCurdService` ← `src/base/AbstractBaseService`）。其余全是「死包删除 + 目录合并」级别的清理。
5. 推荐分期：**P0 视觉焕新（0.5–1 天，立刻可感知）→ P1 去重治理（2–3 天）→ P2 数据层单轨（1–2 周）
   → P3 UI 层去 airpower（2–4 周）→ P4 删依赖收尾。**

## 2. 「杂」到底杂在哪：7 条并存轨道

| # | 轨道 | 现状 | 为什么难维护 |
| --- | --- | --- | --- |
| 1 | **UI 双轨** | `@airpower/web` 的 A 系列（278 文件）与原生 `<el-*>`（17 种组件、数百处）在同一张页面里混用 | 同一件事（表单、表格、弹窗）两套写法、两套样式来源，改样式要改两处 |
| 2 | **数据三轨** | `src/api/**`（typed client）← → `src/model/**Service`（airpower class Service）← → `src/hook/**`（门面转发） | F3「147 → 0」是把「视图直连 Service」改成了「hook 转发 Service」（`src/hook/wms/useInput.ts` 里仍写着 `export { InputService } from '@/model/...'`），**旧层没删，只是被门面挡住了** |
| 3 | **Hook 双目录** | `src/hook/**`（47）与 `src/composables/**`（20）职责重叠，命名也不统一 | 新人不知道新 hook 该放哪；同域逻辑被拆到两处 |
| 4 | **代码生成双计划** | `packages/api-client`（死包）+ `infra/scripts/generate-api.mjs`（输出到被 gitignore 的 `src/api/generated`，从未跑通） | 两条路线都停在半路，谁也没生效；typed client 目前是**纯手写** |
| 5 | **表单协议被装饰器绑死** | `AFormField v-for="item in getFormConfigList(CustomerEntity)"`：表单字段、顺序、校验、控件类型来自 Entity 上的 `@Field` **运行时元数据** | 业务无法自主控制表单布局（分组、栅格、联动）；换 UI 库 = 重写全部 47 个表单 |
| 6 | **工具层重叠 + 兼容补丁** | airpower 的 `DateTimeUtil/getFieldLabel/WebColor/WebEnum` 与自研 `src/utils/**` 并存；`src/utils/airpowerCompat.ts` 是**复刻 airpower localStorage key** 的兼容层 | 已经在给 airpower 打补丁（首屏不引 airpower，但要让懒加载的 airpower 组件仍能读到 `Authorization` / `permissions`），这是明确的技术债信号 |
| 7 | **通信双轨** | `src/websocket/WebSocketManager.ts`（371 行）+ `src/hook/useWebSocket.ts` + `src/hook/usePolling.ts` | 实时通道三种接入方式，行为与重连语义不一致 |

## 3. 该删 / 该换 / 该留（直接回答「替换哪些旧的技术选型」）

### 3.1 保留（不要动，迁移成本 ≫ 收益）

| 选型 | 版本 | 结论 |
| --- | --- | --- |
| Vue | 3.5 | 保留（`<script setup>` + Composition API 已是现代范式） |
| Vite | 7 | 保留（含 PWA、按需组件、体积预算，工程化水平高） |
| TypeScript | 5.9 `strict` | 保留 |
| Pinia | 3 | 保留（+ 自研 persist 插件可用） |
| vue-router | 4 | 保留（后端菜单驱动的动态路由） |
| **TanStack Vue Query** | 5 | **保留并扩为唯一服务端状态入口**（P2 的目标） |
| **Element Plus** | 2.12 | **保留**（换 UI 库不产生「焕新感」，且要重写 47 表单） |
| ECharts / Vitest / ESLint 9 / Sass | 6 / 4 / 9 / 1.10 | 保留 |

> 一句话：**换 Vue / Vite / Element Plus 是无效动作**——它们不是「杂」的来源，也不改变观感。

### 3.3 为什么「换壳」就能立刻焕然一新

现在的页面只有 5 个组成部分，全部来自 airpower：

```
AFrame（顶栏 + 侧栏 + 菜单）        ← 决定「第一眼」观感
  └─ APanel（卡片容器）
       └─ ATable（列表：工具栏 + 表格 + 分页 + 操作列）
            └─ ADialog → AFormField v-for getFormConfigList()（编辑弹窗）
```

**观感 = 这五件的默认样式之积。** 所以：

- 换 `KAppShell` → 顶栏高度/布局、菜单配色、面包屑、用户区、深浅色**全站同时变**，而**业务页零改动**；
- 换 `KDataTable` → 表格密度、斑马纹、悬停、工具栏按鈕、分页器、空态**一次统一 69 个页面**；
- 两者叠加即可交付「换了个系统」的观感，且**不触碰数据层**，风险最低。

建议的视觉方向（三选一，等拍板）：

| 方向 | 参考气质 | 特征 | 适配度 |
| --- | --- | --- | --- |
| **A · 现代企业风** | Linear / Vercel | 大留白、细边框、圆角卡片、强调色克制、默认浅色 + 深色一键切 | 通用性最好，推荐 |
| **B · 数据密集型** | Ant Design Pro | 深色侧栏 + 浅色工作区、紧凑行高、状态色语义强 | 最贴合 MES/WMS 的高信息密度 |
| **C · 轻量卡片风** | Notion / 飞书 | 大量卡片分组、弱分隔线、圆角偏大 | 看板类页面好看，列表页偏松散 |

## 4. 分期路线（含验收口径）

| 阶段 | 目标 | 动作 | 产出 | 工作量 | 风险 | 验收 |
| --- | --- | --- | --- | --- | --- | --- |
| **P0** | 立刻可见的焕新 | 品牌 token 定稿 → `KAppShell` → `KDataTable` 样板（列表页 3 个）→ 深色默认值 | 全站新壳 + 3 个样板页 | **0.5–1 天** | 低（不动数据层） | 手动点验 + `pnpm lint:ci && pnpm typecheck && pnpm test` |
| **P1** | 去重治理 | 删 `packages/api-client`；`composables` → `hook`；api codegen 二选一（建议留 codegen，删死包）；`useWebSocket` 统一到 `WebSocketManager` | 目录与依赖树干净 | 2–3 天 | 低 | `pnpm check`（10 个门禁脚本）全绿 |
| **P2** | 数据层单轨 | `src/model/**Service` → `src/api/**` + vue-query；`X-Tenant-Id` 下沉 axios 拦截器；`useTanStackTable` 改为 `KDataTable` 内聚 | 删 48 个 Service 的 CRUD 职责 | 1–2 周 | 中（46 处表格） | vitest 289 例（31 文件，本轮实测全绿）+ 逐域回归；`auth:check` / `perms:check` 门禁 |
| **P3** | UI 层去 airpower | 表单协议从装饰器元数据 → 显式 schema；`ADialog`/`ASelector`/`FeedbackUtil` 替换 | 47 表单 / 77 弹窗 / 24 选择器 | 2–4 周 | 中高 | 按域分批，每批 CI 绿；体积预算不超标 |
| **P4** | 收尾 | 移除 `@airpower/web` 依赖、`src/base`、`airpowerCompat.ts` | 依赖树只剩主流库 | 2–3 天 | 低 | 入口体积下降（airpower 首屏闭包约 107 KB + 26 个 EP 组件 168 KB） |

**推进原则（建议拍板）**：**「新页面用新体系，老页面按域分批迁」**——不做大爆炸式重写。
MES/WMS 业务页有 47 个元数据表单 + 69 个表格，一次性重写必然引入业务回归；按域（wms → mes → channel → asset → system）分批最稳。

## 5. 护栏与风险

1. **后端零改动**：前端换层不影响 `/api` 契约；`Authorization` / `X-Tenant-Id` 已可由 `src/api/axios.ts` 承担。
2. **现成护栏**：CI 三 job 全绿 + 8 个自研门禁（`perms/auth/text/ddl/migration/monitoring/drill/size`）+ vitest
   **289 例 / 31 文件**（本轮本地实测全绿，21.6s）可直接用作每期回归验收，**不需要新建测试体系**。
3. **体积只会变好**：删掉 airpower 反而腾出首屏预算（现入口预算 450 KB / 总量 900 KB gzip）。
4. **不要同时换 UI 库**：Element Plus 是当前唯一 UI 底座，与 Token 层已打通（`styles/tokens.scss` 映射了 `--el-color-*`）；
   换 naive-ui / antdv 只会把 47 表单重写两遍。
5. **P0 与 P3 解耦**：换壳不依赖去 airpower，可以先把观感拿到手，再慢慢还技术债。
