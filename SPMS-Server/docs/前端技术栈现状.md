## 六、怎么删：三种性质的区分（决定顺序的是"有没有替代品"）

「先删还是先补」不是风格问题，而是**被依赖关系决定的**。按"删掉它之后还会不会有人需要这个能力"分三类：

| 性质 | 判据 | 现在有什么 | 怎么做 |
| --- | --- | --- | --- |
| **A. 纯删**（无消费者） | 全仓没有任何 import / 路径引用 | 已是 0（两道门禁 + `pnpm stack` 的死重量检查共同守着）；本轮清掉 3 个零引用 devDeps 与 10 张死图标 | 立刻删，`deadcode:check` / `exports:check` 保证不回潮 |
| **B. 边删边补**（有替代品，但替代品要先写） | 能力还在用，只是换了实现 | **大部分**：airpower 120 个文件（批 4 后）、各域 `src/api/*` typed client、`useTanStackTable`、`BaseEntity`/`AbstractBaseService` | 按域分批（F4）：同一批里**先补**（新页 + 框架层件）**再删**（旧页 + 旧服务 + 旧装饰器），一批一提交，可单批回滚 |
| **C. 先补才能删**（缺口卡着一片） | 想删的东西依赖一个**还不存在的**组件 | ✅ 已清零：上传组件已在 2026-09 补齐（`KUpload` + `UploadUtil` + `DialogUtil.showUpload`），批 0B 的单据表单件与 `UserCard`/`component/user/*` 已解锁，合同"参与方/附件"与 wms/channel 的编辑器可随批推进重建 | 补 1 件 → 解锁 3 处（0B、合同参与者/附件、后续两域） |

结论：**能纯删的已经删了；剩下的大头不能"先删"**（删了页面就没人渲染、删了服务就没数据），只能在域迁移里边删边补；
唯一值得插队的"先补"是上传组件。判断某次清理属于哪一类，跑一遍 `pnpm stack` 看"死重量"栏 + 该模块的消费者列表即可。

> 详见 F4 文档 §3.4b。教训写在门禁本身里：**「跑过了」不等于「检查了」**，扫描器必须能区分"没扫到东西"和"扫到东西且没问题"。

## 九、清理这两轮留下的"防复发"机制

死代码是**换底座期间最容易堆积、又最难被发现**的一类：文件不被 import 就不进 bundle，
体积门禁、类型检查、单元测试都看不见它。所以两轮清理都不是"手工删一遍"，而是先做工具：

1. **判定靠编译器，不靠正则**：导出级扫描用 TypeScript 的 parser 与 AST（多行 import、别名、
   重导出、`import type`、内联 `import('@/x').Foo`、动态 import 解构都能正确识别），
   并且认**路径字符串**——`vite.config.mts` 把 `element-plus` 别名指向的
   `src/types/element-plus-aggregate.ts` 就是这样保住的（第一版误报它是死件，删了打包直接崩）。
2. **保护"看起来没人用、其实在用"的三类**：`src/framework/**`（对外契约面）、`*.d.ts`
   （环境/生成的全局声明）、**被测试以文本引用的名字**（`maskContract.spec.ts` 会把源码
   当字符串读，检查 `export interface EnforceReadinessCheck {` 那一格不许空着 —— 这一条是被真实
   的测试失败教出来的）。
3. **自动清理带自检**：`prune-unused-exports.mjs` 每轮只做一种编辑（偏移不错位）、
   删完顺带清掉因此变成孤儿的 import、写盘前用 TS 重新解析一遍，**解析不过就不写**。
4. **两道门禁进 CI**：`deadcode:check` + `exports:check` 都在 `pnpm check` 链里，
   新增死代码会在提交前失败，而不是等下次"清扫"。
5. **依赖层也有人守**：`pnpm stack` 的"死重量"栏把「没有任何引用的依赖」「`public/` 里没人用的资源」
   一起报出来（本轮就是靠它发现 3 个零引用 devDeps 与 10 张死图标的）；`pnpm airpower` 报退场进度。
   两个都是**度量**（不阻塞提交），但每批迁移后跑一次，数字写回本文。
6. **删不掉的，把「为什么不能删」写进代码里**（第三轮的教训）：这一轮有一批"看起来零引用"的东西
   其实是**在别处被消费**——`tokens.scss` 的 17 条 token 是「先被映射成 `--el-*`、再由 Element Plus
   组件内部读」+「token 之间互相引用」+「亮/暗成对」，照"grep 不到就删"清一遍就是主题漂移。
   处置方式不是记在文档里（下一个人读不到），而是写在**文件头**：`src/styles/tokens.scss` 顶部
   现在直接写明三类消费路径与"已审计、全部保留"；`src/types/element-plus-aggregate.ts` 写明
   "从聚合入口 import 的组件都会进首屏"这个代价。同理，本轮还修了 3 处**过期注释**
   （`KUnitService`/`UnitEntity`/`useUnit` 仍在解释已被删掉的 `UnitSelector`、`UnitService`）——
   注释过期和文档过期一样会误导迁移，属于同一种债。
