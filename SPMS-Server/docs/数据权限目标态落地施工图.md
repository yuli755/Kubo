## 1. 目标态：能力 → 载体 → 验收证据（逐条对齐，防止"文档级完成"）

| # | 目标能力 | 实现载体（本项目具体位置） | 完成证据（必须可演示） |
|---|---|---|---|
| C1 | 查同一张表，不同角色看到不同行 | `data_permission` 三表 + MyBatis `DataPermissionInterceptor` + `KuboDataPermissionHandler`，按 `mappedStatementId → resourceKey` 解析 | 真实 MySQL：同 SQL、不同 Token，行数不同；`total` 与列表条数一致 |
| C2 | 看不到无权限的敏感字段 | `@SensitiveField` + `ColumnMaskingAspect` → **序列化层** `SensitiveValueSerializer` + `ConcurrentHashMap` L1 + Redis L2 | 无权限角色接口/导出均为脱敏值；**落库原值不变**（断言测试） |
| C3 | 不改业务代码，新表可直接复用 | 约定优于配置：实体继承 `TenantEntity` + `@DataResource(key, alias)`；启动期扫描自动注册资源；Mapper 统一继承 `KuboBaseMapper<T>` | 新增一张表**只写 Entity+Mapper+XML**，行级/列级/租户全部生效（用 `demo_scope` 表做 CI 回归用例） |
| C4 | 多组 AND / OR 灵活组合 | `data_policy.condition_json` 结构化条件树（`ALL_OF`/`ANY_OF`/`TENANT_EQUALS_CONTEXT`/`USER_EQUALS_CONTEXT`/`FIELD_IN_CONTEXT_SET`/`FIELD_EQUALS_VALUE`/`DENY_ALL`）→ JSqlParser AST 拼接 | 单测：3 层嵌套 AND/OR 生成的 SQL 文本快照 + 执行结果 |
| C5 | 兼容分页 / COUNT / JOIN | MyBatis-Plus `PaginationInnerInterceptor` **置于数据权限拦截器之后**；`data_resource.table_alias` 驱动带别名注入；`SELECT … JOIN` 与子查询逐个走 AST | COUNT SQL 与列表 SQL 改写结果一致；带 JOIN 的统计接口结果 = 手工 SQL 对拍 |
| C6 | Redis 缓存规则、降低远程调用开销 | `PermissionRuleProvider` 三级：Caffeine/`ConcurrentHashMap`(L1) → Redis(L2) → gRPC/DB(L3)；key = `dperm:{tenant}:{resource}:{action}:{ver}` | 命中率指标 ≥ 99%；关停 gRPC 后接口仍可用（回源 DB）；P95 加时 < 3ms |
| C7 | 权限变更后缓存与库最终一致 | `permission_change_outbox`（**与业务变更同事务写入**）+ `OutboxDispatcher(@Scheduled)` + RabbitMQ quorum queue + 消费端按 `event_id` 幂等 + 版本单调 + DLX + 人工重放接口 | 断 Redis / 断 MQ / 消费者重启三种故障下，N 秒内收敛；重复投递无副作用 |
| C8 | 真多租户 | `tenant` / `user_tenant` 表；`tenant_id` NOT NULL DEFAULT；Hibernate `@Filter` 覆盖 JPA 侧，`TenantLineInnerInterceptor` 覆盖 SQL 侧；租户来自 **JWT claim / 服务端会话** | 伪造 `X-Tenant-Id` → 403；两租户同名数据互不可见；存量数据 100% 有归属 |

## 2. 三个必须先认账的技术裁决（决定工期，不是风格问题）

### 裁决 A：「加个 MyBatis 拦截器」在当前工程里不会自动生效 —— 必须先换读链路

现状：查询主链路是 `airpower-curd` 的 `CurdService` → JPA/Hibernate Criteria（25 个 Service 覆写 `addSearchPredicate`，77 处 `.filter(...)`）。**没有 MyBatis，拦截器无 SQL 可拦。**

可选路径：

| 方案 | 说明 | 代价 | 建议 |
|---|---|---|---|
| A1 全量迁 MyBatis-Plus | 24 资源 + 明细表的 Entity/Mapper/Service/事务全部重写 | 巨大（估 25 人周）、且 AirPower 的 CRUD/导出/权限扫描会失去依托 | ❌ 不做 |
| A2 **读走 Mapper，写留 JPA**（CQRS-lite） | 受保护资源的 `list / detail / 统计 / 导出` 走新建 `KuboBaseMapper` + XML；`create / update / delete` 仍走 AirPower JPA（用 `@Filter` + `creator_id/tenant_id` 默认值兜底） | 中（12 人日内覆盖 24 资源）；需处理"同一表两套读语义"的边界 | ✅ **采用** |
| A3 只做 JPA Specification（现状） | 已在 24 个 Service 接入 | 低，但**永远达不到"SQL 执行阶段注入 + JOIN/COUNT 全覆盖 + 零接入代码"**，也无法用 `TenantLineInnerInterceptor` | ⚠️ 保留为写侧兜底，读侧被 A2 取代 |

**A2 的红线**（否则会踩审计文档 §3.3 的坑）：
1. **同一事务内不得混用**：读方法 `@Transactional(readOnly = true)` 只走 Mapper；写方法只走 AirPower JPA。跨 ORM 的读后写在同一事务里不做（Mapper 不写）。
2. **AirPower 默认端点接管**：对已换轨的资源用 `@Extends(exclude = {Curd.QueryPage, Curd.QueryList, Curd.Detail})` **关掉 JPA 读端点**，由本模块 `XxxQueryController` 暴露同名路径（`/page`、`/detail`、`/export`）→ 前端 URL 不变，灰度可回退。
3. **过渡期双跑校验**：`mode=shadow` 时同一请求同时执行 JPA 与 Mapper 两条读路径，**只返回 JPA 结果并比对行数/total**，差异写 `data_permission_diff_log`；差异率 < 0.1% 连续 3 天才允许该资源切 enforce。这是"换读链路"唯一安全的外科手术方式。

### 裁决 B：拦截器不手写，用 MyBatis-Plus 的 `DataPermissionInterceptor` + `DataPermissionHandler`

- 版本坐标（Boot 3 必须用 spring-boot3 starter）：
  `mybatis-plus-spring-boot3-starter` + **同版本** `mybatis-plus-jsqlparser`
  （⚠️ **3.5.9 起 Pagination/JSqlParser 相关类被拆到 `mybatis-plus-jsqlparser`**，只加 starter 会出现 `PaginationInnerInterceptor` 找不到的编译/启动错误，两个包版本必须一致）
- 注册顺序（**决定 COUNT 是否正确，写反就是分页 total 泄露无权数据**）：

```java
@Bean
public MybatisPlusInterceptor mpInterceptor(KuboDataPermissionHandler handler, KuboTenantHandler tenantHandler) {
    MybatisPlusInterceptor it = new MybatisPlusInterceptor();
    it.addInnerInterceptor(new TenantLineInnerInterceptor(tenantHandler));      // 1. 租户
    it.addInnerInterceptor(new DataPermissionInterceptor(handler));             // 2. 行级（同一租户内细分）
    it.addInnerInterceptor(new BlockAttackInnerInterceptor());                  // 3. 防全表更新/删除
    it.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));       // 4. 分页必须最后（基于已改写的 SQL 生成 COUNT）
    return it;
}
```

- Handler 关键约束（写进代码注释与 CR checklist）：
  - `mappedStatementId → resourceKey` 用启动期构建的 `Map<String, ResourceBinding>`（Mapper 包名/类名约定 + `@DataResource`），**查不到即 fail-closed**（enforce 下 `WHERE 1=0` + 指标 +1，shadow 下不改 SQL 只记日志）；
  - 注入条件必须**带表别名**（`data_resource.table_alias`），JOIN 场景按"受保护表出现几次就注入几次"；
  - 条件表达式一律由 `LongValue`/`Parameters`/`InExpression` 构造，**禁止字符串拼接用户输入**（`PreparedStatement` 参数化优先）；
  - 解析失败（JSqlParser 抛错）→ 视为安全事件：拒绝 + 告警，**绝不回退原 SQL**；
  - 白名单豁免只能由 `@InterceptorIgnore(dataPermission = "true")` + 受控系统任务身份，且必须落审计日志。

### 裁决 C：gRPC 是"拆进程"，不是"加功能"—— 先定契约，最后拆进程

- P1 期：`PermissionRuleProvider` SPI 已在（`JpaPermissionRuleProvider` 实现）。**先把 proto 契约与三级缓存做实**，业务只依赖接口；
- P5 期：把 provider 实现换成 `GrpcPermissionRuleProvider`（L1 Caffeine 命中 → L2 Redis → L3 gRPC → DB），`permission-rule-service` 独立部署；
- 降级语义：**gRPC 不可用 → 回源 DB → DB 也不可用 → 拒绝，不得放开**（审计文档 §5 阶段 6 通过条件）。
- 收益口径要写清楚：Redis/L1 命中后**不再发生 gRPC 调用**，这条"C6"才是"降低每次查询开销"的可验证证据（附命中率与 P95 对比）。

## 3. 真多租户的数据工程（做真的真实代价，先看数再看排期）

由 `gen_multitenant_migration.py` 扫描得出，**不是估算**：

| 事实 | 数量 | 影响 |
|---|---|---|
| `@Entity` / 表 | 53 | 全部要分级：T1 已注册 23 / T2 明细 9 / T3 共享域 12 / T4 未注册 9 |
| 声明 `unique = true` 的列（散落 29 个实体） | **32** | 真多租户最大兼容性风险：这些唯一约束**必须降为 `(tenant_id, col)` 复合唯一**，否则租户 2 无法注册相同手机号 / 相同物料编码；`user.email`、`user.telephone` 都在这 32 个里 |
| 已注册但**无任何可注入归属列**的资源 | 7（`asset.contract`、`asset.device`、`channel.customer`、`channel.purchase`、`channel.supplier`、`mes.bom`、`mes.operation`） | 这 7 个本期只能做 **tenant 维度** + 列级脱敏；要做"负责人/部门范围"必须先加 `creator_id`/`department_id` |
| `@ManyToMany` 关系（如 `UserEntity.storageList`） | 多处 | 中间表**没有标量列**，SQL 里 `IN` 不到；必须服务端展开成 ID 集合（登录时算好放进 `PermissionContext`） |
| 表名与文档不一致 | `mes.order` 实际表名是 **`orders`** | 审计文档写的 `table: order` 是错的（`order` 是 MySQL 保留字）；资源注册与 `data_resource.table_name` 必须按真实表名 |

已生成的地基脚本（幂等、可分批执行、带校验与回滚说明）：
`SPMS-Server/docs/database/migration/20260906_multitenant_foundation.sql`（517 行）
→ 内含 `tenant` / `user_tenant` 建表、逐表 `tenant_id`/`creator_id` 加列、`idx_*_tenant` 索引、32 处唯一域降级、存量回填 `tenant_id=1`、以及"任一非 0 不得开 enforce"的校验查询。

**还需要补的 3 处代码侧事实**（脚本管不了，必须在 P1 做）：
1. `creator_id` / `tenant_id` 的写入注入点：AirPower `CurdEntity` **没有** `createBy`，所以要么在 `base/BaseEntity` 加 `@PrePersist` 钩子，要么在 `base/BaseService.beforeCreate()` 统一填充（当前 `InventoryService:82` 已有 `beforeCreatePredicate` 覆写先例）。
2. 租户来源改造：`RequestInterceptor:162` 现在**读 `X-Tenant-Id` 请求头**，必须改为 JWT claim / `user_tenant` 校验；`X-Tenant-Id` 仅作为"切换租户候选"且需校验成员关系，失败即 403（**不得回落 0L**）。
3. `ddl-auto`：`application-production.yml` 当前是 **`update`**，加列/改唯一索引必须由迁移脚本做，生产必须 `validate`，否则 JPA 会按实体自动建表与迁移脚本互相打脸。

| **D1** | 租户 ID **只**从服务端 `user_tenant` 关系解析；`X-Tenant-Id` 降级为"切换意图"，必须经成员校验，越权直接 403 | 旧实现 `resolveTenantId` 直接信任请求头且缺省回落 `0L`：任何登录用户改一个头就能切租户，且 `0L` 让租户条件形同虚设。否掉的替代：JWT 里塞 tenantId（切换租户要重签 token，且历史 token 全部失效） |

| **D7** | 导出/文件流不经过 Jackson，序列化层管不到；`/export` 必须在 P3 自建导出并复用同一套 `ColumnMaskingService` | 在 PRD 里明确标为"未完成能力"，禁止把"JSON 已脱敏"写成"字段已脱敏" |

## 12. P1 内核落盘（条件树 + 归属基类 + 影子双跑）

### 12.1 新增/改动

**条件树内核**（`module/system/datapermission/rule/`，全部无状态纯对象，由 `DataPermissionAutoConfiguration` 统一成 Bean）

| 类 | 作用 |
|---|---|
| `PermissionRuleOp` | 受控算子集：`ALL_OF/ANY_OF` + `EQ/NE/GT/GE/LT/LE/IN/NOT_IN/IS_NULL/IS_NOT_NULL/LIKE`；**没有** `RAW/SQL/EXPRESSION` |
| `PermissionRule` | 条件树（`Group`/`Leaf`/`AllowAll`/`Deny`），三个消费方共用同一棵树 |

| `PermissionRuleValidator` | 深度 ≤8、分组子节点 ≤20、叶子 ≤64、列必须在**白名单**内、算子与值形态匹配；空数组 `IN` 视为配置错误 |

| `SqlPermissionRuleRenderer` | P2 MyBatis 侧：树 → `RowPermissionPredicate`（命名参数逐项占位，值绝不进 SQL 文本） |
| `PermissionRuleEvaluator` | 内存求值，作为两个实现的**裁判**（契约测试 + 影子比对复算） |

## 13. 前端 F1 落盘（按钮权限收口）与一条被推翻的计划前提

### 13.1 先纠正前提：**`routes.ts 补 meta.permission` 在本项目结构下不成立**

计划写的是"`routes.ts` 补 `meta.permission`（现 0 条声明），`permissionGuard` 实际空转"。
读完 `Console.vue` 后发现：业务页面路由不是静态声明的，而是
`RouterUtil.initVueRouter(menuList, import.meta.glob('/src/view/**/*.vue'), ...)`
**按后端下发的菜单动态注册**；`routes.ts` 只有 `/login`、`/403` 与一个 `:catchAll(.*)` 兜底。
因此在静态路由上写 `meta.permission` 既无处可写也不该写：

- "看不见的页面"已由**菜单下发**控制，直连未授权路径落进 `catchAll` → error 视图；
- 数据可见性由**后端每个端点的权限码**控制（AirPower `scanPermission()`），前端不是安全边界；
- `permissionGuard` 保留 `meta.permission` 能力即可（有静态路由需要时用），**不要**为了凑指标给动态路由硬塞 meta。

同理，"`v-permission` 只覆盖 4/33"这个指标也**低估了现状**：CRUD 按钮的权限大部分已经由
`@airpower/web` 的 `ATable` 自动收口 —— `WebConfig.autoPermissionPrefix` 默认为 `true`，
未显式传 `*-permission` 时框架按 `{EntityName}_{action}` 自动推导（与后端命名规则一致），
所以"没写 props"≠"没门控"。**真正漏的是不走 ATable 默认按钮的自定义按钮。**

### 13.2 本轮实际收口的东西

### 14.2 F2 实际落盘（前端全部实测）

真实缺口不是"33 个视图没铺 v-mask"，而是**后端策略对前端渲染毫无作用**：
`my-mask` 端点存在、`dataFieldPolicyApi.getMyMask()` 存在、`normalizeMaskPolicy()` 存在，
但**生产代码里 0 处调用**（只有单测在调）。也就是"策略由后端下发"停留在端点层面，
前端 `v-mask` 用的是自己那套硬编码规则。本轮把这条线接上：

1. **口径镜像（先修 bug）**：后端 `applyMask` 支持 `FULL / PARTIAL / REPLACE / LAST4 / HASH` 五支，
   而前端 `MaskType` union 只有三支 → 前端遇到 `LAST4` 会落进"未知类型"被按 `****` 处理（**过度遮蔽**，
   且两端各自"没错"、极难排查）。补齐 union，并新增 `applyMaskPolicy()` 逐分支对齐 Java：
   `FULL/REPLACE` 忽略原值只输出表达式、`PARTIAL` 星号数封顶 6（不泄漏长度）、
   `LAST4` 长度不足 4 时退回表达式、`HASH` **前端不算**（浏览器端算不出同口径摘要，宁可 `****`）、
   未知类型安全失败。15 条 shared 测试的期望值全部按 Java 源码推导。
2. **策略真正进渲染**：新增 `src/composables/useMaskPolicy.ts`

   解析顺序：**后端策略优先**；策略未到达时按"应遮蔽"处理（不能拿"还不知道"当"可以看"）；

4. **价格列按策略渲染**：`channel/{purchasePrice,salePrice}/list.vue` 用 `#price` 插槽，

## 15. F3：把 `@Table({desensitize})` 的错觉戳破，并闭合"读侧脱敏 → 写侧回环"

### 15.1 三条新证据（收紧 §14 的说法，别再当防护用）

**1）`@Table({ desensitize })` 不是访问控制，是"点一下眼睛就看明文"的展示糖。**
`node_modules/@airpower/web/dist/main.js` 里 `__name: "Desensitize"` 的实现是：

```js
const isDesensitize = ref(true)
const desensitized = computed(() => (!isDesensitize.value || !props.type)
  ? props.content                       // ← 点一下就是原值
  : DesensitizeUtil.desensitize(props.content, props.type, props.head, props.tail, props.symbol))
// 图标：onClick: () => (isDesensitize.value = !isDesensitize.value)
```

`content` prop 装的就是**原始明文**，切换是纯本地 ref，没有任何权限判断、没有后端调用。
所以 §14.2 第 3 条"补齐 3 个敏感字段"得到的是**防旁人瞄屏/防截图**级别的默认打码，
**不是权限**。真正的访问控制只在后端序列化层（`@SensitiveField`）：那里响应体里就没有明文。

**2）`desensitize` 与 `copy` 是互斥分支。** 单元格渲染是
`item.desensitize ? h(ADesensitize, {content, type}) : item.copy ? h(Copy, {column, data}) : …`，
声明了 `desensitize` 之后**复制按钮直接消失**。因此 §14.5 里"`copy: true` 可能复制原值"的担心不成立；
副作用是 `User.idCard` 加了 desensitize 后列表上不再有点复制入口（预期行为）。

**3）恒空 `factoryIds` 的后果比"字段没用"严重，且在两条链路上方向相反。**
- `DataPermissionService` / `JpaPermissionRuleProvider` 的主体匹配是
  `context.factoryIds().contains(subjectId)` → 恒空 = **任何人配的 FACTORY 策略都永不命中**；
  若某资源只配了 FACTORY 策略，读链路等价于"没配策略"（除非资源开了默认拒绝）→ **假安全**。
- `RowPermissionPredicate.factory(alias, col, ids)` 对空集合返回 `deny()` →
  在 `condition_json` 里引用 `factoryIds` 会被渲染成恒假条件 → **整个列表空结果**（自锁）。

同一维度，一边"看起来限住了其实没有"，一边"全员看不到数据"。因此本轮**不再等 D13 拍板**，
先把中间态堵掉：`DimensionGuard`（新增，纯静态判定，便于单测与将来放开）在
`DataPolicyService.beforeAdd/beforeUpdate` 里**拒绝** FACTORY 主体策略与引用 `factoryIds` 的条件树，
报错文案直接给出替代维度。建表后只需把 `FACTORY_AVAILABLE` 置 true 并补 `PermissionContext.factoryIds()` 的真实解析。

### 15.2 本轮真正的闭环：读侧遮了，写侧别把掩码写回库

链路是这样的（本项目所有编辑表单都这样）：
`getDetail` → `useEditor` 把实体整体回填 → 用户只改昵称 → **整实体提交** →
`beforeUpdate` 收到 `phone = "138****000"`。一旦 `personnel.user` 上配了 FULL/PARTIAL 策略，
不处理就是**掩码覆盖真实手机号且不可逆**。本轮处置：

| 位置 | 做法 |
| --- | --- |
| `MaskedWriteGuard`（新） | `looksLikeMaskedPlaceholder()`：连续两个 `*` / 整串 `*` / `h:`+十六进制；单个 `*` **不算**（`a*b` 是真实文本）。处置当时写在本类里（`rejectMaskedPlaceholder` / `keepStoredWhenMasked`），**F5 已把处置上移为 `SensitiveWriteProtection`，本类只留 `looksLikeMaskedPlaceholder` 这一个判定**（见 §17.5） |
| `UserService` | ~~`beforeAdd` 拒绝、`beforeUpdate` 从库里取值覆盖掩码字段~~ —— **F5 已删除这段手写代码**：只保护 `personnel.user` 一个实体等于其余 3 个带 `@SensitiveField` 的实体继续裸奔，兜底已上移到 `BaseService`（见 §17.2） |
| `UserEntity` | `idCard` / `phone` / `email` 标 `@SensitiveField(resourceKey = "personnel.user")`。**无策略时输出原值 = 零行为变更**，标注解的意义是"这个字段可以被策略管起来" |
| `DataFieldPolicyController` | 新增 `GET /dataFieldPolicy/my-mask-map?resourceKey=`：一次返回该资源全部生效策略（`ColumnMaskingService.getEffectiveMaskPolicyMap`）。存在的理由不是省流量，而是**表单必须知道哪些字段受限**，逐字段查 = 8 字段表单发 8 个请求 |
| `useMaskPolicy` | `ensureResourceMaskPolicies()` 走批量；**老后端 404 时自动退回逐字段**（前端可先合、后端后上，不互相卡发版）；`maskedFieldsIn()` 只用于提示 |
| `personnel/user/component/editor.vue` | 受限字段提示条："保持不动即可保留原值（提交掩码不会覆盖真实数据）" |

**明确否决的做法**：让前端"提交前把受限字段从 payload 里删掉"。在整实体更新语义下，
删字段等于把该列提交成 `null` —— 比回写掩码更糟（掩码至少是"看得见的坏数据"）。
所以前端只提示，兜底放服务端。

### 15.3 已知缺口（不要当成已完成）

## 16. 数据权限策略管理界面（F4）：没有界面就谈不上"可灰度"

### 16.1 缺口

后端有 3 个 controller（`dataResource` / `dataPolicy` / `dataFieldPolicy`）、3 张表、1 套校验，
**前端 0 个界面**（`src/view/console/system/` 下只有 coderule/config/log/mcp/menu/permission/unit）。
后果不是"少个页面"，而是：

- 策略只能靠 SQL 或 `DevDataInitRunner` 硬编码种子来改 → **shadow 观察期无法按角色试放开**，
  也就没法在不停机的前提下从 shadow 走到 enforce；
- `FACTORY` 在前端 0 命中这件事，说明我上一轮"应在界面里禁用该维度"是无的放矢 —— 根本没有界面。
  这条已核实并改正。

### 16.2 落盘内容

| 层 | 内容 |
| --- | --- |
| 模型 | `src/model/system/datapermission/`：`DataResource` / `DataPolicy` / `DataFieldPolicy` 三个 Entity + Service（`baseUrl` 与后端 `@Api` 一一对应） |
| 枚举 | `DataPermissionSubjectType` / `DataPermissionActionType` / `DataPermissionMaskType`，一律 `WebEnum<string>` |
| 视图 | `src/view/console/system/datapermission/{resource,policy,fieldPolicy}/list.vue` + 各自 `component/editor.vue` |
| 权限码 | `Permissions.System.{DataResource,DataPolicy,DataFieldPolicy}`（add/update/delete/getDetail），`perms:check` 已验证全部能在后端找到对应端点 |
| 菜单 | `MenuService.initMenu()` 追加 3 项（见 16.4） |

三个"必须这样写"的点，都是从实测里来的：

1. **枚举 key 用字符串，不用序号**：`data_policy.subject_type`、`action_name`、`data_field_policy.mask_type`
   存的都是后端枚举的 **name()**（`DevDataInitRunner` 里就是 `DataPermissionSubjectType.SYSTEM.name()`）。
   若按项目里常见的 `WebEnum<number>` 写序号，界面能选、后端读到的是 `"1"` —— 静默失配。
   （我第一版正是这么写的，`vue-tsc` 与后端字段比对时暴露了出来。）
2. **布尔字段必须挂 `BooleanYesNoDictionary`**：否则 `AFormField` 退化成文本框，提交 `"true"` / `""`；
   空串还可能把 `enabled` 这种非空列写成 `null`。挂上字典后 key 就是真布尔，零转换代码。
3. **`FACTORY` 与 `EXPORT` 用框架原生 `setDisabled(true)` 灰掉、而不是删除**，并在编辑器文案里写明原因：
   删除选项只会让人不知道为什么少了一个；灰掉 + 文案才能把"这一维存在但尚未落地"传达到位。
   这与后端 `DimensionGuard` 的 fail-fast 同口径（前端拦选择、后端拦请求，缺一不可）。

编辑器提示里也如实写了两处**未接线**：`EXPORT` 动作的列级策略不会被消费（导出走文件流、不经过 Jackson）；
列级脱敏读链路只解析 `QUERY`（`ColumnMaskingService.DEFAULT_ACTION`）。配了不生效却查无原因，
比配不了更糟，所以宁可把限制摆在表单第一行。

### 16.3 体积现状（需要提前决策）

`pnpm size`：首屏 **404.2 / 450 KB**（未变，新页面都是懒加载独立 chunk）；
总体 **837 / 850 KB**，余量只剩 **13 KB**。下一个整模块页面就会顶破红线，
届时要么按"管理端页面不计入首屏、总体预算上调到 900"改指标（需要在 `check-bundle-size.mjs` 里写理由），
要么先做 vendor 拆分。**不要**到时候直接删规则。

### 16.4 一个必须写进运维说明的事实

`initMenu()` 只在 `DevDataInitRunner` 的初始化路径里执行，且整个方法以 `LOCK_FILE` 存在与否为开关：
**生产库不会因为发版自动出现这三个菜单**。上线时要手工插入 3 条 `menu`（路径分别为
`/console/system/datapermission/{resource,policy,fieldPolicy}/list`）并挂到对应角色，
否则页面文件存在但进不去。前端路由是菜单驱动的（见 §13.1），这条是硬前提。

## 17. F5：把"受限字段怎么写回去"从补丁变成内核

### 17.1 上一轮留下的其实还是补丁

F3 的处置写在 `UserService` 里（`restoreMaskedInputs` / `rejectMaskedInputs`），于是覆盖面等于
**一个实体**。而 `@SensitiveField` 已经标在 4 个实体 6 个字段上：

| 实体 | 字段 | F3 之后受限角色点"保存"的实际结果 |
| --- | --- | --- |
| `personnel/user/UserEntity` | `idCard` `phone` `email` | 掩码被库中原值覆盖（已保护） |
| `asset/material/MaterialEntity` | `purchasePrice` `salePrice` | `"****"` → `Double` 反序列化异常，整条记录改不动 |
| `channel/purchasePrice/PurchasePriceEntity` | `price` | 同上，且实体上的 `@NotNull` 让报错长得像校验问题 |
| `channel/salePrice/SalePriceEntity` | `price` | 同上 |

更要紧的是"每个 service 都要记得写一段"这件事本身 —— 漏一个的后果是**把掩码永久写进真实列**，
而这类遗漏在测试里通常是绿的（没人给它写策略）。所以本轮不新增业务能力，而是把兜底搬进框架层。

### 17.2 现在的分工

| 位置 | 责任 |
| --- | --- |
| `annotation/SensitiveField` | 读写**同一处**声明：`@JsonSerialize(SensitiveFieldSerializer)` + `@JsonDeserialize(SensitiveFieldDeserializer)` + `restoreOnMasked()`。加字段的人只需要打注解 |
| `serializer/SensitiveFieldDeserializer` | 认出掩码 → 登记 → 分流：字符串字段返回 `null` 交恢复；非字符串字段明确拒绝；**真实值一律原样交回 Jackson**（类型错误必须继续是错误） |
| `service/MaskedInputRegistry` | `ThreadLocal<Set<"类全名#JSON字段名">>`：登记"这个字段本次收到过掩码" |
| `service/SensitiveWriteProtection` | 反射收集实体上的绑定（按类 `ConcurrentHashMap` 缓存）+ `restoreOnUpdate` / `rejectMaskedOnAdd` / `hasMaskedInput` |
| `base/BaseService` | `beforeAdd` 拒绝、`beforeUpdate` 恢复。**一处接入，全模块生效** |
| `common/interceptor/RequestInterceptor` | `afterCompletion` 清登记（与 `PermissionContextHolder.clear()` 并排） |
| `service/MaskedWriteGuard` | 只留 `looksLikeMaskedPlaceholder()`：读侧写出什么、写侧认什么的**唯一口径** |

三处设计约束值得单独记，因为它们都是"看起来可以简化、简化完就出事"的点：

1. **登记必须发生在置 `null` 之前**。置 null 之后"用户主动清空"与"受限没提交真值"在实体上
   完全同形，而处置相反（前者照写、后者回灌）。`genuineClearIsNotRestored` 这条测试就是钉这个分界点的。
2. **`ThreadLocal` 必须清**。Tomcat 线程池复用线程，残留会让下一个人的一次普通保存被"恢复"成旧值。
   清两处：`afterCompletion`（HTTP 入口）与 `BaseService` 消费后（异步 / 测试入口）。
3. **零额外查询是硬要求**。`hasAny()` 为假时 `BaseService` 直接返回，不做回表 ——
   正常保存路径不能被"防掩码回写"拖慢，否则这条防护在生产上迟早被人关掉。

另外 `SensitiveWriteProtection.scan` 对**基本类型**上的 `@SensitiveField` 直接
`IllegalStateException`（`long` 承载不了"未提供"，恢复语义无从表达）：配置错误要在启动/首用时
响亮失败，而不是线上表现为"看起来有保护其实没有"。

### 17.3 数值敏感字段：定论是"改不动"，不是"能兜底"

`Double price` 受限时能选的做法只有三种，前两种都被事实否掉了：

- **置 null + 更新时恢复**（字符串字段的正解）：走不通。参数校验在 `beforeUpdate` **之前**执行，
  `PurchasePriceEntity#price` 上的 `@NotNull(groups = {WhenUpdate, WhenAdd})` 会先把请求打成
  "采购单价不能为空" —— 用户面对一个与权限无关的假错误，恢复逻辑根本没机会跑。
- **写 sentinel（0 / 空串）骗过校验，再在 service 里覆盖回来**：能跑，但**只要恢复链路某处漏接，
  就是静默改价**。金额静默错比改不动严重一个量级，否掉。
- **明确拒绝 + 前端提前说明**：采用。后端在反序列化阶段 `PARAM_INVALID.show("字段[price]对当前角色受限…")`；
  前端 `blockedSubmit()` 在点保存时给出同一口径的提示并中止（`useEditor.beforeSubmit` 返回 `null`
  即中止 —— 这条语义是读 `@airpower/web` dist 里 `onSubmit` 的实现实测来的，不是猜的）。

**副作用要如实记下**：受限角色改不了这条记录 —— 这是 fail-closed，不是 bug。
要让它可改，正确路径是 `allowPlaintext`（在 §16 的字段策略界面上按角色放开），不是往代码里塞兜底。

### 17.4 前端配套与新增的第 5 道门禁

- 三个价格编辑器（`asset/material`、`channel/purchasePrice`、`channel/salePrice`）接上
  `useMaskPolicy(resourceKey, fields)`：`el-alert` 说明"该字段当前不可见"，`beforeSubmit` 用
  `blockedSubmit()` 决定是否中止。列表侧的遮蔽不在这次范围内（沿用 `v-mask` / `desensitize`）。
- `useMaskPolicy` 新增 `blockedSubmit()`：**纯函数、只返回文案**，不 import `ElMessage` ——
  composable 不制造副作用，提示由视图发；文案只有一份，三个页面不会各说各话。
- 门禁 5（`src/config/__tests__/maskContract.spec.ts`）：`useMaskPolicy('K', ['f1', 'f2'])` 里的字段名
  **必须**是后端那个 `K` 上真被 `@SensitiveField` 标记的字段。为什么这条比资源键那条更值钱：
  字段名写错 = 策略查不到 = 前端认为"无需脱敏" = **静默 fail-open**，界面上一切看起来都正常，
  而这类声明恰恰是靠复制粘贴改出来的。已做变异验证：把 `purchasePrice` 改成 `purchasePriceX`
  → 该用例立刻红，并回显"后端该资源只标记了 purchasePrice/salePrice"。
- 该门禁的解析边界写在注释里：只认"类型段不含空白"的字段声明（`private Map<String, Object> x;` 会跳过）。
  代价是**少校验一个字段**而不是误报 —— 门禁咬人一次，以后就没人信它了。
- 提交后又补了一处收紧：门禁读后端源码时**只看代码、不看注释**（`readJavaCode()`）。原因很具体 ——
  `SensitiveField` 的 javadoc 里有一个可直接抄的示例键 `@SensitiveField(resourceKey = "wms.inventory")`，
  不过滤就会把"文档举了个例子"当成"后端注册过这个资源"，于是资源键写错也能过门禁。
  自检用例直接盯着这个示例（注释里有、代码里没有），示例被删时同步删掉自检，**不要反向改代码去过测**。
- 两条相关门禁都做了变异验证（不是只跑一遍绿就交付）：`purchasePrice → purchasePriceX` 让门禁 5 红；
  `asset.material → asset.materiaX` 让门禁 2 与门禁 5 同时红，还原后 5/5 绿。

### 17.5 顺手清掉的三处"两套真相"

### 18.3 模块 B：非星号遮蔽改用"正向复算"，§15.3 的缺口收口

之前的判定只问"这串像不像掩码"（连续星号 / `h:` 前缀），于是 `maskExpression = "已隐藏"`
这种配置**天然漏判**：读侧遮成"已隐藏"，写侧认不出，值就落库了。
修正在思路而不在补丁：**不要猜它像不像掩码，而是算一遍"这个用户此刻从读侧看到的会是什么"**。

| 位置 | 改动 |
| --- | --- |
| `SensitiveWriteProtection#restoreMatchingMaskedOutput` | 对每个 `restoreOnMasked` 字段：`expected = maskingService.maskFieldValue(resourceKey, field, storedValue, context)`；`String.valueOf(expected).equals(String.valueOf(incomingValue))` → 说明提交值是我们自己发出去的，保留库中原值 |
| `SensitiveWriteProtection#mayContainMaskedOutput` | 是否需要复算的开关：该实体涉及的资源里存在**真的会遮蔽**的策略（排除 `allowPlaintext=true`，那些用户提交的就是原值，比对纯属浪费） |
| `BaseService#protectSensitiveFields` | 两条识别路径并用：**登记命中**（星号占位，零成本、不查库）+ **输出复算**（需要按主键多取一次）；两条都不需要时直接返回，正常保存仍是一次 UPDATE |
| `ColumnMaskingService` javadoc | 把"提交前剔除"这个**已否决**方案的说法改掉（同一个错误说法在 `DataFieldPolicyController` 里也有一份，一并改） |

三个必须记清的取舍：

1. **复算以 `expected == storedValue` 判"没遮蔽"**，靠的是 `maskFieldValue` 在无策略 / 允许明文时
   返回**同一个对象引用**（不是相等，是同一对象）。这个前提很脆 —— 若哪天有人把该方法改成
   `return strValue` 之类新建对象，明文用户就会白跑一次比对（无害）；但**反向**改成
   "无策略时返回 null"就会让这里静默失去保护，所以测试里专门有一行 `expected == storedValue` 的断言语境。
2. **误判方向固定成"丢弃一次输入"而不是"写坏数据"**：用户真的把备注/手机号改成"已隐藏"时，
   这次输入会被原值覆盖（有 info 日志）。反过来选就会让掩码进真实列，两者不可同日而语。
3. **幂等**：登记路径先恢复过一次，复算路径再跑时 `incoming == stored`、`expected != incoming` → 不动，
   两条路径可以任意顺序重复执行。

### 19.1 C0：让 CI 真的跑到这些改动

`ci.yml` 的 `on.push.branches` 加上 `'arena/**'`。理由见 §18.6：**工作分支上的推送此前一次 CI 都没触发**，
`server` 那个 `./mvnw compile` 硬门禁形同虚设，我把"沙箱内实测"当成唯一验证来源已经好几轮了。
（仍有一句要说清：加触发条件解决的是"会不会跑"，不解决"后端 job 的 test 是 continue-on-error"，
那要等 Testcontainers 收口，见 C1 之后的路线。）

### 19.2 【计划外】资源键整串小写 → camelCase 资源的策略永不命中

`DataPermissionResourceResolver.resolve()` 原来是 `module + "." + entityName.toLowerCase()`，
而注册表里的键是 camelCase：

| Service | 解析出来的键 | `data_resource` 里的真实键 | 结果 |
| --- | --- | --- | --- |
| `MaterialService` | `asset.material` | `asset.material` | ✅ |
| `PurchasePriceService` | `channel.purchaseprice` | `channel.purchasePrice` | ❌ 永远查不到 |
| `SalePriceService` | `channelsaleprice`…（同理） | `channel.salePrice` | ❌ 永远查不到 |

**为什么它能长期潜伏**：查不到资源的后果不是报错，而是"这个模块没有策略" —— 保存成功、
界面显示"策略已配置"、测试全绿。凡是"资源键当外键用的字符串"都适用同一条纪律：
**比较必须与注册表一字不差，不许顺手规范化**。修法是把整串小写换成"只降首字母"的
JavaBean 口径（`decapitalize`），并保留 `BOMService → BOM` 这类缩写不动。
新增 `DataPermissionResourceResolverTest` 用**真实注册键**当断言锚点（不是拿"我以为的规则"验"我以为的实现"）。

### 19.3 C1：导出旁路 —— 这一轮做"收口"，不做"第二套遮蔽"

现状：列级脱敏在 Jackson 层，导出走文件流不经过它；而策略界面里 `EXPORT` 动作一直可配 ——
管理员配完，防护实际为零（§16.2 已把这条写成"界面提示"）。

做法与边界：
- 新增 `ExportBypassGuard`（挂在 `RequestInterceptor.checkUserPermission` 里，紧跟 `ensurePermissionContext`）。
  放拦截器而不是逐个 controller 加钩子，是因为 `BaseController` 全局排掉了 `Curd.Export`、
  只有个别实体 `@Extends` 加回来 —— **逐个加必然漏，旁路漏一个等于没做**。
- URI → 资源键的映射**不猜约定**：用 `data_resource.table_name` 反查（`/material/export` → `asset.material`），
  为此给 `DataResourceRepository` 加 `getByTableName`。为什么不复用解析器：它需要 Service 类，
  拦截器手里只有 URL。
- 判定：该资源在 `QUERY` 下对该用户有遮蔽 → 必须**每一个**被遮蔽字段都在 `EXPORT` 动作下拿到
  `allowPlaintext` 才放行。用"每一个"而非"存在一个"：导出是一整份文件，一列漏了这份文件就泄了。
- 灰度友好：`mode=off` 不介入（回滚开关必须真能回滚）；`mode=shadow` 只写影子记账
  （reason=`export-bypass`）不改结果 —— 先看清"开 enforce 会挡住多少人导出"，再开。
- 动作段识别只认"最后一段"，不用 `contains`：否则 `/exportLog/list` 这类业务路径会被误伤
  （测试 `onlyTheActionSegmentCountsAsExport` 就是钉这个的）。
- 没有给导出实现加"第二套遮蔽"：那与"消灭第二套实现"的改造目标正面冲突（§15.1 的教训）。
  `EXPORT + allowPlaintext` 从此是有语义的授权，而不是一个装饰性下拉项。

### 19.4 C2：`FACTORY` 维度可用性从编译期常量改为配置

`DimensionGuard.FACTORY_AVAILABLE`（`static final false`）换成
`isFactoryAvailable()` 读 `kubo.data-permission.factory-dimension-enabled`（默认 false）。

### 19.5 C3：体积预算改口径要连理由一起改

### 19.9 CI 第一次真的跑起来之后：两件事，都不是"代码逻辑错"

加 `arena/**` 触发只是让门禁**开始执行**；紧接着连续两个坑证明了一件事 ——
**"CI 是红的"和"后端被验证过"完全是两件事。**

**坑一：`./mvnw` 没有可执行位（`exit 126`）。**
`SPMS-Server/mvnw` 在 git 里是 `100644`，`ls -l` 只有 `rw-r--r--`。
于是 `Server` job 的 `Compile` 步骤**从来没有调用过 javac**，`Process completed with exit code 126`
的含义是"命令找到了但不可执行"。修法：索引里改成 `100755`（`git update-index --chmod=+x`，
不依赖各人本地 `core.fileMode`）+ workflow 里再 `chmod +x ./mvnw || true` 兜一次。

> 影响面必须说清楚：**F2 之后所有后端改动（含 F5 写侧守卫、F6 导出收口、F7 资源键修复）
> 的真实状态是"连编译都没开始"**，而我连续几轮把"沙箱内结构自检通过 + 逻辑复读"当成了交付依据。
> 判据应当是"**有没有一个环境真的执行过它**"，不是"我这边所有能跑的检查都绿"。

**坑二：唯一的真实编译错误，是一个少写的反斜杠。**
`MaskedWriteGuard` 里写了 `text.matches("`（单反斜杠）`*+")` —— `*` 不是合法的 Java 转义字符，
`javac` 直接 `illegal escape character`；正确写法是双反斜杠（正则里的 `\*` 在源码里必须成对）。
同文件里 `"*".repeat(n)` 那种**不含反斜杠**的写法不会中招，所以这类问题的特点是：
**只在一个文件炸，却能让整条流水线红**，而且看起来"跟业务逻辑毫无关系"。

**顺带修掉的可读性坑**：Actions 日志正文在对象存储上，本沙箱取不到
（`gh run view --log`、`actions/jobs/{id}/logs` 全部超时），一开始完全看不到失败原因。
现在 CI 把 `[ERROR]` 行转成 annotation（`::error::`），`gh api check-runs/{id}/annotations` 一步读到 ——
**"能不能远程诊断"本身也是门禁的一部分**：读不到原因的红，等于没人会去修的红。

**新增机器门禁：`pnpm text:check`**（`infra/scripts/check-source-text.mjs`，由 `encoding:check` 改名扩展）。
它同时查两类"编译器与测试都不管、但会吃掉数据或吃掉构建"的文本级问题：

```bash
$ pnpm text:check
✓ 文本完整性：937 个文件无 U+FFFD / 非字符；401 个 Java 文件无非法转义
```

- 规则一：`U+FFFD` / 非字符（§18.2 起；本轮把它正式并入"源码文本完整性"门禁）；
- 规则二：**Java 字符串/字符字面量里的单反斜杠非法转义**（本轮新增）。扫描时跳过注释与字符串外区域，
  因此不会误伤 javadoc 里成对的转义示例；401 个文件跑完 0 误报。
  已验证变异：把 §19.9 那处写错的形式放回文件 → 精确指到 `MaskedWriteGuard.java:69` 并 `exit 1`。
- 失败输出**按规则类型分流**"处理办法"：编码类提示"原字节已丢、按语义重写"，转义类提示"双写反斜杠 + 确认 CI 真的编译过"。
  一条笼统的"去重写这些中文"会把人往完全不同的方向带。

**踩坑记录（对自己）**：验证变异时用了一次 `git checkout -- SPMS-Server`，
把**尚未提交**的转义修复一起毁掉了（文件回到 HEAD 的坏版本），当场没察觉。
教训：变异回滚必须用事先 `cp` 出来的副本；`git checkout -- <dir>` 在"还有未提交改动"的仓库里等于随机丢工作。
这条不是理论风险，是本轮真实发生过一次的。

### 19.10 下一步建议（按模块，仍按"能否自动化验收"排序）

1. **给导出补真·遮蔽（可选，且要先解决"看不到框架导出实现"）**：先用 `javap`/反编译确认
   `Curd.Export` 的行组装入口，再决定是"复用 `ColumnMaskingService` 遮蔽单元格"还是维持现状（拒绝导出）。
   验收方式不变：受限角色导出，断言文件内容。
2. **后端 CI 从"`compile` 必过、`test` 允许失败"翻成两步都必过**：`DataPermissionIntegrationTest`
   这类依赖 DB 的用例用 Testcontainers（Postgres/MySQL 容器 + `schema-test.sql` 与真实 schema 对齐）收口。
   前置条件已经具备：`mvnw` 有执行位了、失败原因能从 annotation 读到（§19.9）——
   这件事不做，"Java 未经编译验证"这个状态会一路跟着每一次交付。
3. **D13 的建表分支落地**：现在开关已经可配，缺的是 `user_factory` 表 + `PermissionContext.factoryIds()` 解析 +
   与行权限共用同一份；做完把 `factory-dimension-enabled` 在灰度环境打开，用 `export-bypass` 同款影子记账看影响面。
4. **策略界面的 `EXPORT` 提示可以退役了**：§16.2 写的"该动作暂未被消费"如今不成立（本轮起它决定导出生死），
   界面文案要改成"用于授权受限角色的明文导出"。这是一处**会被误读为已实现**的注释型债务，别拖。
5. **前端 `x-visibility` 彻底作废并删除残留**：受限列元数据已由 `my-mask-map` 承担，
   文档/PRD 里凡是提到"响应头带可见性"的地方都要改，否则会有人按它实现一遍。
