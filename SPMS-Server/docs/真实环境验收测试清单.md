# 真实环境验收测试清单（供人工逐条勾选）

> 目的：把「本地/CI 无法代替」的部分列成可勾选的清单。每一条都标了**前提**、**怎么测**、**期望**、**失败意味着什么**。
> 分组对齐施工图验收矩阵 §8 与各节「仍欠」项。勾选状态用 `[ ]`（未测）/ `[x]`（通过）/ `[!]`（失败，记原因）。

## A. 基础设施与数据

### A1 真实 MySQL 迁移幂等
- **前提**：真实 MySQL 8 实例；已部署最新迁移脚本。
- **测**：执行两遍迁移（Flyway/脚本），对比 `information_schema.COLUMNS`。
- **期望**：两遍结果一字不差，无重复建表/改列报错；`permission_change_outbox` 表存在且 15 列。
- **失败意味**：迁移不幂等 = 升级即事故。
- [ ] 通过

### A2 表结构核对（DDL↔实体）
- **前提**：A1 完成。
- **测**：`node infra/scripts/check-ddl-entity-drift.mjs` 在真实库旁跑一遍；或用 `mvn validate`。
- **期望**：7 张表、7 实体一致。
- **失败意味**：实体缺映射列会被 Hibernate `validate` 启动拦截（生产 ddl-auto=validate）。
- [ ] 通过

### A3 `data_resource` 登记行补齐
- **前提**：A1 完成。
- **测**：查 `data_resource` 是否覆盖你要 enforce 的资源（尤其 8 核心资源）；缺行即「未登记」。
- **期望**：8 核心资源全登记且 `status=ENABLED`。
- **失败意味**：缺行 = 该资源「未登记」，enforce + deny-unregistered=true 下恒假、否则静默不加过滤。
- [ ] 通过

## B. 权限判定五出口（验收矩阵 §8 核心）

### B1 租户隔离（伪造 X-Tenant-Id / 跨租户直查）
- **测**：不带租户头；伪造 `X-Tenant-Id` 切到别人租户；跨租户 id 直查 detail。
- **期望**：403 / 服务端 claim 生效 / 404（看不到别租户数据）。
- [ ] 通过

### B2 行级过滤（仓库/负责人/部门/ANY_OF）
- **测**：同一 page 接口，仓库 A 用户 vs 仓管 B 用户；department 父看子；creator_id 仅看自己；`ANY_OF(仓库 OR 负责人)` 组合。
- **期望**：行数与集合一致；无越权行。
- [ ] 通过

### B3 写路径（改/删无权行 + 归属防篡改）
- **测**：批量更新/删除混入无权 id；PUT 改 `creatorId`/`tenantId` 为别人。
- **期望**：整批拒绝或部分拒绝并给明细；**归属列被恢复为库中值**（新建时被服务端覆盖）。
- [ ] 通过

### B4 列级脱敏（无 plain 权限 + 导出）
- **测**：受限角色读敏感字段；导出文件打开核对。
- **期望**：界面/导出均脱敏；库内原值不变。

### B5 COUNT/分页一致性
- **测**：total vs 实际条数；改 pageSize；JOIN 统计。
- **期望**：一致，COUNT 含权限条件。

## C. 影子双跑与放开门禁

### C1 三日 SHADOW 差异率（B-2 硬前提）
- **前提**：`mode: shadow` 已跑 ≥3 天；`data_permission_diff_log` 有 `EXPECTED_FILTER` 样本。
- **测**：查差异率；`GET /dataResource/enforce-readiness` 看 `SHADOW_EVIDENCE` 档。
- **期望**：连续 3 天差异率 < 0.1%；无 `ANOMALY/ERROR`。
- **失败意味**：「0 差异」也可能是没生产者，别当「已验证」。
- [ ] 通过

### C2 逐资源放开（enforce-resources）
- **测**：把单资源写进 `enforce-resources`，观察 shadow→enforce 行为切换。
- **期望**：名单内 enforce、名单外 shadow；红着（enforce-readiness 不过）不能改名单（启动期门禁）。
- [ ] 通过

## D. 权限变更事件与 Outbox（P5，本轮新写）

### D1 写侧落库（Recorder）
- **测**：改一条策略 → 查 `permission_change_outbox` 出现一行 `PENDING`，`event_key` 唯一、`payload` 为事件 JSON。
- **期望**：变更与 outbox 同事务（变更回滚则 outbox 无残留）。
- **失败意味**：落不下 = 变更没持久化记录。
- [ ] 通过

### D2 Dispatcher 重投（默认关 → 开）
- **前提**：真实 Redis；`kubo.data-permission.outbox.enabled: true`。
- **测**：手动把一行置 `PENDING` 且 `next_retry_at` 过期；观察 `@Scheduled` 轮询是否把它重投到 `spms:datapermission:changes`、状态变 `DONE`。
- **期望**：到期行被拉取、投递成功 → DONE + processed_at；投递失败 → retry_count+1、按退避排下次、5 次后 DEAD + last_error。
- **失败意味**：Dispatcher 不轮询（查 `@EnableScheduling` 与开关）、或缺 Redis、或缺依赖。
- [ ] 通过

### D3 消费幂等（重复投递无副作用）
- **测**：对同一 event_key 重投多次，观察各节点缓存失效结果。
- **期望**：无副作用（清缓存可重放）。
- [ ] 通过
