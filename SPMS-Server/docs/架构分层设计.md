# 架构分层设计（2026-09-18）

> 这份文档回答三件事：**哪些层**、**谁能依赖谁**、**这条线怎么被机器守住**。
> 所有规则都来自一次实测（不是设计时想象的图），每条例外都**具名**、带理由、带清理批次。
> 机器版判据：`pnpm layer:check`（门禁，进 `pnpm check` 与 CI）。

---

## 一、层（自下而上）

| 层 | 包 | 职责 | 允许依赖 |
| --- | --- | --- | --- |
| **L0** | `cn.hamm.spms.core` | 与业务无关的工具/常量/异常/注解（原 AirPower-Core 自持） | 三方库；**不依赖本仓任何其它包**（实测 0 处） |
| **L1** | `cn.hamm.spms.framework` | 框架层：`framework.api`（HTTP/响应/鉴权）、`framework.curd`（CRUD 引擎/查询模型/权限抽象）、`framework.redis` | `core`；`common.exception`（唯一例外，见 §四）。**要应用的能力时不 import，而是声明契约由应用注册**（前端同款做法：`framework/transport.ts`，见 §八） |
| **L2** | `cn.hamm.spms.base` | 项目骨架基类：`BaseEntity`/`BaseRepository`/`BaseService`/`BaseController`、单据基类、租户感知实体、无条件注册的 Mapper 配置、**`base/spi`（向业务域要能力的契约，见 §四）** | `core` / `framework`；**不得依赖 `module.*`**（白名单已归零，新增即红） |
| **L3** | `cn.hamm.spms.module` | 业务域六个：`asset` / `channel` / `factory` / `personnel` / `system` / `wms`（每域内含 controller / service / repository / mapper / entity / config） | 上面任意层；**跨域只许经对方的 `service`**（L6，见 §3.2） |
| 组合根 | 根包（`Application` / `WebConfig` / `RequestInterceptor` / `DevDataInitRunner`）、`config/`、任何带 `@Configuration` 的**装配类** | 装配与跨域编排（认识所有域是它的职责） | 任意层 |
| 横切包 | `common`（`exception` / `errorreport` / `security` / `filter` / `cookie` / `email` / `sms` / `tree` / `CsvFormulaSanitizer` …） | 与业务无关的横切关注点与工具 | `core` / `framework` / `base` + JDK / 三方库；**不得依赖 `module.*`**（L7：装配类例外） |

**`common` 的定位（2026-09-18 L7 收口）**：它**不是**"任意层"的免检区，而是**横切包** ——
与业务无关的错误码、安全过滤、错误上报、Cookie/邮件/短信、CSV 清洗等。
实测它曾藏着 18 处对业务域的依赖（应用请求管线、灰度引擎、跨域声明式注解），
每一处都让"common 能不能依赖业务域"失去答案；这三类东西现在各有归属：
应用请求管线 → **根包**（跨域编排 = 组合根）、灰度引擎 → **`module/system/config`**（它的存储面就是 config 表）、
跨域声明式注解与字段字典 → **`base/coderule`**（契约在底座、实现在域，同 `base/spi`）。
`common.exception` 另有特殊性：它只依赖 `core`（最底层错误码），被 `framework` 当 SDK 用（规则允许，见 §四）。

**组合根特权**：任何 `*Configuration.java`、带 `@Configuration` / `@ConfigurationProperties` 的装配类、`Application` / `WebConfig` 允许引用任意层 ——
装配 Bean 的地方必然认识被装配的东西，否则装配只能靠反射或字符串，那才是真的坏味道。
（`common` 里的装配类也在此列：它们按**注解**判定，不按文件名 —— `AppConfig` 这类名字不含 "Configuration"，按名字判会漏。）

## 二、包内约定（一个业务域里东西放哪）

以 `module/wms/inventory` 为例：

```
InventoryController.java       HTTP 出入口：只调 service（L5 规则：禁止注入仓储/Mapper）
InventoryService.java          业务编排：调 repository / 其它 service
InventoryRepository.java       CRUD 数据访问（写侧仓储：ICurdRepository + 同名 XML）
mapper/InventoryMapper.java    读侧 Mapper（MyBatis-Plus，开关控制注册）+ 同名 XML
mapper/InventoryWriteMapper.java 写侧 Mapper（无条件注册，永不跟灰度开关消失）
InventoryEntity.java           持久化实体（字段 ↔ 列；MyBatis-Plus 注解口径见 §五）
```

| 产物 | 落点 | 约束 |
| --- | --- | --- |
| SQL | `src/main/resources/mapper/**/*.xml` | **禁止写在 `.java` 里**（门禁 `pnpm sql:check`）；测试夹具在 `src/test/resources/sql/**` |
| 实体 | `module/**.java`（域根）或 `module/**/entity/` | 不得依赖 service / mapper / repository / controller（门禁 L4，实测 0 处违规） |
| 数据访问 | `<域>/mapper/**`（读侧 Mapper）、`<域>*Repository.java`（写侧仓储） | 不得依赖 service / controller（门禁 L3） |
| 服务 | `<域>*Service.java` / `<域>/service/**` | 可依赖本域仓储/Mapper；**跨域只许调对方的 Service**（门禁 L6：对方的 `repository`/`mapper`/`controller` 一律不许 import） |
| 控制器 | `<域>*Controller.java` / `<域>/controller/**` | 只调服务；**不得注入仓储/Mapper**（门禁 L5，本轮把最后 1 处修掉了） |
| 装配 | `<域>/config/**` | 组合根：允许引用任意层 |

**白名单纪律**（脚本里实现）：① 条目必须**仍然存在**（代码已改、白名单没删 = 红，防止白名单长成化石）；② 条目数**只许降**（当前上限 **0**，即一条都不许有）。

### 3.1 `base/spi`：底座向业务域要能力的契约（L2b，2026-09-18）

`base` 要在"所有落库路径的必经点"上挂若干能力，而实现都在 `module.*`。整改的做法是
**契约在 base、实现在业务域**（`module → base` 是允许的那一档），七个契约与实现一一对应：

| 契约（`base/spi`） | 业务域实现 | 底座用在何处 |
| --- | --- | --- |
| `CodeRuleAllocator` | `module.system.coderule.CodeRuleService` | `beforeSaveToDatabase`（补自动编码） |
| `DataPermissionEnforcer` | `module.system.datapermission.service.DataPermissionGuard` | `beforeAdd/beforeUpdate/beforeDelete`（动作级） |
| `RowPermissionEnforcer` | `module.system.datapermission.service.RowWriteGuard` | `beforeSaveToDatabase/beforeDelete`（行级） |
| `SensitiveFieldProtector` | `…datapermission.service.SensitiveFieldProtectorAdapter` | `beforeAdd`（拒绝掩码）/ `beforeUpdate`（恢复原值） |
| `ExportColumnProtector` | `…datapermission.service.ExportColumnProtectorAdapter` | `afterExportQuery`（导出遮蔽） |
| `OperationLogSink` | `…datapermission.service.OperationLogRecorder` | 新增/更新/删除后记账（含动作常量） |
| `SystemConfigSwitch` | `module.system.config.ConfigService` | 单据基类读自动审核开关 |

三条硬约束**不由本门禁管**（它们要读文件内容，属于契约测试的活）：由 `maskContract` 的四条判据盯着 ——（`pnpm test` 里跑）：

1. **字段必须真的被注入**：立一个接口没人用等于保护是摆设 —— 契约类名必须出现在
   `BaseService` / `AbstractBaseBillService` 的字段里。
2. **实现必须是常驻 Bean**：不许 `@Profile` / `@Conditional*`。整改前 `SystemServices` 是
   `@Profile("!test")`，test profile 下守卫直接是 `null`（钩子在、保护没了，日志里毫无痕迹）。
3. **脱敏判定仍是不可替换的静态工具**：`SensitiveWriteProtection` / `ExportColumnMasker` 不做成 Bean
   （做成 Bean 就能被替身换掉，判定会静默失效）；两处适配器**只转发**，不许自己实现判定。

顺带的两次"顺手清掉"：① `SystemServices` 里 `getRowWriteGuard()` / `getDataPermissionGuard()`
已无人使用（本批换成注入），删掉；② `ConfigFlag` / `ConfigType` 两个纯字典枚举下沉到 `base/config`
（判据同 §四 L2a：纯值类型下沉到"用到它的最下层"），业务域侧只改 import。

### 3.2 L6：跨业务域只许经对方的 Service（2026-09-18 新增）

L2 管"上下方向"（base 不许认识 module），L6 管"横向"：`module` 内部六个业务域之间也不许乱伸。

**为什么必须管**：`channel` 直接注入 `wms.output.OutputRepository` 这种写法有三重代价，
而且都不会在编译期报错：
① 两边表结构焊死，一边改列名两边一起红；
② **绕过对方 Service 就等于绕过它挂的全部钩子** —— 动作级/行级数据权限、受限字段写保护、
操作审计都在 `BaseService` 的钩子上，直接读别人的仓储是实打实的越权通道；
③ 依赖图从"域是可替换的单元"退化成一张网。

**允许的跨域形状**：对方的 `service`（业务入口，钩子齐全）、共享值类型
（`entity` / `enums` / `annotation` / 以子域命名的实体包），以及 `base` / `framework` / `core` 里的一切。

**当前实测（2026-09-18）**：跨域 import 对方的 `repository` / `mapper` / `controller` **0 处**，
所以这条规则**没有基线**（对比 JPA 那次是 108/594/473 的棘轮）：
新增一处就是红，不需要"先记下再慢慢还"。跨域 import 的现存形态里 `service` 45 处、
实体/枚举/注解 90 余处，都是这条规则允许的。

### 3.3 L7：`common` 的边界（2026-09-18 新增）

规则一句话：**`common` 只许依赖 `core` / `framework` / `base`，不许 import `module.*`**。

**为什么要管**：旧口径把 `common` 写成"组合/横切，任意层"，于是它成了越层的藏身处 ——
实测 18 处引用业务域，散在三个性质完全不同的地方。它们各自的正确归属是：

| 原位置 | 它其实是什么 | 搬到哪里 | 理由 |
| --- | --- | --- | --- |
| `common/interceptor/RequestInterceptor` | 应用请求管线：串起人员域（令牌/用户）、系统域（权限/数据权限）、工厂域（仓库范围） | **根包** `cn.hamm.spms.RequestInterceptor` | 它是**跨域编排**，不是通用横切件；根包（与 `WebConfig` 并列）就是组合根，认识所有域是职责 |
| `common/feature/FeatureFlagService` | 灰度引擎（规则 DSL 存在 `config` 表） | `module/system/config/FeatureFlagService` | 存储面就是 config 表，复用 `ConfigService`；归到配置域比留在"通用包"清楚 |
| `common/annotation/AutoGenerateCode` + `module/system/coderule/enums/CodeRuleField` | 跨域声明式注解 + 编码字段字典（十几个域的实体都在用） | **`base/coderule/`**（随迁的还有被 `CodeRuleField` 引用的 `SerialNumberUpdate`） | 判据同 `base/spi`：**契约在底座、实现在域**（取号仍在 `CodeRuleService`）；搬 `CodeRuleField` 时撞出了一处门禁盲区，见下 |

**唯一例外：装配类**（带 `@Configuration` / `@ConfigurationProperties` / `@SpringBootApplication`），
逐条打印在门禁输出里 —— 现在只有 `AppConfig`（`@ConfigurationProperties("app")` 里有个
`FileUploadPlatform` 字段）。为什么只对 L7 放宽：framework / base 里的装配类是"框架自己的装配"，
去认识业务域是真越层，仍按原口径拦。

**判据的迭代教训（两条，都是这批实测撞出来的）**：

1. **组合根不能只按文件名判**：第一次判定是 `*Configuration.java`，于是 `AppConfig` / `OpenApiConfig`
   这类"名字里没有 Configuration 的装配类"成了盲区 —— L7 改成按**注解**判定（见 §四）。
2. **`import static X.*;` 必须能被解析**：旧判据的 import 正则遇到通配符**整行不匹配**，
   于是通配符静态导入成了免检通道 —— 本批把 `CodeRuleField` 搬进 `base` 后，
   它那句 `import static ...module.system.coderule.enums.SerialNumberUpdate.*;` 没有触发任何红灯；
   补上解析后门禁立刻报 `[L2] base → module`，随即把 `SerialNumberUpdate` 也下沉到 `base/coderule`。
3. **门禁自己要有反例测试**：盲区是靠"手工塞探针文件"发现的，而手工探针不会留在仓库里 ——
   下一批重构的人照样会以为每一行都被看过。现在 `src/config/__tests__/layeringGate.spec.ts`
   用一份故意违规的夹具树跑真实脚本，逐条断言"会红"，`--check` 必须真的以 1 退出。
   **教训：门禁的"我扫了 445 个文件"不等于"每行 import 都被看过"。**

## 四、例外（每条都有名字与理由）

| 例外 | 内容 | 为什么允许 | 什么时候清掉 |
| --- | --- | --- | --- |
| 组合根 | `*Configuration.java` / 带 `@Configuration`·`@ConfigurationProperties` 的装配类（含 `AppConfig` / `OpenApiConfig` / `CookieConfig`）/ `Application` / `WebConfig` / 根包（`RequestInterceptor` / `DevDataInitRunner`）可引用任意层 | 装配与跨域编排天然需要认识被装配者；用反射回避反而更差 | 永久（判定按**注解**，不按文件名 —— 名字判定会漏掉 `AppConfig` 这类装配类） |
| `framework → common.exception` | `ExceptionInterceptor` 用 `Errors` 做统一错误响应 | `common.exception` 只依赖 `core`（实测），是"最底层错误码"；它是**规则允许**的，不占白名单 | 永久（若将来把它搬进 `core.exception`，这条规则可以直接删） |
| ~~`base → module`~~ | `base/BaseService` 9 条 + `base/bill/AbstractBaseBillService` 3 条：写侧守卫、脱敏、审计、取号 | **L2b 已清**（2026-09-18）：12 → 0，走 `base/spi` 契约（见下一行）。**契约放 `base/spi` 而不是 `framework`**：接口应当住在"使用它的最下层"，放进 framework 等于让内核认识一个它自己永远不用的能力 | 已完成 |
| ~~纯静态工具~~ | `MaskedInputRegistry` / `DataPermissionResourceResolver` / `AttributionWriteProtection` | **L2a 已清**（2026-09-18）：三个只依赖 JDK/base 的静态工具直接下移，白名单 15 → 12。教训：**能搬的下移优先于做接口** | 已完成 |

## 五、本轮（2026-09-18）实测到的三件事 + 处理

1. **`base` 反向依赖 `module`（最严重）**：`base/BaseService` import 了 16 个 `module.system.datapermission` 类型，`base/bill/*` 还 import 了 `ServiceLocation`（`SystemServices` 静态服务定位器）。
   → 本轮先把**纯共享内核**（只依赖 JDK 的 5 个类型）下移到框架层：
   `PermissionContext` / `PermissionContextHolder` / `DataPermissionAction` / `RowParityCounter` → `framework/curd/datapermission`，
   `OperationLog`（审计注解）→ `framework/curd/audit`；全仓 184 处 import/静态导入跟随（`pnpm java:imports` 逐条验证可达性）。
   → 剩下的 15 条钩子进白名单，随后**分批归零**：
   **L2a**（同日）把三个纯静态工具（`MaskedInputRegistry` / `DataPermissionResourceResolver` / `AttributionWriteProtection`）
   直接下移 → 15 → 12；**L2b**（同日）把剩下 12 条改成 `base/spi` 契约 + 业务域实现 → 12 → 0（见 §四）。
   两批的共同判据：**能搬的下移优先于做接口；只有真的要读配置/读实体/落库的能力才值得立接口**。
2. **控制器直接回表**：`UserController` 注入 `TenantRepository`（当时全仓唯一一处真注入）。
   → 补 `TenantService`（本仓"每张表一个 Service"的既有约定），控制器改调服务；`TenantRepository → TenantService → 控制器`。语义一字未改。
3. **Mapper 层依赖服务层的"假阳性"**：`RowParityCounter` 虽是 `service` 包里的接口，但它属于**数据访问侧的契约**（实现者就是各资源的读侧 Mapper）。
   → 随共享内核一起下移到 `framework/curd/datapermission`；20 个 Mapper 的 import 跟着改，L3 从此 0 违规。
   → 同时修正了门禁自己的判据：**按文件名**判定（`*Mapper.java`/`*Repository.java`），不按目录判定 —— `module/**/mapper/` 下还住着 `*ReadShadowService` 这类实现类，按目录判会误报（第一版就是这么错的）。

## 六、与去 JPA 的关系（后续批次的分层动作）

| 批次 | 分层动作 |

| J2（引擎换轨） | `ICurdRepository` 从 JPA 接口退成"引擎契约 + `BaseMapper`"；**新增一处 `@MapperScan`**（`**.repository`，无条件注册）—— 契约测试 `maskContract` 的"注册面只许一处"要升级为"逐个解析 marker 与开关条件"（判据不放宽） |

## 七、怎么验

```bash
pnpm layer:check            # 分层门禁（人读：L0–L7 规则、白名单用量、例外、违规明细）
pnpm layer:check -- --json  # 机器读
pnpm layer:check -- --check # 门禁（违规 / 白名单过期 / 白名单超限 → exit 1）
pnpm sql:check              # SQL 分层（语句只许住 mapper XML）
pnpm java:imports           # import 可达性（没有 javac 时的半个编译器）
pnpm jpa:check              # JPA 归零门禁（0/0/0 + pom 无 starter + yml 无 spring.jpa/ddl-auto + 实体零 JPA 注解）
pnpm front:layer:check      # 前端分层门禁（LF1–LF4）
pnpm java:decl              # Java 声明级门禁（形参重名 / 字段重名）
pnpm vitest run src/config/__tests__/layeringGate.spec.ts   # 两道门禁自己的反例测试
```

> 沙箱无 JDK，这几条是"没有编译器也能守住的线"；类型层面的编译错误仍需要在本机 `mvn -q compile` 收敛。

**这道门禁抓到的真事（2026-09-18）**：L2b 的批量脚本给 `SystemServices.initService` 插参数时插重了一个
（同一签名里 `DataFieldPolicyProvider dataFieldPolicyService` 出现两次），**提交进了仓库、过了 21 道门禁、
没人发现** —— 沙箱里没有 JDK，`mvn compile` 在使用者机器上跑，`mvn compile` 一跑就是红的。
所以补了一道**声明级**门禁（`pnpm java:decl`，第 24 道）：只做 javac 一定会拒绝、纯文本就能判、
**不会误报**的两类 —— 形参重名与字段重名。第一版还写了「同名同参型的方法重复」，
它在文件级文本扫描下会把 `if (...)` / 另一个类里的 `of()` 也算成方法（实测 4 条假命中），
**砍掉**：宁可少一条规则，不要一条会误报的规则（误报的代价是所有人开始忽略它）。

**门禁自己怎么被验**：`src/config/__tests__/layeringGate.spec.ts` 拿两份**故意违规**的夹具树
（`infra/fixtures/layering-java/`、`infra/fixtures/layering-front/`、`infra/fixtures/java-decl/`）跑真实脚本，断言
后端 L0 / L2 / L2-通配符 / L3 / L4 / L5 / L6 / L7、前端 LF1–LF4、Java 声明级 D1–D2 每一条都会红、
`--check` 真的以 1 退出、装配类与前端白名单例外不被误报、注释里的示例不算依赖。
（夹具放 `infra/` 而不是 `src/` 下：`tsconfig` 的 include 只有 `src/**`、eslint 又忽略 `infra/**`，
夹具若是 `.ts` 放在 `src` 里会被类型检查与 lint 当成真代码。）
理由见 §3.3 的教训③：**"我扫了 445 个文件"不等于"每一行 import 都被看过"**。

## 八、前端分层（LF1–LF4，2026-09-18 新增）

后端的分层纪律与前端是两套代码，但**是同一件事**：谁允许认识谁。前端此前只有"目录看着挺整齐"，
实测一量就发现了越界 —— `framework/http.ts` 会去 import `api/axios`（框架层依赖应用装配面），
编译器与 lint 都不拦，只是把"framework 是库还是胶水"这个问题变得没有答案。

| 层 | 目录 | 允许依赖 |
| --- | --- | --- |
| 纯工具 | `utils` / `types` | 只允许 `utils` / `types`（**零出向**） |
| 数据层 | `base` / `model` | 纯工具 + `framework`（模型基类）；**不知道 UI**（`base` 放实体/单据基类，`model` 放业务模型，与后端 `base` 同义） |
| 框架层 | `framework` | 框架内部 + `component` / `base` / 纯工具 / `model`；**不认识应用面** |
| 视图层 | `view` | 任意层（**叶子**） |
| 组合根 | `main.ts` / `App.vue` / `router/**` / `config/routes*` | 任意层（挂载点与路由表的工作就是把路径接到组件上） |

四条规则（`pnpm front:layer:check`，进 `pnpm check` 与 CI）。
**没有硬造规则的地方**：`component` / `hook` / `composables` / `guard` / `demo` / `pwa` 之间互相依赖是正常的，
`styles`·`assets` 没有依赖可言 —— 规则只覆盖"确实有方向"的那几条，宁可少而真。

| 规则 | 内容 | 当前状态 |
| --- | --- | --- |
| LF1 | 非组合根文件不得 import `view/**` | ✅ 0 处 |
| LF2 | `framework/**` 不得 import 应用面（view/api/stores/config/router/composables/hook/guard/demo/pwa） | ✅ 0 处（**接缝**清掉了原来那 2 条例外） |
| LF3 | 数据层（`base/**` 与 `model/**`）不得 import `view` / `component` / `composables` / `hook` | ✅ 0 处 |
| LF4 | `utils/**` / `types/**` 零出向 | ✅ 0 处 |

**那 2 条例外怎么清的（`src/framework/transport.ts`）**：框架的请求出口**必须**是应用那个统一实例
（拦截器、租户头、401 刷新、链路追踪、幂等键、演示适配器都挂在 `src/api/axios.ts` 上），
所以问题不是"要不要用"，而是**依赖方向**。把 `import` 改成**接缝**：

```
  src/api/axios.ts ──注册──▶ framework/transport.ts ◀──取用── framework/http.ts
  （应用装配面）               （框架声明契约）                （框架的请求出口）
```

依赖方向变成 `api → framework`（应用依赖框架，正常），框架里不再有一句提到应用；
白名单从 2 条降到 **0 条，上限也是 0**。

当初不敢拆的理由是"接线漏了会变成**运行期静默无请求**"（页面点了没反应、控制台干净）。
接缝的解法不是"忘了装就算了"，而是**把失败变显式**：

1. 未装配时 `getTransport()` 直接抛错，错误信息里带文件名；
2. 组合根 `src/main.ts` 显式 `import '@/api/axios'`（不依赖"别的模块恰好先加载"）+ 启动自检
   `if (!hasTransport()) throw` —— 漏接就是**启动即失败**，不是等用户点按钮；
3. 契约由 `src/framework/__tests__/transport.spec.ts` 三条用例钉住（自动注册 / 未装配抛错 / 取到的是装进去的那个）。

**判据口径（两个坑，都写进了脚本头部）**：

1. **注释不算依赖**：`composables/useRoutePreload.ts` 的 JSDoc 示例里写着
   `preload(() => import('@/view/home.vue'))` —— 那是**教读者怎么用**，按文本扫会报假违规。
   门禁扫描前先剥注释（与后端 `stripJavaComments` 同一个教训）。
2. **`.vue` 只看 `<script>`**：`<style>` 里的 `@import '@/styles/x.css'` 也长得像 import，
   当依赖处理会得到一堆假边。

两条口径都有反例测试（`infra/fixtures/layering-front/` 里的 `composables/ok.ts`
与 `framework/styleOnly.vue`）—— 判据写错时，第一个人会先怀疑门禁而不是代码。
