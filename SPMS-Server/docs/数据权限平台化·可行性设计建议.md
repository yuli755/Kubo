# 数据权限平台化 · 可行性设计建议（物流仓储方向）

> 触发：使用方提出目标技术底座「Spring Boot 3 + Vue + Vite + Element Plus + ECharts + MyBatis +
> AOP + 自定义注解 + gRPC + Redis + RabbitMQ + MySQL」，目标能力是
> **「多角色协作平台里，不同角色查同一张表自动只看到有权看的行、看不到无权看的敏感字段，
> 且这套逻辑不用改业务代码，加新表也能直接复用」**，并要求可行性设计建议。
>
> 本文逐项对照仓库既有实现（可复现），指出 **3 个必须纠正的认知**、
> **物流场景必须补的 3 个设计**，以及 **gRPC / RabbitMQ 该不该上、什么时候上**。

---

## 0. 结论先行

1. **这套栈没有一项需要换掉**——而且 **10 项里有 8 项仓库里已经在跑**，其中"行级 + 列级数据权限"
   正是现有 `datapermission` 包（**102 文件 / 13,721 行**）在做的事，**你要的能力已经实现**。
2. **两项确实没落地：gRPC、RabbitMQ**（0 依赖 / 0 `.proto` / 0 amqp 引用）。
   我的判断是：**现在都不该上**，理由是它们解决的是「服务拆分后」的问题，而你现在是单体。
   下面给出「什么时候该上」的判据与最小设计。
3. **你的「一句话」描述是对的，但要做到需要 3 条纪律**，否则会得到一个
   「看起来有权限、实际到处漏」的系统。这 3 条下面展开。
4. **物流场景必须补 3 个设计**：**货主（OWNER）维度**（现有维度枚举里**没有**）、
   **作业动作模型**、**动态上下文维度**（当前工位/波次）。

## 2. 必须纠正的 3 个认知（否则一定做歪）

### 2.1 ❌「行级权限用 AOP 实现」 —— AOP 做不到行级过滤

AOP 只能包住 **Java 方法**。而「同一张表不同角色看到不同行」是 **SQL 层面**的事：
你必须在 SQL 真正执行前改写它（加 `WHERE` 条件），否则数据已经从库里取出来了。

**正确分工（仓库就是这么做的）**：

```
AOP  = 身份上下文注入 + 决策 + 审计（不做过滤）
SQL 改写 = 真正的行级过滤（MyBatis-Plus DataPermissionInterceptor + JSqlParser）
```

为什么必须用 SQL 改写：它**同时覆盖** `getPage` / `getDetail` / `getCount` / `getStat` / `export`，
连 `COUNT(*)` 和分页总数都是过滤后的（否则前端"共 100 条"会泄露真实行数）。
仓库为此在 `pom.xml` 特意显式引入 `mybatis-plus-jsqlparser`（注释写明：只引 starter 不引 jsqlparser，
任何 InnerInterceptor 都不可用）。

### 2.2 ❌「列级脱敏用 AOP 反射改写返回对象」—— 这是仓库**踩过并放弃**的坑

`ColumnMaskingAspect` 的类注释明确记录了历史实现的**两个致命问题**：

1. 这些实体是 **JPA 托管对象**，被反射改写后有**把脱敏值持久化回库**的风险；
2. `@SensitiveField` 多标在 `Double price` 这类**数值字段**上，
   `field.set(obj, "1*.*5")` 会抛 `IllegalArgumentException` → **脱敏一开就 500**。

**正确做法**：脱敏放在**序列化层**（`SensitiveFieldSerializer`），
不触碰持久化对象、自动覆盖所有 JSON 出口；AOP 只保留「不经过 Jackson 的出口告警 + 可见性诊断」。

> 👉 若你自己重写：**千万别用 AOP 反射改写实体**。这是这套体系里最容易踩、也最贵的一个坑。

### 2.3 ⚠️「加新表直接复用」是可达的，但**不是零配置**

要做到"不改业务代码"，前提是三条**纪律**，缺一条就会出现"看起来配了、其实没生效"：

| 纪律 | 内容 | 不遵守的后果 |
| --- | --- | --- |
| ① 绑定 | Mapper 必须标 `@DataResource(key)`，且 `data_resource` 有该行 | 拦截器**不认识这条 SQL** → enforce 下**恒假**（查不到任何数据） |
| ② 维度列 | 表必须有维度列（`tenant_id` / `creator_id` / `dept_id` / `warehouse_id`）且有命名约定 | 策略配了也**绑不上列** → 不生效 |
| ③ JOIN 纪律 | **不 JOIN 未登记的表** | JOIN 表成为**权限旁路**（从另一个方向看到不该看的行） |

仓库为此做了**五类盘点**（缺口 / 惰性策略 / 永不命中 / 维度绑定 / 策略指向缺失资源），
并在 `deny-unregistered` 打开时**未登记即拒绝**。

> 👉 一句话：**"零业务代码改动"是真的；"零配置"是假的**。任何声称"零配置"的方案，最终都会在
> 生产上表现为"某些查询悄悄多返回了数据"。

## 3. 物流仓储：必须补的 3 个设计

### 3.1 🔴 补「货主（OWNER）」维度 —— 现有维度枚举里没有

现有 `DataPermissionSubjectType`：

```java
USER, ROLE, DEPARTMENT, FACTORY, WAREHOUSE, TENANT, SYSTEM
```

**有仓库、有工厂、有租户，但没有货主**。而 3PL / 云仓的核心场景恰恰是：

> 一个仓库同时服务多个货主；仓管员 A 负责货主甲、仓管员 B 负责货主乙，
> **A 绝不能看到乙的库存、订单、收货人信息**。

这是**物流区别于通用制造**的第一维度。建议：

- 维度枚举新增 `CARGO_OWNER`（或 `OWNER`）；
- 主数据加 `cargo_owner` 表（货主：编码/名称/结算主体/联系人）；
- 业务表加 `owner_id` 维度列（库存、入库、出库、移库、盘点、运单）；
- 策略主体支持「用户/角色 ↔ 货主」授权（**多对多**，一个人可负责多个货主）。

> 顺带建议：**把维度做成可扩展的注册表**（`dimension_key` + 解析器 SPI），
> 而不是硬编码枚举——物流行业每个客户要的维度都不同（货主 / 项目 / 线路 / 客户组），
> 硬编码枚举改一次就要发版。

### 3.2 🟡 补「作业动作」模型

现有 `DataPermissionAction` = `QUERY, DETAIL, CREATE, UPDATE, DELETE, EXPORT`（通用 CRUD）。
但物流的**作业动作**对数据可见性要求不同：

| 作业动作 | 典型可见性差异 |
| --- | --- |
| 拣货 | 只需库位 + 物料 + 数量，**不需要**收货人手机号 |
| 复核 / 装车 | **需要**收货人姓名/电话/地址 |
| 盘点 | 需要账面数 + 实盘权限，**不应看到**成本价 |
| 客服查询 | 需要轨迹与收件人，**不应看到**成本与供应商 |

建议：动作维度扩展为「**通用 CRUD + 可注册的作业动作**」，
或引入「**作业角色 × 资源 × 动作**」矩阵，而不是给每个人配一套 CRUD 权限。

### 3.3 🟡 补「动态上下文维度」

物流的可见性往往**不是静态归属**，而是**当前作业上下文**：

> "我此刻在 3 号库区做波次拣货" → 可见范围 = 当前波次 + 当前库区，
> 而不是"我名下所有仓库"。

建议维度解析器支持**从请求上下文取动态值**（工位 / 当前波次 / 当前单据），
并**严格限定来源**（由服务端会话或已校验的请求头决定，不能由前端自由传参，否则等于没有权限）。

## 4. gRPC：现在不该上（附判据与最小设计）

### 4.1 判据：什么情况下才该上

| 问题 | 现在是单体，答案 |
| --- | --- |
| 权限服务会被**多个服务**消费吗？ | ❌ 单体里就是进程内调用 |
| 需要**非 JVM 客户端**吗？ | ❌ 前端走 HTTP，不需要 protobuf |
| 权限计算成为**独立扩缩容瓶颈**吗？ | ❌ 有 Redis 缓存 + 进程内策略树缓存 |
| 团队能承担 protobuf 工具链 + 跨进程调试 + 超时/重试/熔断成本吗？ | ⚠️ 这是主要成本 |

**结论：单体阶段引入 gRPC 是纯成本。** 正确姿势是**先把边界定死，不引入传输**：

```java
// 接口先立，实现留在本地
public interface PermissionRuleProvider {
    PermissionRuleTree loadFor(String resourceKey, PermissionContext ctx);
}
// 现在：LocalPermissionRuleProvider（进程内 + Redis 缓存）
// 将来：GrpcPermissionRuleProvider（真拆分时再加，契约测试保证两个实现同解）
```

仓库施工图 W11–W13 正是这个思路（`permission_rule.proto` + 双实现一致性契约测试），
并**明确标为"后置/可选"**——这是对的。

### 4.2 若坚持要上，最小可行设计（含必须配套项）

必须同时给出：
1. **契约**：`permission_rule.proto`（`GetRuleTree` / `SubscribeChanges`）；
2. **双实现 + 契约测试**：本地实现与 gRPC 实现**同一组用例必须同解**（否则灰度期两套结果）；
3. **降级策略**：gRPC 不可用时**必须降级为"恒假"而不是"恒真"**（降级方向决定安全成败）；
4. **配套**：服务发现（Nacos 已在 compose 里）、超时/重试**上限**、熔断、版本演进策略；
5. **数据面**：权限规则变更如何跨进程生效（这就是下面 RabbitMQ 的用途）。

## 5. RabbitMQ：现在不该上（但有 3 个真实刚需点）

### 5.1 现状与替代

仓库已实现 **outbox 写侧落库 + Redis 重投 Dispatcher**（`permission_change_outbox`）。
对**单实例/多实例共用 Redis** 的场景，**Redis Pub/Sub 已经够用**：
策略变更 → 广播 → 各节点清缓存。

### 5.2 什么时候 Redis Pub/Sub 不够

| 需求 | Redis Pub/Sub | RabbitMQ |
| --- | --- | --- |
| 广播失效通知（丢一条无妨，下次查询会自愈） | ✅ 够 | 过度 |
| **可靠投递**（不丢、需重试/死信） | ❌ 不保证 | ✅ 必须 |
| **消费者组 / 竞争消费 / 积压削峰** | ❌ | ✅ |
| 跨服务、跨语言集成 | 弱 | ✅ |

### 5.3 物流场景下 MQ 的**真正刚需点**（不是权限，是业务）

1. **作业指令下发**：波次 → RF 手持终端（不能丢、要重试）；
2. **异步导出 / 报表**：大导出不阻塞请求线程；
3. **外部系统集成**：快递面单、ERP、TMS、温控设备上报。

> ⚠️ **落地风险（必须知道）**：仓库 **CI 依赖黑名单明确禁止 `spring-boot-starter-amqp`**，
> 且 `infra/rabbitmq/definitions.json` 已备好但代码零引用。
> 启用 MQ 需**同步修改 CI 白名单 + 安全评审**（消息体可能含业务数据，等同新的数据出口）。

**结论**：MQ 留给**业务**（作业指令/导出/集成），**不要为权限广播引入 MQ**。

## 6. 落地路线（建议分 4 阶段）

| 阶段 | 做什么 | 产出 | 工作量 |
| --- | --- | --- | --- |
| **S1 抽出** | 把 `system.datapermission` 抽成**独立模块/包**（现仅依赖 `base` + `user` + `tenant` + `permission`，耦合很轻） | `kubo-datapermission` 模块 | 3–5 天 |
| **S2 补维度** | 新增 **CARGO_OWNER** 维度 + 维度注册表（SPI）+ 作业动作模型 | 物流可用的维度体系 | 1–2 周 |
| **S3 配置面** | 策略配置 UI（已有雏形：资源/行级/列级三页）+ 生效度看板 + 五类盘点 | 运维可自助 | 1 周 |
| **S4 按需分布式** | 真拆分时才上 gRPC / MQ（§4 §5 判据） | — | 视拆分 |

**S1 的关键收益**：把「仓库里的一个包」变成「**可复用、可演示、可交付**的能力」——
这正好对应你想要的"在一个多角色协作平台里做数据权限这块"。

## 7. 一句话回答

> **栈没问题（10 项里 8 项已在跑），但光有栈不等于有能力。**
> 这套东西真正的难点在 3 个认知（AOP≠行级过滤、反射改写≠列级脱敏、"零配置"是假的）
> 和 3 个物流专属设计（货主维度、作业动作、动态上下文）。
> gRPC 与 RabbitMQ 现在上都是纯成本——它们是**拆分之后**的解法，
> 而你现在要的是**先把单体的能力做深、做成可复用模块**。
>
> 顺带说一句：**你要的这套能力，仓库里已经写完了 13,721 行**，且踩平了 6 个安全坑。
> 最省力的路线不是重写，而是**把它抽出来、补上货主维度、做成可交付的模块**。
