# 异步运行时面安全审计（WebSocket 消息面 + 定时任务）

> 触发：生产级审查「全方位/深层次/多维度审核」的延续。请求-响应面（HTTP 端点）已在
> `公开端点安全审计.md`、`导出与注入面安全审计.md` 收口，本文补上**两条非请求-响应路径**：
> WebSocket 长连接消息面 与 `@Scheduled` 定时任务面。

---

## 0. 结论先行

1. **WebSocket 消息面：鉴权正确，无跨房间/跨租户注入面**。握手按 JWT 建 `userId→session`，
   未认证会话直接丢弃；房间频道订阅由「加入房间」流程（房号 + 密码）服务端门控，客户端**无法**
   任意订阅他人频道；消息只发往「发送者自己的当前房间」。真正差距是**文档把设计愿景当已实现**
   （§1.3），以及聊天室密码的两处低危卫生问题（§1.4，其一已本轮修复）。
2. **定时任务面：两个任务实现健康**（配置门控、可选依赖降级、逐行/逐表错误隔离、幂等消费）。
   唯一发现：**多实例部署无分布式选主**，多个副本会并发跑同一任务——靠幂等消费/幂等删除兜底
   「不产生数据错误」，但属冗余放大，建议多实例化前补选主（§2.3）。

---

## 1. WebSocket 消息面

### 1.1 实际鉴权链（代码为准）

airpower `WebSocketHandler`（框架）+ `AppWebSocketHandler`（本项目）共同构成：

| 环节 | 实现 | 安全结论 |
| --- | --- | --- |
| 握手 | `afterConnectionEstablished` 读 `session.getUri().getQuery()` 里的 `accessToken` → `AccessTokenUtil.verify(token, secret)` → `payloadId`（= userId） | ✅ 无 token 直接 `closeConnection` |
| 会话绑定 | `userIdHashMap.put(session.getId(), userId)` | ✅ 后续消息都靠它取 userId |
| 自动订阅 | 每连接自动订阅 `WEBSOCKET_ALL`（全局）+ `WEBSOCKET_USER_<userId>`（个人频道） | ✅ 个人频道按 userId 隔离 |
| 房间订阅 | `subscribe("group_"+roomId, session)` **只在 `AppWebSocketHandler` 加入房间鉴权通过后**调用 | ✅ 服务端门控，客户端不能任意订阅 |
| 消息入口 | `onWebSocketPayload` 先查 `userIdHashMap`，取不到 userId 直接 return | ✅ 未认证会话无法触发房间事件 |
| 消息出口 | `publishToUserRoom(userId, …)` 只发往 `userService.getCurrentRoomId(userId)`（发送者自己的当前房间） | ✅ 无跨房间注入 |
| 房间密码 | `checkIfNeedPassword`（私有房间 + MEMBER/VISITOR 角色）→ `room.getPassword().equals(...)` | ✅ 本轮把 `equalsIgnoreCase` 改 `equals`（§1.4） |

### 1.2 客户端「任意订阅」不可行（纠正文档一处不准确）

`WEBSOCKET_PROTOCOL.md` §0 写「客户端发 `{ type: 'subscribe'|'unsubscribe', data: channel }`」——
这与当前代码不符：框架 `handleTextMessage` 只处理 PING/PONG 与 `onWebSocketPayload`，
`subscribe`/`unsubscribe` 是 `protected final`，**只有 `AppWebSocketHandler` 能调**，客户端没有
任何消息类型能触发任意频道订阅。这是「防御性正确的实现」，只是文档描述错了方向（把服务端
门控写成了客户端动作）。

### 1.3 设计愿景 vs 实际实现（诚实化）

`WEBSOCKET_PROTOCOL.md` §11「安全考量」表里的这些是**设计愿景、当前未实现**，不应被误读为已上线：

| §11 声称 | 实际 |
| --- | --- |
| 消息体 JSON Schema 校验 | ⚠️ 部分落地：类型白名单 + 消息体长度上限（`WebSocketMessageGuard`，§1.5）；字段级 Schema 仍缺 |
| 连接/用户/租户多维限流（Token Bucket） | ⚠️ 部分落地：每用户发送限流 120/min（复用 `RateLimitHelper`，§1.5）；连接/租户维度仍缺 |
| 敏感字段 AES-GCM 加密 | ❌ 未实现 |
| 防重放（消息 ID 幂等 + 时间戳窗口） | ❌ 未实现 |
| 全链路审计（连接/订阅/发送/ACK） | ❌ 未实现（仅框架 debug 日志） |
| 订阅时二次校验权限 | ⚠️ 部分等价：房间订阅由「加入房间」流程门控，但无独立订阅鉴权层 |

> 上表两项「部分落地」是本轮（第十七批）补的：把性价比最高的「输入白名单 + 长度上限」与
> 「发送限流」落成纯逻辑 + 契约测试（§1.5），其余（字段级 Schema / 连接与租户维度限流 /
> AES-GCM / 防重放 / 全链路审计）仍是增强项、非当前可利用漏洞——房间频道门控 + 个人频道隔离 +
> 消息出口锁定发送者房间已把跨房间/跨租户读取堵死。

### 1.4 聊天室密码卫生（低危）

1. **大小写敏感（✅ 第十六批已修）**：`AppWebSocketHandler` 原用 `equalsIgnoreCase` 比对房间密码，
   `RoomPass`/`roompass`/`ROOMPASS` 同码，削弱口令熵。已改 `equals`。
2. **明文落库（⚠️ 待拍板）**：`RoomEntity.password` 是 `varchar(255)` 明文（虽有
   `@JsonProperty(WRITE_ONLY)` 不外泄）。聊天室口令属低敏场景，哈希化需迁移存量明文、属行为
   变更，建议与业务确认后再动；过渡期至少确认「房间密码不复用其他系统口令」。

### 1.5 输入守卫落地（`WebSocketMessageGuard`，✅ 第十七批）

在 `AppWebSocketHandler.onWebSocketPayload` 入口（鉴权之后、事件分发之前）加三层守卫：

1. **事件类型白名单**：只放行客户端→服务端的 `ROOM_MEMBER_JOIN`/`ROOM_MEMBER_LEAVE`/
   `ROOM_TEXT_MESSAGE`；其余（服务端→客户端事件、系统事件、未知值、非数字）一律丢弃。
   顺带消掉了 `ChatEventType.getByStringKey` 对非数字输入 `Integer.parseInt` 抛 NFE 的「异常路径」，
   改为「白名单前置判断」。
2. **消息体长度上限**：`data` 超过 8192 字符即丢弃，堵住超大文本经 Redis 频道**放大**广播给
   全房间成员（带宽/内存放大）。
3. **每用户发送限流**：复用 `RateLimitHelper`（Redis 固定窗口）按 userId 计数，120 条/分钟；
   Redis 不可用时降级放行，与公开端点限流同口径——只防脚本刷屏、不误伤真人聊天。

契约测试 `WebSocketMessageGuardTest` 5 用例锁白名单与长度边界（客户端三事件放行 / 服务端与系统
事件拒绝 / 非数字与 null 拒绝 / 长度边界 / 限流常量自洽）。计数逻辑由既有的 `RateLimitHelperTest`
覆盖，此处不重复。

## 2. 定时任务面

### 2.1 任务清单（代码事实）

| 任务 | 调度 | 门控 | 隔离 |
| --- | --- | --- | --- |
| `PermissionChangeOutboxDispatcher.dispatchDue` | `fixedDelay` 5s（可配） | `outbox.enabled`（默认关）+ 缺依赖跳过 | 逐行 try/catch，单行失败不影响其余行 |
| `DataPermissionEvidenceRetention.purgeExpiredEvidence` | `cron 0 15 3 * * *`（可配） | `retention-cleanup-enabled` + `retention-days>0` | 三张表分别 try/catch，缺表返回 0 |

### 2.2 审计结论（健康项）

- **状态迁移纯逻辑**：Outbox 的状态迁移只走 `OutboxDispatchStep`、退避只走
  `PermissionChangeOutboxBackoff`，纯静态、可测，不重抄。
- **幂等消费**：`DataPermissionEventListener` 按事件幂等处理，重复投递无副作用（注释已声明）。
- **失败取向正确**：Dispatcher 单行失败各自退避、下次重试；Retention 清理失败只影响观测表、
  不碰请求链路，下一轮重试。
- **可选依赖降级**：两任务都用 `ObjectProvider.getIfAvailable()`，仓库/Redis 未就绪时跳过而非
  启动即崩（H2 本地跑时不炸）。

### 2.3 发现：多实例无分布式选主（低危）

`@EnableScheduling` 是每实例独立启动的。若 k8s 起多副本，**每个副本都会**每 5s 拉同一批到期
Outbox 行、每天凌晨清一次同一批证据：

- `findTop100ByStatusAndNextRetryAtLessThanEqualOrderByIdAsc` 无 `FOR UPDATE SKIP LOCKED`，无
  「先原子认领再投递」的 UPDATE 守卫 → 多副本会**重复投递同一行**；
- 后果被两处兜底吸收：消费端幂等（重复事件无副作用）+ 证据删除幂等（删已删行返回 0），
  故**不会数据错误**，但会放大 Redis 发布量与 DB 查询量（N 副本 × 同一批）。

**建议**：当前单实例部署（docker-compose 单后端）无需处理；若多实例化，优先引入轻量选主
（如 ShedLock，或复用项目已有 `RedisHelper` 的 `setIfAbsent` 做 leader key + TTL），把这两个
`@Scheduled` 包进「只有 leader 执行」的分支。属部署形态变更，未擅自改动。

## 3. 与其它能力的关系

- **公开端点限流**（`RateLimitHelper`）：管 HTTP 请求面；WebSocket 消息面当前无限流，属 §1.3
  的增强项，与 HTTP 限流是两套关切。
- **数据权限 Outbox**（`PermissionChangeOutboxDispatcher`）：与 `公开端点`/`导出` 无直接关系，
  但它是「数据权限变更不丢」的恢复路径，多实例选主建议与数据权限 enforce 灰度同批评估。
- **文件上传/导出**：均属请求-响应面，已在前两篇审计收口；本文补的是长连接与定时两条路径，
  至此「进/出/异步」三类面均有结论。
