# 可观测性与告警加固方案（第七批 · 告警 + APM）

> 触发：生产级审查报告 §9 的第七批第 2、3 项（告警规则 + APM 全链路采集）。
> 本文基于代码事实盘点现状，给出分阶段、可落地的方案；**运维栈部署（Prometheus/Grafana 等）与
> 告警阈值需在真实环境标定，故本批以方案为主，代码改动仅「traceId 打通」一项可本地验证**。

---

## 0. 结论先行

可观测性目前**只有「日志」这一根支柱，且链路是断的**：

1. **traceId 链路断在前端**：后端 airpower 已完整支持 traceId（`CurdRequestInterceptor` 读请求头
   `HttpConstant.Header.TRACE_ID` → `TraceUtil.setTraceId` → MDC `X-Trace-ID` → logback 打印
   `TRACE_ID=%X{X-Trace-ID}`；`CurdResponseInterceptor` 按 `bodyTraceId` 把 traceId 回写到响应
   body 或 header）。但**前端 axios 请求拦截器不发送该头**，也不从响应提取 traceId —— 于是后端
   日志的 `TRACE_ID` 永远是空（或框架兜底值），用户报障时**无法把「前端的一次操作」关联到
   「后端的一串日志」**。
2. **InfluxDB 是业务数据，不是系统监控**：`InfluxHelper` 写的是 IoT 设备上报（quantity/switch/
   status 等），给报表用；CPU/内存/GC/慢查询/请求延迟/错误率等**系统指标无任何采集**。
3. **告警规则「有文件、无闭环」**（勘误 2026-09-10）：`infra/prometheus/rules/alerts.yml` 已有一份
   相当完整的告警规则（实例/JVM/API/MQ/DB/Redis/磁盘/CPU/WebSocket/业务/安全），`prometheus.yml`
   也配了抓取目标。但整套配置是**按「目标态微服务 + K8s」写的，与当前「单体 + Docker」现实脱节**：
   - 后端 pom 只有 actuator、**没有 `micrometer-registry-prometheus`** → `/actuator/prometheus`
     端点不存在 → Prometheus 抓不到任何 JVM/API 指标；
   - `prometheus.yml` 用 `kubernetes_sd_configs` 服务发现，实际部署是 docker-compose（无 K8s）；
   - `alerts.yml` 大量规则引用代码**未暴露**的指标（`rabbitmq_*`、`inventory_stock_quantity`、
     `order_processing_duration_seconds`、`ws_reconnect_total`、`auth_login_failed_total`、
     `mysql_slave_status_seconds_behind_master`），且 RabbitMQ 组件代码根本没接；
   - `alerting.alertmanagers.targets` 为空 `[]` → 告警触发也**无处可送**，docker-compose 里也没有
     alertmanager 服务。
   结论：告警规则是「愿景态半成品」，从未真正闭环过。**配置侧已于 2026-09-10 闭环**：
   prometheus.yml 静态 targets 化 + alerts.yml 瘦身 + alertmanager 服务 + 静态门禁
   `monitoring:check`（详见 §2/§3）。应用层指标（JVM/HTTP）仍待后端引入
   micrometer-registry-prometheus。落地方向见 §3 第七批第 2 项。
4. 前端错误上报已留好钩子（`src/utils/errorHandler.ts` 的 `setErrorReporter`），待接监控栈。

结论：先**打通 traceId**（本地可验证、零风险），再**接指标 + 告警**（需运维栈，按阶段推进）。

## 2. APM 全链路采集（第七批第 3 项）

### 第一步：打通 traceId（✅ 已落地 2026-09-10 · 本地可验证 · 零风险）

> 前置确认：`HttpConstant.Header.TRACE_ID` 的确切字符串值（airpower 框架内部常量，约
> `X-Trace-Id`）。落地前用 CI 的 framework-intel 通道或反编译 jar 确认，**发错头名不会破坏功能、
> 只是链路不通**，故这步本身零风险。

- **请求侧**：`src/api/axios.ts` 请求拦截器生成 `crypto.randomUUID()`，写 `config.headers` 的
  `TRACE_ID_HEADER`（常量，当前 `X-Trace-Id`）头，并挂到 `config.traceId` 供错误分支回填。
- **响应侧**：业务错误分支回填 `res.traceId`（airpower `bodyTraceId=true` 时响应 body 带 traceId）；
  状态码错误分支回填 `data.traceId` / 响应 header；网络错误回退到请求侧 `config.traceId`。
  `ApiError` 增加 `traceId` 字段，使前端错误与后端日志可关联。
- **验收**：一次操作后，前端报错带 traceId = 后端日志 `TRACE_ID`。
- **待办**：header 名与 airpower jar 核对后，若不一致只需改 `TRACE_ID_HEADER` 一个常量。

### 第二步：系统指标（需运维栈）

- **引入 `micrometer-registry-prometheus`（✅ 理论代码已落地 2026-09-10）**：`pom.xml` 已加
  `io.micrometer:micrometer-registry-prometheus`（版本由 Spring Boot BOM 管理），
  `application-production.yml` 的 `management.endpoints.web.exposure.include` 已追加 `prometheus`。
  本机 `./mvnw compile` + 启动后 `/actuator/prometheus` 才有数据（沙箱无 JDK/Maven 依赖无法自测）。
- 采集四类指标：JVM（堆/GC/线程）、HTTP（请求数/延迟/错误率，Spring MVC 自带）、
  HikariCP（连接池活跃/等待）、数据权限/outbox 业务计数器（已有审计，可加 Micrometer counter）。
- Prometheus 抓取 + Grafana 面板（导入 JVM/Hikari 现成 dashboard，再补业务面板）。
- **现状衔接**（✅ 配置侧已落地 2026-09-10）：`infra/prometheus/prometheus.yml` 已从 k8s 服务发现
  改为 docker-compose 静态 `targets`（prometheus 自身 / node-exporter / redis-exporter /
  mysql-exporter / spring-boot-actuator 五个 job）；`alerts.yml` 已瘦身为「真实可采集」集
  （基础设施 up / node_* / redis_* / mysql_* 11 条 + 应用层 jvm_* / http_* 7 条，共 18 条），
  引用未暴露指标的规则（rabbitmq_*、业务指标等）已删除；`infra/alertmanager/alertmanager.yml` 与
  docker-compose 的 alertmanager / node-exporter / redis-exporter / mysql-exporter 服务已补上；
  新增静态门禁 `monitoring:check`（YAML 语法 / alertmanager 有处可送 / target 真实存在 / 无愿景
  指标，内嵌自检防空转）。spring-boot-actuator 的 target 用 `host.docker.internal:8080` 占位
  （后端当前在宿主单独跑，容器化进 compose 后改 `kubo-server:8080`）。

### 第三步：分布式追踪（可选演进）

- 接 OpenTelemetry（OTel agent 无侵入）或 SkyWalking，把单点 traceId 升级为跨服务全链路。
- 当前单体 + Redis + MySQL + WebSocket，**不是必须**；等真正拆分服务再上。

## 3. 告警规则（第七批第 2 项）

告警建立在第二步的指标之上，用 Prometheus Alertmanager（或 Grafana Alerting）触发，通道接
邮件 + 企业 IM（钉钉/企微）。**配置侧已落地（2026-09-10）**：`alerts.yml` 已瘦身为「真实可采集」
最小集、`infra/alertmanager/alertmanager.yml` + docker-compose 的 alertmanager 服务已补上
（webhook 用 `example.invalid` 占位，待真实环境填钉钉/企微通道）；应用层告警（jvm_* / http_*）
已注释挂起，待后端暴露 `/actuator/prometheus` 端点后取消注释启用。

以下是**最小可用告警集**（阈值需按真实负载标定，此处给默认值）：

| 告警 | 指标/条件 | 默认阈值 | 级别 |
| --- | --- | --- | --- |
| 接口错误率 | `http_server_requests` 5xx 占比 | 5 分钟 > 5% | P1 |
| 慢请求 | 接口 P99 延迟 | > 2s | P2 |
| 数据库连接池耗尽 | HikariCP 等待线程 | > 0 持续 1 分钟 | P1 |
| JVM 堆使用 | heap used / max | > 85% 持续 5 分钟 | P2 |
| 频繁 GC | GC 次数/时长 | 1 分钟 FullGC > 5 次 | P2 |
| 磁盘占用 | 日志/数据盘 | > 80% | P1 |
| 实例存活 | `up` / readiness 探针 | 探针失败 30s | P0 |
| Outbox 积压 | 数据权限 outbox 待重放数 | > N 持续 10 分钟 | P1 |
| 前端错误率 | `errorHandler` reporter 上报量 | 突增（环比） | P2 |

> 告警必须「可行动」：每条都要能指向排障动作（看哪张面板、查哪段日志、回滚哪个变更），
> 否则告警疲劳比没有告警更糟。
