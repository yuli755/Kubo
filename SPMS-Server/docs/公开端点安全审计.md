# 公开端点（未认证）安全审计与限流加固

> 触发：生产级审查「全方位/深层次/多维度审核」的延续。登录防爆破（`07b9cc0`）与错误上报限流
> （`ed97046`）只覆盖了两类公开端点；本文把**全部 `@Permission(login = false)` 出口**盘点一遍，
> 逐一定性暴露面，并对「未认证 + 可枚举 + 无限流」的采集端出口补限流。
> 原则：**限流只做 DoS 防护、不做认证**；需要认证语义的端点应加令牌/API-Key，而不是靠限流冒充认证。

---

## 0. 结论先行

1. **公开端点共 9 处**（§1 全量清单），绝大多数已有防护（令牌校验 / 签名 / 防爆破），**真正缺口是
   设备采集端的 3 个读出口**——未认证、按 ID 可枚举、无限流。
2. **已落地加固**（本批）：
   - 新增可复用 `RateLimitHelper`（固定窗口 Redis 计数 + 降级放行），把此前分散在登录/错误上报的
     「IP 解析 + 计数」收敛为一处；
   - 设备采集端 3 出口接入限流（单 IP 3000 次/分钟，DoS 防护阈值、刻意宽松防误伤 NAT 内网）；
   - 新增错误码 `REQUEST_TOO_FREQUENT(103)`；
   - 清理 `AppWebSocketHandler` 过时 `// todo 密码不正确` 注释（功能早已实现）。
3. **剩余建议（需设计决策，未擅自改动）**：设备采集端的**认证**本身仍是「UUID 当弱令牌」——
   正式方案建议给设备加 API-Key / UUID 签名（§3），这是业务决策，需用户拍板。

## 2. 已落地的加固（本批代码）

### 2.1 `RateLimitHelper`（`common/security/RateLimitHelper.java`）

统一「按 key 计数 + 过期」的固定窗口限流原语：

- `allow(key, limit, windowSeconds)`：窗口内超 `limit` 拒绝；首次计数设过期（key 不泄漏）；
  Redis 不可用降级放行（与防爆破守卫同口径）。
- `allowByIp(request, keyPrefix, limit, windowSeconds)`：解析客户端 IP（X-Forwarded-For 首个 /
  X-Real-IP / remoteAddr）后按 IP 限流；取不到 IP 放行。
- 契约测试 `RateLimitHelperTest` 6 用例：窗口内放行 / 超限拒绝 / 首次设过期 / Redis 降级 /
  XFF 取 IP / 无 IP 放行。

### 2.2 设备采集端接入

`DeviceController` 的 `getCurrentReport` / `getDeviceConfig` / `getDevicePayloadHistory` 三个
`login=false` 出口，统一 `REQUEST_TOO_FREQUENT.when(!rateLimitHelper.allowByIp(...))`，
阈值 `MAX_REQUESTS_PER_MINUTE = 3000`（单 IP 50 QPS，采集端轮询远达不到，纯防扫描枚举与 DoS）。

### 2.3 错误上报端点复用

`ErrorReportController` 原先内联的限流 + IP 解析逻辑，改为复用 `RateLimitHelper`（行为不变，
删除重复代码）。

## 3. 剩余建议（需业务决策，未擅自改动）

### 3.1 设备采集端认证（关键缺口，非限流能补）

现状：`getDeviceConfig` 用设备 **UUID** 当令牌、`getCurrentReport`/`getDevicePayloadHistory` 用
**数字 ID**。风险：

- ID 可枚举（自增），攻击者可遍历读任意设备实时数据/历史；
- UUID 熵高但仍是「知道即通过」的弱令牌，且 UUID 一旦在日志/配置里泄露即失效。

建议（按落地成本排序）：

1. **设备 API-Key**：设备注册时签发随机 API-Key（`DeviceEntity` 增 `apiKey` 列），采集端带
   `X-Device-Key` 头访问；后端校验 + 绑定设备，读出口按「当前设备」过滤，堵死跨设备枚举。
2. **UUID 签名**：复用 open 平台已有的 RSA/AES 签名链（`AirPowerJavaSdk` 语义），设备侧签名请求。
3. 过渡期：至少把 `getCurrentReport`/`getDevicePayloadHistory` 从「按 ID」改成「按 UUID」，
   消除最直接的枚举面。

> 这是一次**采集终端与后端的协议变更**，需设备端协同发版，故列为待拍板项，未擅自动。

### 3.2 MCP `getMcpTools` 信息泄露

`/mcp/getMcpTools` 未校验任何凭证，直接返回 `McpService.tools`（内部工具清单 = 能力枚举，且可能
含工具参数 schema）。建议：与 `/mcp` 同口径校验 `?token=`，或干脆去掉该端点、由 `/mcp` 的能力协商
返回工具列表。影响面小，可单独排期。

### 3.3 观察项（暂不改）

- `OpenAppController.getByAppKey`：open 平台登记查询，AppKey 即弱令牌；若后续 AppKey 泄露面变大，
  再评估是否收紧。当前与 open 平台签名链一致，属设计内。
- `coderule` 两个字典端点：只返回编译期枚举元数据，无数据、无副作用，保留 `login=false` 无碍。

## 4. 与其它能力的关系

- **登录防爆破**（`LoginBruteForceGuard`）：失败计数+锁定，与 `RateLimitHelper` 的固定窗口是两种
  语义（前者「行为阻断」、后者「流量削峰」），各自保留、不合并。
- **SLO/SLI**（`SLO与SLI定义.md`）：限流拒绝会体现为 403/业务错误码，不应计入「5xx 可用性」，
  但可作为「恶意流量」面板的信号。
- **错误上报**（`/api/error-report`）：采集端被限流后，若终端上报 `context=device` 错误，可在 Loki
  观察到「限流误伤」迹象（正常终端突然大量 `REQUEST_TOO_FREQUENT`），辅助阈值标定。
