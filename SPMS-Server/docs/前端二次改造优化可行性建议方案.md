## 0. 结论先行（TL;DR）

1. **`law-firm-platform` 对本项目的借鉴价值有限**：它是单租户 CRUD 教学级项目（Vue 3.5 + Element Plus +
   Pinia + ECharts，手写 axios、无 typed client、无测试门禁）。Kubo 前端在技术栈与工程化上**全面领先**，
   不建议照搬任何技术选型。真正值得借鉴的只有**两个功能形态**：① 角色差异化工作台看板；② 通用操作审计日志切面。

2. **Kubo 前端的重点不是「换框架」，而是「补机制」**：F0–F4 已基本完成（权限收口 / 脱敏消费 / 数据层收敛 /
   数据权限管理界面），真正的增量价值在「把已有的数据权限可观测性 composable 变成可运营的看板」和
   「补一条通用操作审计闭环」，以及「测试覆盖硬化」。

3. **推荐推进序**：P0 决策拍板（需产品）→ P1 读侧换轨收尾（我可独立推进）→ P2 数据权限感知看板 →
   P3 通用操作审计日志 → P4 前端测试覆盖硬化 → P5 Outbox 消费幂等（后端）。

## 1. 参考项目评估（law-firm-platform vs Kubo）

| 维度 | law-firm-platform | Kubo 现状 | 结论 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3.5 + Vite 6 | Vue 3.5 + Vite 7 | 持平 |
| UI 库 | Element Plus 2.9 | Element Plus 2.12 | 持平 |
| 状态管理 | Pinia 3 | Pinia 3 + **TanStack Vue Query 5**（服务端状态与客户端状态分离） | Kubo 领先 |
| 接口层 | 手写 `api/` 封装 | `openapi-typescript-codegen` 生成的 **typed client** + `@/api` 模块 | Kubo 领先 |
| 数据可视化 | ECharts 5.5（看板用） | ECharts 6（仅 `device/history` 用，**无看板**） | law-firm 有看板，Kubo 缺 |
| 工程化 | 无 lint/test 门禁 | ESLint(antfu) + strict TS + vitest + 体积预算 + PWA | Kubo 领先 |
| 权限 | 角色菜单（RBAC） | 角色菜单 + **行级/列级数据权限 + 五类盘点面板 + 前后端权限码一致性门禁** | Kubo 领先 |
| 审计 | `audit_log` 表 + `@Aspect` 审计日志切面 | 数据权限 deny/evidence 日志（B4），**无通用操作审计** | law-firm 有通用审计，Kubo 缺 |
| 定时任务 | `@Scheduled` 巡检逾期账单 | `ServiceCron`（已有） | 持平 |
| 多租户 | 名义多租户，无行级隔离 | 真多租户（tenant_id/creator_id + 三态 enforce + 影子对账） | Kubo 领先 |

**结论**：除「看板」和「通用审计日志」两个功能形态外，law-firm-platform 没有 Kubo 需要补的机制；
其余它宣称的能力（JWT、BCrypt、Redis 锁、CSV 导出、角色菜单、定时任务）Kubo 均已具备或更强。

## 2. 可借鉴的功能形态（仅 2 项 + 1 项提示）

### 2.1 角色差异化工作台看板（值得借鉴，但要「数据权限感知」）

- **law-firm 做法**：按律师/客户/管理员三类角色展示专属数据看板（案件数、财务、评价排行），ECharts 渲染。
- **Kubo 现状**：`src/view/console/index/index.vue` 是空壳首页；ECharts 已装但仅用于设备历史曲线。
- **风险点（关键）**：看板本质是**跨资源的 COUNT/聚合读**，恰恰是数据权限最容易漏的地方——若用一个
  「不经过行级过滤」的聚合接口喂看板，就等于把「只有本租户能看的数据」泄漏到统计图里。因此看板聚合
  必须走**读侧 Mapper + 拦截器同一条权限链**（与 14 资源换轨完全同构），不能新开旁路。
- **价值**：高（把 `useEnforceReadiness` / `useDenyLogReport` / `useExportGapReport` 等 10 个已存在的
  composable 汇成一个「安全态势 + 业务概况」看板，是当前投入产出比最高的一块）。
- **工作量**：中-高（前端看板页 + 后端聚合读出口，聚合出口复用 14 资源换轨的 `countByPermission` 范式）。
- **前置**：P1 读侧换轨收尾后更有底气（聚合源都已有 Mapper 读出口）。

### 2.2 通用操作审计日志切面（值得借鉴）

- **law-firm 做法**：`audit_log` 表 + `@Aspect` 切面，记录「谁在何时做了什么」，后台可查。
- **Kubo 现状**：有数据权限 deny/evidence 审计（`data_permission_deny_log` / `orm_parity_log`），
  但**没有**面向普通业务操作（增删改）的通用审计轨迹；管理员无法回答「这条物料是谁改的、改前改后是什么」。
- **价值**：高（数据权限是「能不能看/改」，通用审计是「改没改、改了啥」，两者是互补的两条证据链）。
- **工作量**：中（注解 + 切面 + `operation_log` 表 + 迁移 + 管理页，可参考 law-firm 的 `@Aspect` 形态）。
- **风险**：低；与现有 `PermissionContext` 打通（记录操作者 tenant/user），避免重复造鉴权。
- **前置**：无硬前置，可与 P2 并行。

### 2.3 提示（Kubo 已有，无需借鉴）

定时任务（`ServiceCron`）、CSV 导出（读侧导出走同一权限链）、角色菜单（`permissionStore` + 后端菜单注入）、
BCrypt / Redis 锁 / JWT 均已具备，无需再动。

### P1 · 读侧换轨收尾（我可独立推进，本批做 B2）

14 资源中渠道域 6 已完成；剩余 10 个长尾按路线图分批：

- **B2** `mes.bom` / `mes.operation` / `mes.routing`（制造域单表，关系简单，改继承链试点）← 本批
- **B3** `asset.device` / `asset.contract`

- **B5** `personnel.department` / `role` / `user`（**需产品拍板**是否纳入行级，不建议无脑换轨）

价值：高（补齐全模块 enforce 的读侧一致性）；工作量：每资源 6 文件 + 测试，机械可复制；风险：低（模板已跑通）。

### P2 · 数据权限感知看板（安全态势 + 业务概况）

- 内容：① 安全态势（enforce 进度、SHADOW 差异率、deny 事件趋势、导出缺口、惰性策略）；
  ② 业务概况（按租户/角色的单据数、库存、价格统计）。
- 实现要点：聚合读出口走 Mapper + 拦截器；前端复用既有 composable + ECharts。
- 价值：高；工作量：中-高；风险：中（聚合旁路必须收敛）；前置：P1 收尾后更稳。

### P3 · 通用操作审计日志

- 见 §2.2。价值高、风险低，可与 P2 并行。

### P4 · 前端测试覆盖硬化

- 现状：vitest 100+ 例，但真正的「门禁」大量落在 `infra/scripts/*.mjs`（perms:check / maskContract /
  ddl:check / text:check）这类**扫描型脚本**上，它们不是 vitest 用例，缺覆盖率与变异测试兜底。
- 优化：① 给 `maskContract` / `permissions` 等安全关键逻辑补 coverage 报告与阈值；② 引入变异测试
  （Stryker）验证门禁本身「能红」（反证）；③ 关键 composable 的单元测试补齐。
- 价值：高（安全系统，门禁自身的可靠性是第二道防线）；工作量：低-中；风险：低。

### P5 · Outbox 消费幂等 + 死信重放（后端）

- 现状：写侧落库 + `PermissionChangeOutboxDispatcher`（Redis 重投 + 状态机纯函数）已做；
  消费幂等 / 死信重放接口 / 真实环境端到端仍后置。前端 `useOutboxDead` composable 已就位等后端。
- 价值：中-高；工作量：中（需真实 MQ）；前置：真实环境。

### P6 · 后置（低优先，非当前痛点）

国际化（i18n）、可访问性（a11y）、首屏性能（已有体积预算 + `useRoutePreload` 路由预载，可再挖懒加载）。
