## 二、前端架构（自研底座，已无 airpower）

### 2.1 底座怎么分层

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 框架层 | `src/framework/**` | 元数据装饰器（`@KModel/@KTable/@KForm/@KField/@KSearch`）、`RootEntity`、HTTP/服务基类（`AbstractCurdService`）、查询模型（`QueryRequestPage` 等）、反馈（toast/确认/命令式弹窗 `DialogUtil`）、枚举字典、格式化、单元格、导出、上传、脱敏 |
| 组件层 | `src/component/framework/K*.vue` | `KTable` / `KFormDialog` / `KPanel` / `KSelector` / `KDetail` / `KDetailTable` / `KDialog` / `KUpload` |
| 应用外壳 | `src/component/{KAppShell,Console,ErrorBoundary,UserCard}.vue` | 侧栏 + 面包屑 + 抽屉、动态菜单路由注册、错误兜底、账号中心 |
| 数据层 | `src/hook/kubo/{useTable,useDetail}.ts` + `src/hook/<域>/*` | 列表/详情状态与请求流；视图不直连 Service，统一经 hook 转发（ESLint 拦） |
| 视图层 | `src/view/console/<域>/...` | 路由路径 == 视图路径；菜单由后端下发 |

**关键约定**：实体只挂 `@K*` 装饰器（不再有双注册）；模板里的 `<el-*>` 必须显式 import；
新用到的 Element Plus 组件要补进 `src/types/element-plus-aggregate.ts`（`elementPlusAggregate.spec.ts` 会拦漏项）。

**这套分层是机器判据**（`pnpm front:layer:check`，扫 287 个 `.ts/.vue`，2026-09-18 起）：

| 规则 | 内容 | 现状 |
| --- | --- | --- |
| LF1 | 非组合根文件不得 import `view/**`（视图是叶子） | ✅ 0 |
| LF2 | `framework/**` 不得 import 应用面（view/api/stores/config/router/…） | ✅ 0 |
| LF3 | 数据层（`base` / `model`）不得 import `view` / `component` / `composables` / `hook` | ✅ 0 |
| LF4 | `utils` / `types` 零出向 | ✅ 0 |

组合根（= 允许认识视图）只有 `main.ts` / `App.vue` / `router/**` / `config/routes*`。

**框架层要应用的能力时不 import，而是声明契约、由应用注册**：`src/framework/transport.ts`
（HTTP/上传的接缝，`src/api/axios.ts` 把自己注册进去）。未装配时 `getTransport()` 直接抛错，
组合根还有一道启动自检 —— 把"接线漏了 = 运行期静默无请求"换成"启动即失败"。白名单 **0/0**。

| airpower-redis | 6.4.3 | `cn.hamm.spms.framework.redis.*` | 3 |

（三个模块各有 1 个 `Auto` 类**没有**搬：`@AutoConfiguration` + `META-INF/spring/…AutoConfiguration.imports`
是给外部 jar 的注册方式；应用内 `@SpringBootApplication` 的组件扫描本来就会扫到本仓包，
再写一份等于把同一个 Bean 注册两次。）

**同批改掉的「名字里还有 airpower、但已经不是它的东西」**：配置前缀 `airpower.api/curd/redis` →
`spms.api/curd/redis`（与早先的 `spms.cookie` 同一种改法）、Redis key 前缀 `airpower:` → `spms:`、
环境变量 `AIRPOWER_API_ACCESS_TOKEN_SECRET` → `SPMS_API_ACCESS_TOKEN_SECRET`
（**部署侧必须同步改名**：守卫 `AccessTokenSecretGuard` 会拒绝启动并打印新变量名，不会静默用弱默认值）、
`Application` 里 `exclude = airpower.cookie.Auto.class` 删除（那个自动装配源已不存在）。

**为什么从「只搬调用闭包」改成「整模块搬」**：B2 只搬了 15 个类；这一批连框架层一起搬时，
半套副本会把「缺哪个类」变成编译期的猜谜 —— 整模块搬入，缺口一次归零。

**这一批的可 review 形状**：84 个新文件（MIT 头 + 来源坐标）、161 个文件 545 处 import 改名、
pom 删 1 条依赖、2 个 yml 配置键改名、`Application` 去掉一行排除、撤销上一批为兼容而保留的
`CollectionUtil` / `ReflectUtil` / `AccessTokenUtil` 三处例外（自持层里它们都在）。

**仍然待办（已经不是 airpower 的活，是本仓内务）**：

1. **编译修复**：这一批是「大搬家」，而沙箱没有 JDK / Maven 仓库（**无法编译验证**，用户已批准「先删后修」）。
   首次 `mvn -q compile` 预期有一批 import/符号级报错要收；修法纯机械 —— 缺的类都在本仓或栈内。
2. **JPA → MyBatis-Plus**：**J1/J2/J3/J4 全部落地**（J1 证据族、J2 写链路引擎、J3 实体注解 + 关系对象图、
   J4 去 starter + 去 `ddl-auto` + 影子线收尾；执行记录见 `去JPA决策评估.md` §9.2 / §9.6 / §9.7.7 / §9.8）。
   本仓现在**只有一套 ORM**：`PersistenceStackTest` 钉住"没有 `EntityManagerFactory`、只有一个
   `DataSourceTransactionManager`"，`pnpm jpa:check -- --check` 钉住"JPA 不许写回来"。
   全程未新增依赖：栈内 MyBatis-Plus 3.5.9 的拦截器、`MetaObjectHandler` 与 mapper XML 已经够用。

## 八、本轮补回：父 POM 退场时被"删过头"的 7 条依赖（2026-09-19）

**症状**：`SPMS-Server/pom.xml` 只有 10 条依赖，而代码在 import 183 个文件的 `lombok.*`、
112 处 `org.springframework.web/http`、28 处 `spring-data-redis`、46 处 `jakarta.validation`、
151 处 `org.jetbrains.annotations` —— 换句话说：**整个后端编译不过**，`mvn` 第一步就红。

**为什么一直没被发现**：三件事同时成立 ——
① 沙箱没有 JDK，`pnpm check` 全是静态检查（`pom:check` 只查"不该有的"：无版本依赖、悬空属性、`cn.hamm` 残留）；
② 那段时间 CI 因计费问题全部「未启动」，真编译一步没跑；
③ 旧结构下这些依赖是**父 POM / `airpower-curd` 传递过来**的，删它们时没人"看见"过它们。

**修法（两条腿）**：
1. **补依赖**：pom 加 7 条并逐条注释"谁在用、多少处"（含 `org.jetbrains:annotations` 显式写版本 ——
   它**不在 Boot BOM 家族**，BOM 里只有 `org.jetbrains.kotlin:*`，这一点是核对着
   `spring-boot-dependencies-3.4.4.pom` 逐条确认的，不靠记忆）；
2. **加门禁**：`pnpm deps:check`（`infra/scripts/check-pom-imports.mjs`）——
   按 **import 全限定名**反查 pom 声明（规则表 16 条），并查 yml 里的 JDBC 驱动是否在 pom 里。
   配套三条反证（拿掉 web / 拿掉 lombok / 拿掉 MySQL 驱动）都先红后复原绿。

> 教训一句话：**"删除型"重构必须配"该有的在不在"的判据**。
> 只查"不该有的"（airpower 0 引用、JPA 0 引用）永远抓不到"删过头"，
> 而"删过头"的后果与"没删干净"一样致命 —— 一个是脏，一个是不能编译。

## 九、怎么复现/自检这套结论

```bash
pnpm stack:project                 # 本文件的机器版（本次实测：前端 9 + 15 个依赖；后端 17 个依赖；16 个 compose 服务）
pnpm stack:project -- --json       # 给脚本读
pnpm stack                         # 前端：依赖 + 死重量 + 体积
pnpm airpower:check                # 前端 airpower = 0
pnpm airpower:backend              # 后端 airpower 足迹（当前 0/0/0 + 0 依赖 + 0 配置键）
pnpm airpower:backend -- --check   # 后端归零门禁（CI 已接；基线 0，出现任何引用即红）
pnpm pom:check                     # 后端 pom 自持校验（无版本依赖 / 悬空属性 / 发版插件残留；**只管"不该有的"**）
pnpm deps:check                    # 后端 pom↔import 对账（**只管"该有的"**：import 家族必须有依赖兜底，含 yml 里的 JDBC 驱动）
pnpm java:imports                  # Java 导入可达性（无 JDK 的半个编译器：本仓 import 必须落地、自持层不得反依赖 airpower、同名副本必须承认）
pnpm sql:check                     # SQL 分层门禁（禁止 .java 写 SQL，只许住 mapper XML）
pnpm java:decl                     # Java 声明级门禁（形参重名 / 字段重名）—— javac 会拒绝，而本仓没有 JDK，见 docs/架构分层设计.md §七
pnpm layer:check                   # 后端分层门禁（core→framework→base→module；控制器不注入仓储…）见 docs/架构分层设计.md
pnpm front:layer:check             # 前端分层门禁（utils/types → model → framework → view；组合根 main/App/router/routes）
pnpm jpa:check                     # JPA 归零门禁（足迹 0/0/0 + pom 无 starter + yml 无 spring.jpa/ddl-auto + 实体零 JPA 注解）
pnpm mapper:check                  # Mapper XML 命名空间门禁（namespace 必须落到存在的 Java 接口；无重复注册 / 空壳 XML）
pnpm check                         # 全链门禁（含上面这些；29 道）
java -version && mvn -v            # 后端：本沙箱没有，需在本地/CI 执行
```
