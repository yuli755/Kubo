# 功能开关与灰度发布方案（生产级能力补全 · 功能开关/灰度）

> 触发：生产级审查报告「功能开关/灰度（复用 Nacos）」项。本文基于代码事实，说明现状、已落地的
> 灰度决策引擎，以及「复用 Nacos」的接线路径（诚实标注需真实环境验证的部分）。

---

## 0. 结论先行

1. **现状是「全局布尔开关」**：`ConfigFlag` 枚举 + `config` 表（`ConfigEntity`/`ConfigService`），
   每个开关全量生效，**没有租户级灰度、没有百分比放量**。加开关要改枚举 + 插 DB 行，无法「先 10% 租户试水」。
2. **已落地灰度引擎**：新增 `FeatureFlagService`（`cn.hamm.spms.module.system.config`），在现有
   `ConfigService` 之上补一层规则 DSL（全局 / 百分比 / 白名单 / 黑名单），**零新依赖、零迁移、立即可用**，
   已带契约测试。
3. **Nacos 现状**：docker-compose 有 `nacos` 服务（v2.3.2，含鉴权），但后端 `pom.xml` **未引**
   Spring Cloud Alibaba，**后端没有接 Nacos**——它是「目标态演示组件」。把开关源切到 Nacos 是后续
   可选项（§3），不是本批硬门槛。
4. **诚实边界**：灰度引擎的决策核心为纯函数，已单测；`FeatureFlagService` 读 DB 的部分需真实
   Spring 上下文（本机 `./mvnw test` 验证）。Nacos 接线需 Nacos server + Spring Cloud Alibaba
   版本对齐，属「代码先行、本机验证待用户」。

## 2. 已落地的灰度引擎（立即可用）

### 2.1 规则 DSL

开关在 `config` 表里的 `config` 字段写规则（`flag` = 开关名，可自由命名，不必是 `ConfigFlag` 枚举）：

| 规则 | 语义 |
| --- | --- |
| `on` / `1` / `true` | 全局开启 |
| `off` / `0` / `false` | 全局关闭 |
| `pct:25` | 25% 放量：按 `scope` 哈希取模，**同一 scope 结果稳定（sticky）**，不会反复横跳 |
| `allow:1,2,3` | 白名单：仅 scope ∈ {1,2,3} 开启 |
| `deny:4,5` | 黑名单：scope ∈ {4,5} 关闭，其余开启 |

配置缺失 / 规则非法时回落 `defaultValue`（默认关闭）——**灰度失败不放大爆炸面**，这是核心安全底线。

### 2.2 scope 是什么

放量维度，多租户系统按**租户 ID** 灰度最合理（也可传用户 ID 做用户级灰度）。传 `null` 时：全局开关
正常；白名单对空 scope 视为「不在名单」；百分比对空 scope 仍是稳定桶（不抛错）。

### 2.3 接入示例

```java
// 先 10% 租户 → 观察 → 50% → 100% 的渐进发布，改 config 表一行即可，无需发版
if (featureFlagService.isEnabled("feature.new-report", String.valueOf(tenantId))) {
    // 新报表逻辑
} else {
    // 旧报表逻辑
}
```

### 2.4 灰度发布流程建议

1. 上线新功能时，代码里用 `isEnabled("feature.X", tenantId)` 包住新路径；
2. `config` 表插一行 `flag=feature.X, config=pct:10` → 先放 10% 租户；
3. 看监控（错误上报 `/api/error-report` 的 `context`、日志、业务指标）无异常 → `pct:50` → `pct:100`；
4. 稳定后把开关收敛（移除旧路径，或改为 `on`）。

> 与现有 `ConfigFlag` 的关系：**不动**现有 13 个全局开关的语义（它们本就是全局策略，非发布开关）；
> 新功能要灰度时用本引擎的独立开关名，二者共存、互不干扰。

## 3. 复用 Nacos（后续接线，代码先行）

> 现状：Nacos 在 compose 里但后端未接。要接，需两步，且都需真实环境验证。

### 3.1 依赖 + 配置（需版本对齐验证）

```xml
<!-- pom.xml 增加（版本须与 Spring Boot 3.x 对齐，airpower parent 6.4.3 → Spring Boot 3.x） -->
<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
  <version>${spring-cloud-alibaba.version}</version>
</dependency>
```

```yaml
# bootstrap.yml（或 spring.config.import）
spring:
  config:
    import: nacos:feature-flags.yaml?group=KUBO   # Nacos 里建 dataId=feature-flags.yaml
  cloud:
    nacos:
      server-addr: ${NACOS_SERVER_ADDR:localhost:8848}
      username: nacos
      password: ${NACOS_PASSWORD:}
```

### 3.2 切换开关源

`FeatureFlagService.isEnabled` 目前从 `ConfigService`（DB）读；接 Nacos 后，把「读配置」这步改为从
Nacos 的 `feature-flags.yaml` 读同名开关（`flag` → 规则串），**决策 DSL 与所有调用方不变**。这一步的
落地形态是加一个 `FeatureFlagSource` 接口 + Nacos 实现，待依赖与 Nacos server 就绪后补（属「代码先行、
本机验证待用户」，沙箱无 Nacos server 与 Spring Cloud Alibaba 依赖，无法运行时验证）。

### 3.3 选型对比

| 维度 | DB `config` 表（现状/已落地） | Nacos（目标态） |
| --- | --- | --- |
| 热更新 | 需重启或手动刷缓存 | 原生热更新（`@RefreshScope` / 监听） |
| 集中管理 | 各环境各自 DB | 统一配置中心，多环境 dataId 区分 |
| 灰度开关 | 已可用（本引擎） | 更强：配置下发 + 监听 + 审计 |
| 落地成本 | 零 | 需依赖 + server + 版本对齐 + 迁移开关数据 |

**建议**：短期用 DB + `FeatureFlagService` 满足灰度需求；待系统规模上来（多环境/多实例需要统一配置
下发）再切 Nacos，切换成本已被 `FeatureFlagService` 的单一读取点收敛到最小。

## 4. 与其它能力的关系

- **密钥轮换 SOP**：灰度开关本身也可能存敏感配置，若开关源切到 Nacos，注意 Nacos 鉴权（compose 已
  开 `NACOS_AUTH_ENABLE`）与账号最小化。
- **错误上报闭环**：灰度放量期把 `feature.X` 写进前端 `reportError` 的 `context`，Loki 可按开关聚合
  新功能的错误率，做「放量→回滚」的观测闭环。
- **恢复演练 DR**：`config` 表是 MySQL 资产的一部分，随备份/演练一起恢复，灰度开关状态不丢。
