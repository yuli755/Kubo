# 项目重定位：砍什么、留什么（物流仓储 / 半导体方向）

> 触发：使用方明确「真实业务是**物流仓储**或**半导体工厂**方向」，并提出「技术栈太杂太乱，
> 想大刀阔斧砍掉」的诉求。
>
> 本文先用代码事实核对「杂」是否真实存在，再把「该砍的」与「不该砍的」分开，
> 最后给出针对这两个行业的差距清单与建议顺序。**所有数字均可复现。**

## 0. 结论先行

1. **「哪里都沾点边、又没啥大用」——你的直觉是对的，有硬证据**：仓库里自己就存着一份
   `docs/业务功能未开发盘点.md`，承认「**整模块未开发 3 个**」（聊天后端完整/前端零、微信空壳、企微空壳），
   且 `OpenApiConfig` 的对外文案里写着「仓储管理: 入库、出库、库存、**盘点、波次**」——
   **代码里根本没有盘点和波次**。
2. **但「砍技术栈」是砍错了对象**。真正的问题是三层混在一起：**业务模块（该砍该换）**
   混着 **平台能力（该留）** 与 **技术底座（该留）**。
3. **关键事实：技术底座与平台能力是「行业无关的资产」**，价值约 **8–14 人月**：
   数据权限内核 102 文件 / 13,721 行、660 后端用例、12 个工程门禁、认证/租户/审计/文件/编号/单位/菜单/权限。
   **做物流仓储或半导体，这些东西一样要用，一行都不用改。**
4. **真正要做的三件事**：①先定行业（两个不能都做）②砍掉 A 环无关模块（立刻变清楚）
   ③按行业**补核心能力**（这才是主要工作量）。

## 4. 建议：分层处置（不是「全砍」，是「精准砍」）

### 4.1 立刻砍（A 环 · 无关模块，收益=「清楚」，不是省代码）

| 对象 | 体量 | 建议 |
| --- | --- | --- |

| `wechat` / `wecom` | 4 文件（空壳） | **删**（或显式标注「预留」） |
| `mcp` | 1 文件 | **删**（纯平台化附属） |
| `open` 开放平台 | 32 文件 / 1,823 行 | **看业务**：不对外提供 API 就删 |
| `iot` | 14 文件 / 713 行 | **看行业**：半导体留（改 EDC），物流看是否有设备 |

### 4.2 坚决保留（B 环 + C 环，价值 8–14 人月）

### 4.3 按选定行业补（A 环 · 真正的工作量在这里）

**若做物流仓储**（推荐先做，与现有模型同源）：
1. 批次/效期管理（lot + 效期 + 先进先出）
2. 序列号/唯一码追溯
3. 波次拣选 + 拣货策略
4. 盘点（全盘/循环盘/差异调整）
5. 货主与计费（3PL 必需）
6. 承运商/运单/发货交接
7. RF/条码作业前端（移动端）

**若做半导体**：
1. **Lot/Wafer 批次与在制品（WIP）** —— 核心
2. **Recipe 配方管理**
3. **SECS/GEM 设备联机**（或先做 EDC 数据采集）

5. 载具/洁净室管理（FOUP）
6. 复用：设备台账、工艺路线、工序、数据采集（改造）

## 5. 我要修正上一轮的判断（诚实起见）

上一轮我说「**不建议重开**」，理由是「领域模型对得上」。
现在知道你真实业务是**物流仓储/半导体**，这个前提**不成立了** —— 这正是我当时列的
「重开的第一条硬理由：领域模型错了」。

**但「技术栈全砍」仍然不对。** 修正后的准确结论是：

> **「重做业务域 + 保留平台底座」**，而不是「重开项目」，更不是「全砍技术栈」。
>
> - 半导体：MES 业务域**重建**（Lot/WIP/Recipe 是另一套范式）；
> - 物流仓储：WMS 在现有骨架上**补 4–6 个模块**；
> - 两者都**复用 B 环 + C 环**（省 8–14 人月 + 避开 6 个安全坑）。

**如果连 B/C 环也重写**，等于用 16–34 人月换一个**必然更弱**的系统：
因为那些安全坑（跨租户缓存泄露、JOIN 成权限旁路、写侧条件绑不上、导出绕过脱敏、会话假活、归属可篡改）
**重写时一定会再踩一遍**，而现有代码里**已经解决且有 660 用例钉住**。

## 6. 我的建议（顺序很重要）

```
第 0 步  定行业：物流仓储 还是 半导体（**二选一**，两个都做 = 又变回「哪里都沾点边」）
   ↓
第 1 步  砍 A 环无关模块（chat/wechat/wecom/mcp/按需 open、iot）→ 项目立刻「清楚」
   ↓
第 2 步  修文档失真（DATABASE.md 21 张虚构表）→ 新人不再被误导
   ↓
第 3 步  按行业补核心模块（§4.3），**每补一个，把对应权限策略/审计/测试一起补**
   ↓
第 4 步  前端表现层重做（KAppShell + KDataTable + 表单 schema）—— 与第 3 步并行，互不阻塞
```

**为什么第 3 步与第 4 步可以并行**：后端补能力走 API，前端换表现层走组件；
两者只通过「字段矩阵」这一份契约耦合（见 `前端从零重构·后端契约与字段库表评估.md` §2.3）。

## 7. 一句话回答你的问题

> **我不建议「砍技术栈」，我建议「砍业务模块 + 换业务模型」。**
>
> 你感觉的「杂」是 A 环塞了无关模块、又缺行业核心能力；
> 而 B/C 环（数据权限内核 + 工程化底座）恰恰是**最值钱、最与行业无关**的部分 ——
> 那是资产，不是负债。砍掉它，你会在 6 个月后重新写一遍，并且写得更薄。
