# 业务功能未开发 / 未实现盘点（2026-09-10）

> 触发：用户要求盘点「各业务系统里哪些模块没开发、哪些模块的哪些功能没实现、是否还有类似情况」。
> 方法：对后端 50 个 Controller、前端 144 个 .vue、菜单初始化（`MenuService.initMenu`）、迁移脚本、
> 全仓 TODO/空壳/占位做了系统性扫描。**只列代码事实可证的点，不臆测「业务还该有什么」**。

---

## 0. 结论先行

- **整模块未开发：3 个** —— 聊天（后端完整、前端零）、微信（后端空壳）、企业微信（后端空壳）。
- **具体功能点未实现：4 个** —— 短信验证码真发送、工单报工并发锁、工序级 BOM 拣货关联、前端 RSA 测试。
- **文档已记录的未闭环：约 8 类**（数据权限导出旁路等，见 §3，多为「刻意诚实化 / 需真实环境 / 需拍板」，非遗漏）。
- **易误判为「未实现」但实际已闭环：3 处**（IoT 时序、OAuth2 第三方登录、MCP），见 §4。

核心判断：**「业务 CRUD 骨架」基本齐全且前后端闭环**（所有菜单项都有对应页面）；未开发/未实现的
集中在「非 CRUD 的增值功能」（即时通讯、外部平台集成、短信通道）与「写侧健壮性」（并发锁、事务边界）。

## 1. 整模块未开发

### 1.1 聊天模块 `chat`（后端完整，前端零页面、零入口）

| 维度 | 现状 |
| --- | --- |
| 后端 | ✅ 完整：`RoomEntity`/`MemberEntity` + Room/Member CRUD（创建房间 / 我的房间 / 热门房间 / 成员）+ `ChatServices` + WebSocket 事件（`MemberTextMessageEvent`/`RoomMemberEvent`/`ChatEventType`）+ 房间密码校验 |
| 前端 | ❌ 零：`src/view` 无 chat 目录、`src/api` 无 chat 文件、`MenuService.initMenu` 无聊天菜单入口 |
| WebSocket 通道 | ✅ 已就绪：`WebSocketManager` + `useWebSocket` hook 已实现（协议、重连、频道订阅），但**没有聊天 UI 去消费它** |

结论：聊天是**后端已投入、前端完全未做**的模块。若产品要聊天功能，只需纯前端增量；否则后端
这套（含 DevDataInitRunner 对默认房间的初始化）处于「孤儿」状态，建议明确取舍。

### 1.2 微信 `wechat`（后端空壳）

`WechatController` 只有 `init()` 返回字符串 `"success"`（`@Permission(login=false)`）。无公众号/小程序
登录、消息推送、回调处理、JS-SDK 签名等任何实质逻辑。

### 1.3 企业微信 `wecom`（后端空壳）

`WecomController` 只有 `callback()` 返回 `"<h1>Server running!</h1>"`。无企业微信回调验证、消息接收、
成员同步、登录集成。

> 1.2/1.3 的共同点：**有 Controller 占位、无任何业务实现、无前端、无菜单**。属于「看起来有、实际不能用」，
> 建议二选一：实现它，或显式标注「预留/移除」，避免对外口径误以为已支持微信/企微集成。

## 5. 补充建议（供决策，不臆测偏好）

1. **空壳模块（wechat/wecom）先定去留**：它们是最容易「对外口径失真」的点——README/文档若宣称
   「支持微信/企微」，与实际不符。建议要么删掉占位 Controller，要么在文档里显式标注「未实现」。
2. **聊天模块是纯前端增量**：后端已投入，若产品有即时通讯诉求，前端接 WebSocketManager 即可闭环；
   若没有，后端这套「孤儿代码」应在下一轮清理时评估是否移除。
3. **短信验证码是「最后一步」欠账**：代码已做到「生成+存储+限频」，只差接短信服务商（仓库已引
   `aliyun-sdk-oss`，同生态可加 `aliyun-sdk-dysmsapi`），是一个明确的低风险增量。
4. **报工并发锁是唯一有数据正确性风险的未实现项**（§2 第 2 条）：并发报工丢更新属于「真实业务损失」，
   ~~建议优先排期~~ ✅ 已按 Redis 分布式锁落地理论代码（2026-09-10），本机编译 + 并发验证待真实环境。
