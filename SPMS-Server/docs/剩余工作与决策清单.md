## 2. A 类 · 需拍板（落地前必须先定语义）

### A1. 设备采集端认证（唯一「安全关键」剩余项）⭐ → ✅ 已落地

- **问题**：`getCurrentReport`/`getDevicePayloadHistory` 按**数字 ID**、`getDeviceConfig` 按 UUID
  当弱令牌，未认证即可按 ID 枚举读任意设备实时数据/历史（`公开端点安全审计.md` §3.1）。
- **落地（第二十批）**：
  - `DeviceEntity` 加 `apiKey` 列（`@JsonProperty(WRITE_ONLY)` + `@ToString.Exclude`，读端永不回显）；
  - 迁移 `20260911_device_api_key.sql`（`kubo_mt_add_column` 幂等加列，生产 `validate` 下必跑）；
  - `DeviceService`：新建设备自动生成密钥（`RandomUtil.randomBytes` Base64，与 AppSecret 同口径）、
    更新不重置；`authenticateDevice` + `apiKeyMatches`（`MessageDigest.isEqual` 常量时间比对，
    空密钥/null 一律不匹配，设备不存在与密钥不匹配返回同一 401）；
  - 三个公开出口 `getCurrentReport`/`getDeviceConfig`/`getDevicePayloadHistory` 全部改走 API-Key 认证；
  - 登录态新增 `getApiKey`（查看一次）/`resetApiKey`（重置），供管理员向采集端下发密钥；
  - 前端监控/历史视图按需取钥随请求提交（`monitor.vue` 懒加载缓存，`history.vue` 经 `showHistory` 透传）；
  - 契约测试 `DeviceApiKeyTest`（匹配/空密钥/401 语义/新建生成·更新不重置）。
- **仍待你本机验证**：编译 + 联调（真实 MySQL/Redis）；**采集端协议变更**：设备侧需携带 `apiKey` 字段发版。

### A2. 聊天室密码明文落库 → ✅ 已拍板：接受明文

- **问题**：`RoomEntity.password` 明文 `varchar(255)`（已有 `@JsonProperty(WRITE_ONLY)` 不外泄）。
- **拍板（接受明文，不哈希）**，理由三条：
  1. **低敏**：聊天室口令是「进房间的临时门禁码」，非账户凭证，泄露影响面极小；
  2. **已不外泄**：`WRITE_ONLY` 读端永不回显；比对已改大小写敏感 `equals`（第十六批，弱化口令熵问题已修）；
  3. **哈希风险 > 收益**：`BaseService.java:148` 明言框架 `beforeUpdate` 语义「可能收到已合并实体、
     也可能收到仅提交值」，在 `beforeAppSaveToDatabase` 哈希有**双哈希 / 空值覆盖**歧义，且需迁移
     存量明文。为一个低敏字段引入这些风险不值得。
- **若将来升级为高敏**（如房间口令与账户打通）：先确认框架 update 合并语义 + 哈希前缀标记法
  （`$room$sha256(...)` 可防双哈希）+ 存量迁移，再做。

### A3. 归属列不可变（creatorId 可被 PUT 篡改）⭐ → ✅ 已落地闭环（2026-09-22）

- **问题**：普通用户 PUT 改 `creatorId` 可把行「送出视野」（`业务功能未开发盘点.md` §3）。
- **落地闭环（路线一）**：
  - `TenantAwareEntity` 中 `tenantId` 与 `creatorId` 均打标 `@ReadOnly`；
  - `BaseController` 反序列化与参数清洗自动剥离 `@ReadOnly` 字段；
  - `BaseService.beforeAdd` 强制取当前服务端登录上下文覆盖 `creatorId` 与 `tenantId`；
  - `BaseService.beforeUpdate` 接入 `protectAttribution` 自动回表校验与恢复，杜绝客户端篡改。

### A4. wechat/wecom 空壳去留 → ✅ 已彻底清理移除（2026-09-22）

- **清理动作**：历史无业务逻辑的 `WecomController.java` 与 `WechatController.java` 均已彻底移除，系统公开接口完全真实，无空壳端点欺诈。
