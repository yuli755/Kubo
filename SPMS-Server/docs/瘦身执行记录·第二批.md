## 一、为什么 `asset/device` 与 `common/influx` 跟着一起走

`module/iot` 不是能单独摘掉的挂件，它是**设备物联竖切**的入口，四根线都咬在别处：

| 依赖 | 咬在哪 | 结论 |
| --- | --- | --- |
| `module/asset/device` | `DeviceService` 第 217 行调 `InfluxHelper` 查历史；`DeviceEntity.monitor/history` 页读 `iot.parameter` | 留 device 就得留 influx + parameter，等于没删 |
| `common/influx` | 只被 `DeviceService` 与 `ReportMqCallback` 使用 | 纯为 IoT 上报服务 |
| `module/iot/report`（MQTT 上报） | `ReportEventListener` 注册在 `Application.main()`；paho + `airpower-mqtt` 只服务它 | 删 IoT = 后端不再需要 MQTT |
| `DevDataInitRunner` | 播种 3 个系统参数、2 台模拟设备、`asset.device` 数据资源 + 写策略 | 全是 IoT 专属种子 |

业务方向是**物流仓储**：这套「设备状态/报警/实时产量 → InfluxDB 时序 → 监控大屏」是半导体工厂的形状，
留着只会继续贡献「哪里都沾点边、又没啥大用」。所以本批按**整条竖切**拆除，而不是保留一个残废的设备台账 CRUD。

> 若将来仓储真需要管设备（叉车/AGV/扫码枪），应按新域模型重做，而不是复活这套生产上报链。
