# 备份与恢复策略方案（第七批第 1 项）

> 触发：生产级审查报告 §9 第七批第 1 项。仓库此前**没有任何备份/容灾文档或脚本**，这是「可持续
> 运行」最薄的一块。本文基于代码事实盘点真实数据资产，给出分级的备份策略、RPO/RTO 目标、
> 恢复演练与验证方法。**备份方案必须基于「实际有什么数据」，而不是愿景架构。**

---

## 0. 结论先行

1. **真正的数据资产只有五样**（见 §1），其中 **MySQL 是唯一「丢了就事故级」的资产**，其余四样
   要么可重建、要么有天然冗余。
2. **好的一面**：docker-compose 里 MySQL 已开 `binlog`（GTID + ROW + `log-bin` + 保留 7 天），
   这为**时间点恢复（PITR）**提供了免费基础，只差一个定期全量备份 + 把 binlog 备出宿主机。
3. **最紧迫的缺口**：没有任何「全量备份」动作，也没有「恢复演练」——备份策略的价值不在备份本身，
   而在**被验证过能恢复**（未经演练的备份约等于没有备份）。

## 1. 数据资产清单（代码事实）

| 资产 | 位置 | 关键性 | 备份必要性 | 理由 |
| --- | --- | --- | --- | --- |
| MySQL 8.0 | `kubo-mysql:3306`，库 `kubo` | **P0** | **必须** | 业务主库：合同/物料/工单/订单/数据权限策略/审计，唯一真相源 |
| 文件存储 | 本地 `/home/static/upload/`（`app.upload-platform: local` 默认）或阿里云 OSS（二选一） | P1 | 必须（本地）/ OSS 自带 | 合同附件、设备图、导入导出文件；本地盘无冗余，机器坏=文件没 |
| InfluxDB | IoT 时序（token 已外置） | P2 | 建议 | 设备上报时序；丢失=历史报表缺失，可接受部分丢失 |
| Redis 7.2 | `kubo-redis:6379`，db 5 | P3 | 可选 | 缓存 + WebSocket 状态 + 数据权限缓存（TTL 30m），全部可重建；AOF+RDB 已开 |
| 日志 | logback 文件（7 天/3GB） | P4 | 可选 | 排障用，非业务资产；已滚动保留 |

> 后端代码（单体 pom + application*.yml）**没有接**——它们不产生需要备份的真实数据，不在备份范围内。

## 2. 分级备份策略

### 2.1 MySQL（核心，PITR 能力）

- **全量**：每日凌晨（业务低峰）`mysqldump` 或 `xtrabackup`（数据量大时用后者，热备无锁）：
  - `mysqldump --single-transaction --quick --routines --triggers --events kubo | gzip > kubo-$(date +%F).sql.gz`
  - `xtrabackup --backup --target-dir=... `（InnoDB 热备，适合 >10GB）
- **增量**：binlog（已开 GTID + ROW），`mysqlbinlog` 持续归档到备份机（7 天保留已配，但**必须备出宿主机**，否则宿主机坏=binlog 没）。
- **RPO**：≤ 5 分钟（binlog 归档间隔）；**RTO**：≤ 1 小时（全量 + 回放 binlog）。
- **验证**：每周在**独立环境**（CI 的 MySQL 8 service 即可复用）完整执行「全量恢复 + binlog 回放 + 应用启动 + 冒烟查询」，验证「能恢复」而非「备份文件存在」。

### 2.2 文件存储

- **本地**（`/home/static/`）：每日 `rsync -az --delete /home/static/ 备份机:/backup/static/`；
  量小可并入 MySQL 备份脚本统一打包。
- **阿里云 OSS**：OSS 自带冗余（同城 3 副本）+ 可选**版本控制/跨区域复制**，备份职责交给云；只需开启版本控制防误删。

### 2.3 InfluxDB

- 时序数据，按「保留策略（Retention Policy）」裁剪历史；需备份时用 `influx backup` 导出到对象存储。
- 明确 RPO：丢 1 天时序可接受（历史报表场景）。

### 2.4 Redis

- 不单独备份。AOF + RDB 已开（`appendonly yes` + `save`），持久化文件随 docker volume；
  极端场景下清空重建即可（缓存 + 可重建状态）。唯一注意：**数据权限 outbox 在 MySQL 不在 Redis**，Redis 无业务真相。

### 2.5 日志

- 不备份。滚动保留 7 天足够排障；如需审计留痕，接入 Loki（已有 docker-compose 配置）而非备份文件。

## 3. RPO / RTO 目标（建议值，需业务确认）

| 资产 | RPO | RTO | 恢复手段 |
| --- | --- | --- | --- |
| MySQL | ≤ 5 分钟 | ≤ 1 小时 | 全量 + binlog PITR |
| 文件（本地） | ≤ 24 小时 | ≤ 1 小时 | rsync 快照 / 最近备份 |
| InfluxDB | ≤ 24 小时 | ≤ 2 小时 | influx backup 恢复 |
| Redis | —（可重建） | ≤ 10 分钟 | 清空重建 |

> RPO/RTO 是**业务决策**，不是技术能单方面定的；上表给的是制造型 MES/WMS 的常见默认值，
> 最终需与业务方确认「能接受丢多少数据、能等多久恢复」。

---

## 4. 恢复演练（关键，别跳过）

未经演练的备份 = 没有备份。建议：

1. **季度演练**：在隔离环境从「最近全量 + binlog」完整恢复，核对关键表行数、跑 CI 的迁移脚本验证 schema、
   启动应用做冒烟（登录 + 一个列表页）。
2. **演练产出**：记录恢复耗时（对表 RTO）、遇到的问题、备份脚本/文档的修正。
3. **自动化**：把「恢复验证」做成 CI 的一个 job（复用 migrations job 的 MySQL 8 service），
   每夜拉最新备份跑一次恢复，**备份损坏当天就能被发现**，而不是等灾难那天。
