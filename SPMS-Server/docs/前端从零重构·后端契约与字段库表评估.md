## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| **页面展示字段要不要改？** | **要，而且是硬性的（阻塞级）**。当前列表页大量「关联名称列」在 JPA 读路径下侥幸有值；一旦 `mapper-read.enabled=true`，后端只回主表列 + 外键 id，这些列会**集体变空**。另有 2 处语义错配（前端 `storage` ↔ 后端 `structure`）。 |
| **库表要不要改/补？** | **权限相关的表已经齐了**（user_tenant / user_factory / data_resource / data_policy / data_field_policy / 三张日志表 / outbox）。**缺的是「数据播种」与「配置入口」**：①生产环境没有菜单播种路径（只有 dev runner）②菜单缺「操作日志」③`user.factoryList/storageList` 有表无 UI ④ `data_resource` 无登记行 ⑤ `DATABASE.md` 失真（52 张表里 21 张在代码里不存在）。 |
| **能从零重写前端吗？** | **能，且推荐**。但起点不是「画页面」，而是**先锁契约**：后端 springdoc 已就绪（生产按安全策略关闭，需在 dev/CI 出 spec）→ 生成 typed client → 出「页面 × 字段 × 来源 × 脱敏」矩阵 → 再写页面。 |

## 1. 我理解的后端现状（请校正，有错我就改）

### 1.1 技术栈

| 层 | 实际选型 | 证据 |
| --- | --- | --- |
| 框架 | **Spring Boot 3 + airpower 6.x**（`airpower-curd` / `-websocket` / `-mqtt` / `-ai` / `-open` / `-email`） | `pom.xml` |
| 写侧 ORM | **JPA / Hibernate**，生产 `ddl-auto: validate` | `application-production.yml` |
| 读侧 ORM | **MyBatis-Plus**（「读走 Mapper，写留 JPA」换轨中，`kubo.data-permission.mapper-read.enabled` 默认 **false**） | `application.yml:141`、21 个 `resources/mapper/*.xml` |
| 存储 | MySQL 8 + Redis + InfluxDB（IoT 时序）+ 阿里云 OSS | `pom.xml`、`common/influx` |
| 认证 | JWT + **WebAuthn**（`webauthn-server-core`）+ 第三方登录（微信/企微/OAuth） | `pom.xml`、`module/open`、`module/wechat` |
| 文档 | **springdoc OpenAPI**（生产 `api-docs.enabled: false` —— 防端点测绘，安全策略） | `application-production.yml:62` |

### 1.2 API 形态（决定前端怎么写）

- 每个资源一个 Controller，`@Api("input")` 决定 URL 段；基类提供 CRUD：
  `/{resource}/getPage|getDetail|add|update|delete|disable|enable|export`；
- 手写扩展端点：`audit` / `reject` / `setBillDetailsAllFinished` / `addFinish` / `getCount` / `getStat`；
- **共 52 个 Controller**（含 `dashboard` / `dataResource` / `dataPolicy` / `dataFieldPolicy` / `mcp` / `status` / `file` / `oauth` 等）。

### 1.3 权限设计（这是二次改造的核心，前端必须按它设计）

| 概念 | 落地物 | 默认值 |
| --- | --- | --- |
| 全局档位 | `kubo.data-permission.mode`：`off` / `shadow` / `enforce` | 本地 `off`，**生产 `shadow`** |
| 资源登记 | 表 `data_resource`（+ `DataResourceEntity`）；`deny-unregistered` 未登记默认拒绝 | `false` |
| 行级策略 | 表 `data_policy`（QUERY / UPDATE / DELETE）× 主体类型（TENANT / DEPARTMENT / **FACTORY**） | — |
| 列级脱敏 | 表 `data_field_policy`（mask）；前端 `my-mask` / `my-mask-map` 端点 | — |
| 多租户 | `user_tenant` + 请求头 `X-Tenant-Id` + `tenant-required` | `false` |
| 工厂维度 | **表 `user_factory` 已建**，`factory-dimension-enabled: true`（D13 已落地，不再是阻塞项） | 开 |
| 写侧行级保护 | `row-write.enabled`（改/删前判「这行在不在你的范围」） | `false` |
| 层级闭包 | `hierarchy.department-enabled` / `.factory-enabled`（展开=放宽可见范围） | 均 `false` |
| 证据链 | `data_permission_diff_log`（影子差异）/ `data_permission_deny_log`（拒绝事件）/ `data_permission_orm_parity_log`（ORM 对账） | 留痕 |
| 变更分发 | `permission_change_outbox` + Dispatcher（Redis 重投，默认关） | 关 |

### 1.4 菜单与路由是「数据驱动」

- 后端 `MenuService.initMenu()` 写死菜单树（**但只被 `DevDataInitRunner` 调用**）；
- `path` 就是**前端路由全路径且含 `/list`**（如 `/console/wms/input/list`），`component` 缺省时**取 path**；
- 前端 `Console.vue` → `getMyMenuList()` → `initVueRouter()` 动态 `addRoute`；
- 实测对账：菜单 39 个节点，**除「首页」外 100% 能命中 `src/view/<path>.vue`**；
  **唯一缺口：`/console/system/log/list`（操作日志）页面存在但菜单里没有**。

## 2. 问题一：页面展示字段——必须改（附证据）

### 2.1 决定性证据：读侧 Mapper 只回主表列 + 外键 id

`InputMapper.xml` 的 `resultMap`：

```xml
<association property="purchase" javaType="...PurchaseEntity">
    <id column="purchase_id" property="id"/>   <!-- 只有 id，没有 name/code -->
</association>
```

注释把设计意图写得很清楚：

> 「明细和关联单据不在这里 JOIN」
> 「关联表不 JOIN：关系读取由 Service 调用受控详情出口完成，**避免未登记 JOIN 表形成旁路**」（`InventoryMapper.xml`）
> 「关系表不在本资源的权限绑定中；详情先只返回关联 ID」（`MaterialMapper.xml`）

而 JPA 读路径（当前默认）里关联是 **EAGER**（`InputEntity` 4 处 `@ManyToOne(fetch = EAGER)`），
所以**今天列表里的仓库名/客户名/物料名是有值的** —— 是 JPA 给的，不是 Mapper 给的。

> ⚠️ **风险窗口**：一旦按施工图把 `mapper-read.enabled` 打开并逐资源进 enforce，
> 前端这些列**不会报错，只会集体变空** —— 这是最难排查的一类回归。

### 2.2 前端现有字段与后端的错配（实测清单）

| 资源 | 前端有但后端没有 | 后果 |
| --- | --- | --- |
| 入库单 | `storage`（仓库） | 后端是 `structure`（**退料位置**）—— 不是同一个概念，属语义错配 |
| 库存 | `materialCode/materialName/unitName/storageName/structureName`（11 字段 vs 后端 7） | 5 列无数据来源 |
| 销售单 / 计划 | `customerCode/customerName/customerId`、`planBillCode` | 同上（Maple 路径下为空） |
| 工艺路线 | `materialCode/materialName/bomCode/bomName` | 同上 |
| 订单 | `materialCode/materialName/routing` | 同上 |
| 物料 / 设备 / 合同… | `unitName` / `label` 之类 | 同上（`label` 是前端 getter，无害） |

（实测方式：脚本解析后端实体 `private` 字段 + 继承链，与 `src/model/**/XEntity.ts` 声明字段逐项对比。）

### 2.3 三种解法（必须选一个，我推荐 A）

| 方案 | 做法 | 代价 | 评价 |
| --- | --- | --- | --- |
| **A（推荐）** | **后端补「读侧展示字段」**：列表 DTO 显式声明展示列，SQL 里 LEFT JOIN，并**把这些 JOIN 出来的字段一并纳入列级脱敏与行级条件**（正面回应「JOIN 成为旁路」的顾虑） | 后端每人日 0.5–1（21 资源） | 前端一次请求拿全，性能最好；脱敏链路可复用现有 `@SensitiveField` + `my-mask` |
| B | 前端按 id 二次请求详情 | 列表 15 行 → 15+ 请求（N+1），且每次都要过权限 | ❌ 只适合详情页，不适合列表 |
| C | 前端删掉这些列 | 信息量下降（列表看不到"给谁/什么料"） | ❌ 业务方基本不会接受 |

**无论选哪个，都应先产出「字段矩阵」**：`页面 × 列名 × 后端来源（实体列 / JOIN 列 / 计算列）× 是否脱敏 × 所需权限`。
我可以从后端实体 + Mapper + 前端页面**自动生成初稿**给你评审，评审通过后再写页面 —— 避免"页面写完才发现字段没来源"。

## 3. 问题二：库表要不要改（分「已够 / 要补 / 要修正」）

### 3.1 已经够用，不需要动

`user_tenant`、`user_factory`、`data_resource`、`data_policy`、`data_field_policy`、
`data_permission_diff_log`、`data_permission_deny_log`、`data_permission_orm_parity_log`、
`permission_change_outbox`、`operation_log`、`menu.permission`、`device.api_key`、`file.creator_id`
—— 二次改造的表都在，迁移脚本共 9 个（`docs/database/migration/`）。

### 3.2 需要补的 5 件事（按优先级）

| # | 缺口 | 为什么影响前端 | 建议 |
| --- | --- | --- | --- |
| 1 | **菜单没有生产播种路径**：`initMenu()` 只被 `DevDataInitRunner` 调用（dev profile） | 新前端上线后，生产库若 `menu` 表为空 → **登录后没有菜单、没有路由**，等于白屏 | 加一个**幂等迁移脚本**（或启动期 bootstrap）把菜单写进库；顺带补 `icon`（现在 seed 不设 icon → 新壳图标全是兜底）、`orderNo`、`permission` |
| 2 | **菜单缺「操作日志」** | 页面存在、菜单点不到（只能手输 URL） | 随 #1 一起补 `/console/system/log/list` |
| 3 | **`user.factoryList / storageList` 有表无 UI** | D13 后端已落地，但「给用户授权仓库/工厂」只能改 SQL —— 权限配置闭环缺一半 | 用户管理页加「仓库/工厂授权」编辑（多选树），或明确"暂不做" |
| 4 | **`data_resource` 登记行缺失** | 未登记 + `deny-unregistered` 打开 = 直接拒绝 | 播种脚本，或在数据资源页加「一键登记/扫描资源」 |
| 5 | **`DATABASE.md` 失真**（52 张表里 **21 张**在当前代码中不存在：`delivery/receipt/stock_in/stock_out/stock_check/work_order/work_report/quality_check/device_parameter/app_version/message…`） | 从零重构时若以它为准 → 设计出后端根本没有的模块 | 重新生成（从 JPA 实体 + 迁移脚本），或明确标注"历史规划表" |

### 3.3 视需求决定（现在不必做）

- **列偏好 / 看板布局持久化**：建议前端 localStorage，不建表（跨设备需求出现再上 `user_preference` JSON 表）；
- **导入任务进度**：若要"大文件导入 + 进度"，需要 `import_task` 表（当前没有）；
- **权限码 ↔ 菜单 ↔ 资源** 的完整绑定：`20260914_system_permission_identities.sql` 已开这个头；若按钮权限改由后端下发，需要把它补全。

## 4. 从零重构前端：建议路线

### 4.1 契约优先（第一步，不要跳过）

1. 在 dev / CI 起后端 → `GET /v3/api-docs`（生产按安全策略关闭，需在本地或 CI 出 spec，**不要在公网打开**）；
2. 用仓库里**已有但空跑**的 `pnpm api:generate`（`infra/scripts/generate-api.mjs` → `openapi-typescript-codegen`）生成 `src/api/generated`；
3. 以生成物为**唯一数据源**，替换现在"手写 42 个 api 模块 + 152 个 model 实体"的做法；
4. 产出 §2.3 的**字段矩阵**并评审。

> 这一步直接消灭本文 §2 里的一半问题：字段来源以契约（后端 DTO）为准，而不是前端"猜一个 join 名"。

### 4.2 技术选型（保留 / 替换）

- **保留**：Vue 3.5 · Vite 7 · TS 5.9 · Pinia 3 · vue-router 4 · **TanStack Query 5**（唯一服务端状态入口）· **Element Plus 2.12**（不换 UI 库）· ECharts 6 · Vitest 4；
- **替换**：`@airpower/web`（壳 `AFrame` / 表 `ATable` / 装饰器元数据表单）→ 自研
  `KAppShell` + `KDataTable` + 显式表单 schema；
- **删除**：`packages/api-client`（零引用死包）、`src/composables` 与 `src/hook` 双目录、`src/model/**Service`（48 个）。

### 4.3 必须保留的 4 条权限链路（否则安全设计失效）

1. **按钮级**：`v-permission`（现有 47 处）；
2. **路由级**：`meta.permission` + `permissionGuard`（后端菜单下发 `permission` 列）；
3. **列级脱敏**：`v-mask` / `useMaskPolicy`（`my-mask` 端点）+ **导出前预检** `useExportVisibility`；
4. **租户上下文**：`X-Tenant-Id` 请求头 + 切租户清缓存（并发请求不得跨租户复用）。

### 4.4 分期（建议）

| 期 | 内容 | 产出 |
| --- | --- | --- |
| **P0** | 契约 + 字段矩阵 + 设计系统（token / 壳 / 表格 / 表单规范） | spec + 3 个样板页（列表 / 表单 / 看板） |
| P1 | 按域铺开（wms → mes → channel → asset → system/personnel） | 每域可并行、可回滚 |
| P2 | 删旧（airpower / model Service / 旧壳） | 体积下降、依赖收敛 |
| P3 | 权限管理闭环补全（用户仓库/工厂授权、资源登记） | 运维可自助 |

### 4.5 与后端换轨的**顺序**（重要）

```
先定读侧展示字段契约  →  再切 mapper-read（逐资源）  →  再铺前端页面
```

反过来做（先铺页面、后切 Mapper）会出现"字段集体变空"的回归窗口，且责任难界定。
