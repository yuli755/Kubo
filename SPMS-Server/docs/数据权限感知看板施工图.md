## 2. 待下一批：业务概况（后端聚合读出口）

> 关键约束（立项时已定）：**聚合读出口必须走 Mapper + 拦截器同一条权限链，不能开旁路**。
> 用「不经行级过滤的 JPA COUNT」喂看板，等于把只对本租户可见的数据泄漏到统计图里。

### 2.1 语义：当前用户可见范围内的统计，而非跨租户

与 `law-firm-platform` 的角色看板同构：业务概况回答「**我**能看到的单据/库存/价格有多少」，
不是「全平台各租户有多少」。因此每一档统计都必须经过 `countByPermission(filter)`（该资源读侧
Mapper 出口，权限条件由拦截器注入），天然按当前用户的行级权限收敛，不会跨租户。

### 2.2 端点契约（建议形状）

```
GET /dashboard/overview            # 当前用户视角的业务概况（只读）
```

返回（示意，字段名最终以后端实体为准）：

```json
{
  "resources": [
    { "resourceKey": "channel.purchase", "label": "采购单",   "count": 12 },
    { "resourceKey": "channel.sale",     "label": "销售单",   "count": 30 },
    { "resourceKey": "wms.input",        "label": "入库单",   "count": 8  },
    { "resourceKey": "wms.output",       "label": "出库单",   "count": 6  },
    { "resourceKey": "wms.inventory",    "label": "库存",     "count": 421 },
    { "resourceKey": "channel.customer", "label": "客户",     "count": 55 },
    { "resourceKey": "channel.supplier", "label": "供应商",   "count": 18 }
  ]
}
```

- 每项 `count` 由对应资源的 `XxxMapper.countByPermission(filter)` 得出（filter 含当前用户租户/归属维度）。
- 资源清单在后端维护（`DashboardService` 内一张「资源键 → count 供给函数」的表），
  避免前端写死 14 个资源名再各发一个请求（那会退化成 N+1 且把资源清单抄到前端）。
- 权限：仅需登录身份（`getMyInfo` 级），返回内容本身已被行级权限过滤，不暴露跨租户元数据。

### 2.3 为什么「逐资源 count 端点」不如「单一 overview 端点」

14 个资源各开一个 `GET /xxx/count` 会让前端发 14 个请求、且把「哪些资源要上概览」这份清单
摊到前端。单一 `overview` 端点把清单收在后端，前端只渲染返回数组——与安全态势看板
「只搬运、不判定」同一条纪律。
