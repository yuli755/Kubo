## 2. 已落地：业务概况（后端聚合读出口）

> 关键约束（立项时已定，落地时守住）：**聚合读出口走 Mapper + 拦截器同一条权限链，不开旁路**。
> 用「不经行级过滤的 JPA COUNT」喂看板，等于把只对本租户可见的数据泄漏到统计图里。
>
> 落地形态（2026-09-10）：`DashboardController#overview`（`GET /dashboard/overview`，
> `@Permission(authorize = false)` 只要求登录）→ `DashboardService#overview` 对 14 个资源逐个调
> `getMapperCount(entity)` —— Mapper 开启走 `countByPermission`（拦截器注入权限条件），关闭回退
> JPA `filter().size()`（`addSearchPredicate` 注入权限谓词）。前端 `useBusinessOverview` +
> `BusinessOverview.vue`（对全部登录用户可见），`DashboardOverviewContractTest` 钉住 14 资源键
> 契约与「计数流经 getMapperCount、非硬编码」。

### 2.1 语义：当前用户可见范围内的统计，而非跨租户

与 `law-firm-platform` 的角色看板同构：业务概况回答「**我**能看到的单据/库存/价格有多少」，
不是「全平台各租户有多少」。因此每一档统计都必须经过 `countByPermission(filter)`（该资源读侧
Mapper 出口，权限条件由拦截器注入），天然按当前用户的行级权限收敛，不会跨租户。

### 2.2 端点契约（已实现）

```
GET /dashboard/overview            # 当前用户视角的业务概况（只读）
```

- 每项 `count` 由对应资源的 `getMapperCount(entity)` 得出（Mapper 开启走 `countByPermission`，
  关闭回退 JPA `filter().size()`，两者都经权限链）。
- 资源清单收敛在 `DashboardService#overview`（一张「资源键 → count 供给」的表），
  前端只渲染返回数组，不写死资源清单、不发 N+1 个 count 请求。
- 权限：`@Permission(authorize = false)` 仅需登录，返回内容本身已被行级权限过滤，不暴露跨租户元数据。

### 2.3 为什么「逐资源 count 端点」不如「单一 overview 端点」

14 个资源各开一个 `GET /xxx/count` 会让前端发 14 个请求、且把「哪些资源要上概览」这份清单
摊到前端。单一 `overview` 端点把清单收在后端，前端只渲染返回数组——与安全态势看板
「只搬运、不判定」同一条纪律。
