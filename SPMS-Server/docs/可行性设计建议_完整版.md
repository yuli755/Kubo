## 二、核心问题与修正建议

### 2.1 架构形态修正
- **当前事实**：模块化单体（asset、factory、iot、mes、wms 等）
- **规划文档假设**：已落地微服务集群
- **修正方案**：
  - 首期坚持“**模块化单体 + 可拆分边界**”策略
  - 仅在模块边界稳定、数据库事务边界清晰、独立部署有收益时才考虑拆分微服务
  - 先建立清晰的模块边界划分

### 2.2 协议冻结
- 当前实际：AirPower 原生 JSON 协议 + PING/PONG
- 规划文档同时出现“自定义 WebSocket”和“STOMP”
- **立即冻结方案**：
  - 保留原生 JSON 协议
  - 补充关键字段：`connectionId`、`messageId`、`eventVersion`、`serverTime`、`sequence`、`ack`、`resumeFrom`、`ttl`
  - 优先级策略：P0（安全/停机）必须确认，P1（设备状态）可合并覆盖，P2（普通日志）可丢弃或批量处理

### 2.3 性能与一致性边界
- 原目标：FCP<1.2s、TTI<2s、10k msg/s 无丢包、PWA 强缓存
- **修正后指标**（分场景）：
  - 首页：P75 FCP/LCP 达标（低端办公机 + 4G）
  - 核心读接口：P95 延迟 + 错误率
  - WebSocket：连接成功率、重连成功率、消息处理延迟、积压长度
  - 数据一致性：可确认、可重放、最终一致
  - PWA 只缓存静态资源和明确允许的只读数据

### 2.4 权限闭环
- 当前：仅有审计阶段，未实现行级/列级 + Outbox + Redis 版本化
- **必须完成顺序**：
  1. 租户隔离（tenant_id 必须显式带上）
  2. 行级权限（覆盖列表、详情、更新、删除、导出、批量）
  3. 列级脱敏（敏感字段动态脱敏）
  4. 缓存一致性（本地 + Redis + Outbox + RabbitMQ 版本化）

## 三、完整分阶段实施路线图

### 阶段 0：基线冻结与盘点（1-2 周）
**目标**：在不改变业务行为前提下确定权限边界和事实来源。

**工作项**：
- 生成受保护业务表清单 + 字段归属矩阵（tenant_id、部门、工厂、仓库、负责人等）
- 盘点所有 JPA Repository、复杂查询、导出/批量操作
- 记录现有 Redis Key 命名和权限缓存现状
- 建立越权测试数据集
- 统一错误码、分页结构、租户上下文、Trace ID

**产出**：
- 数据资源清单（data_resource）
- 权限回归基线
- 数据库迁移基线脚本

**通过条件**：每个试点资源都能明确数据归属字段，无归属字段的表标记暂缓接入。

### 阶段 1：权限模型 + 数据库迁移（2-3 周）
**目标**：把权限数据本身建起来。

**工作项**：
- 创建 `data_resource`、`data_policy`、`data_field_policy`、`permission_change_outbox` 表结构
- 为试点业务表补充租户字段并完成历史数据回填
- 将超级管理员从“用户 ID=1”迁移为显式系统权限
- 建立策略版本和变更审计机制
- 补充可执行的数据库迁移脚本（基于现有 `20260817_data_permission_model.sql`）

**产出**：可重复执行的迁移脚本 + 权限管理后台接口

### 阶段 2：权限内核实现（3-4 周）
**目标**：在不拦截现有业务 SQL 的前提下完成权限内核。

**工作项**：
- 定义 `PermissionContextResolver`
- 定义 `PermissionRuleProvider`（结构化条件树）
- 实现默认拒绝的 `PermissionDecisionService`
- 实现本地缓存 + Redis 版本化缓存
- 增加权限模拟接口（仅供测试环境）

**产出**：权限上下文和结构化规则模型

### 阶段 3：MyBatis-Plus 行级拦截 + 列级脱敏（4-5 周）
**目标**：建立可靠 SQL 拦截和脱敏能力。

**推荐迁移顺序**（每个模块必须完成）：
1. personnel / system（基础数据）
2. factory（组织结构）
3. wms / mes（核心业务）
4. asset / iot

**必须覆盖**：
- Entity/Mapper/Service 映射
- 分页、JOIN、统计、导出、批量操作验证
- 原 JPA 写路径下线
- @SensitiveField 列级脱敏

### 阶段 4：Outbox + RabbitMQ + 缓存一致性（3-4 周）
**目标**：权限变更可靠传播。

**工作项**：
- 权限变更和 Outbox 写入同一数据库事务
- 实现定时投递 + 幂等消费
- 清理本地缓存并递增 Redis 规则版本
- 增加人工重试和死信补偿

### 阶段 5：灰度与生产上线（2-3 周）
**上线顺序**：
1. 观察模式（只记录，不改变结果）
2. 对比验证
3. 单资源强制模式
4. 单模块灰度
5. 扩大租户/用户范围
6. 下线旧旁路

**回滚要求**：必须有明确版本号和向前兼容的迁移脚本。
